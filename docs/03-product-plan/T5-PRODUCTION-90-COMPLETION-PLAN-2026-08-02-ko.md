# T5 프로덕션 90 완성 계획

- 상태: `APPROVED_FOR_EXECUTION` · Wave 0 계약·계측 편입 완료 · 공식 30회 기준선 수집 대기
- 기준선: `b0111b6` · 회귀 1,898/1,898 · 돌연변이 235/235 · plan/docs/workspace PASS
- 목적: 현재 강한 개발 완성체를 일반 사용자가 반복해서 믿고 쓰는 90점대 프로덕션으로 끌어올린다.
- 범위: 장기 작업상태, 도구 턴 지연, 소비자 설치 생명주기, 실제 사용 폭
- 비범위: 기능 전면 재작성, 특정 모델 문구 맞춤, 광범위한 구조 건전화, 공개 배포 승인
- 실행 책임: Codex 5.6 Sol 본선 구현·통합. 같은 세션의 자체검증은 `겸임 구현`으로 표시하고,
  최종 감사는 오너가 준비한 독립 세션에서 수행한다.

## 1. 90점의 뜻

90점은 시험 수나 기능 목록이 많다는 뜻이 아니다. 일반 사용자가 자연어로 맡긴 일을 T5가 반복해서
이해하고, 실제로 수행하고, 못 한 것은 정직하게 말하고, 중단·재시작·업데이트 뒤에도 이어 가며,
터미널을 몰라도 설치·제거할 수 있다는 뜻이다.

각 작업선은 아래 100점표로 독립 평가한다.

| 축 | 배점 | 증거 |
|---|---:|---|
| 기능 완결 | 30 | 요청에서 사용자 결과까지 끊기지 않는 제품 경로 |
| 반복 신뢰성 | 20 | 결정적 반대시험과 변동 경로의 사전 등록 반복 |
| 실제 환경 관통 | 25 | 실제 모델·브라우저·파일·서비스·설치 산출물 |
| 인간 체감 | 15 | 질문·카드·지연·문장 밀도·복구 부담 |
| 운영·복구 | 10 | 재시작·실패·업데이트·되돌림·원장 |

다음 조건을 모두 만족해야 90점으로 판정한다.

1. 총점 90 이상이며 어느 축도 배점의 80% 아래가 아니다.
2. 거짓 성공, 민감정보 노출·지속, 잘못된 외부 실행, 되돌릴 수 없는 데이터 손실은 1건도 없다.
3. 실제 제품 경로 증거가 있다. fixture와 모델 대역만으로 90점을 선언하지 않는다.
4. 결과를 본 뒤 문턱을 바꾸지 않는다. 변경이 필요하면 이유와 이전 판정을 함께 남긴다.
5. 네 작업선이 모두 90 이상이고, 마지막 7개 코어 재평가도 각 90 이상이어야 전체 완료다.

### 1.1 Wave 0 점수 계약

구현 전에 작업선별 세부 문항·배점·분모·판정자를 별도 점수표로 동결한다. 아래 규칙은 그 점수표가
자의적으로 변하는 것을 막는 상위 계약이다.

1. 각 문항은 `결정적 사실`, `모델 변동 성능`, `사람 체감` 중 하나로만 분류한다.
2. 한 증거가 서로 다른 사실을 입증할 수는 있지만, 같은 사실의 점수를 여러 축에 중복 가산하지 않는다.
3. 자체검증은 구현선 점수, 읽기 전용 독립 감사는 증거 적합성 판정이다. 감사 PASS가 점수를 추가하지 않는다.
4. 미실행은 0점이다. 외부 자격·서비스 차단은 사전 등록된 대체 경로가 없으면 분모에서 빼지 않는다.
5. 모델·네트워크 실패는 end-to-end 성능에 포함하고 T5 내부 성능에서는 분리한다. 거짓 성공은 어느 쪽에서도
   성공으로 계산하지 않는다.
6. 결정적 계약은 상주 반대시험+제품 관통 1회, 모델 변동 계약은 사전 등록된 표본과 성공률로 판정한다.
7. 18개 항목과 7개 코어는 각각 독립 산식을 갖는다. 한쪽 평균으로 다른 쪽 90점 미달을 가리지 않는다.
8. 점수표 변경은 실행 전에만 허용한다. 실행 뒤 변경은 이전 점수와 변경 사유를 함께 보존하고 해당 표본을
   새 문턱의 증거로 재사용하지 않는다.

## 2. 실행 원칙

1. **진단은 짧게, 구현은 공통 원인에만.** 새 가설은 동일 상태 A/B 또는 결정적 반증으로 먼저 가른다.
2. **반복은 변동 경로에만.** 결정적 저장·권한·복구 계약은 상주 검사와 제품 관통 1회로 닫는다.
3. **모델을 대본으로 묶지 않는다.** Runtime은 사실·현재성·관계·경계를 공급하고 판단은 모델에 둔다.
4. **카드를 늘려 해결하지 않는다.** 새 승인은 외부 효과나 비가역 실행 경계에서만 허용한다.
5. **한 번에 한 작업선의 행동을 바꾼다.** 공용 파일 배선은 본선 통합자가 소유한다.
6. **성능과 정확성을 맞바꾸지 않는다.** 빠르지만 거짓인 답과 정확하지만 빈 화면인 답은 모두 실패다.
7. 광범위한 `server.js`·`turn.js` 분리는 별도 구조 건전화로 남긴다. 이 계획에서는 목표 달성에 필요한
   최소 책임 추출만 허용한다.

## 3. P90-1 장기 작업상태와 말귀

### 사용자 목표

30~100턴 프로젝트에서도 확정·수정·철회·미정·완료가 섞이지 않고, 마지막 종합과 다음 대화·재시작에서
현재 상태가 정확히 이어진다. 기억을 많이 넣는 것이 아니라 지금 필요한 프로젝트 사실만 조용히 놓는다.

### 단일 진실 계약

새 구조의 정본은 append-only `WorkEventLedger`다. 현재 WorkState는 사건 원장의 투영이며 별도 수정 가능한
두 번째 저장소가 아니다.

WorkEvent를 쓰기 전에 다음 신분 계약을 먼저 세운다. 현재 lane의 성공 판정이 정식 영수증
`lifecycle: delivered`가 아니라 fixture 전용 `executed`를 보고 있는 불일치도 이 진입 단계에서 먼저 닫는다.

- `ReceiptRef = TurnRef + turnOrdinal + receiptDigest`: 한 턴의 여러 실행을 각각 지목한다.
- `WorkRef`: OS가 작업을 처음 만들 때 발급하는 안정 신분. 산출물 집합 digest를 작업 신분으로 쓰지 않는다.
- `CompletionContractRef = WorkRef + contractDigest`: 완료 계약과 그 계약을 충족한 영수증을 결합한다.
- `subjectRef`: 최초 사건에서 OS가 발급하고 수정·철회 사건은 대상 사건에서 상속한다.
- 모델이 제출한 임의 내부 신분은 수용하지 않는다. 모델은 사용자에게 보인 문장을 지목하고 OS가 ref로 대조한다.

| 사건 | 진실 출처 | 활성 조건 |
|---|---|---|
| `agreement_set` | 사용자 발화 원문+정확한 `TurnRef` | 원문 대조 성공 |
| `agreement_superseded` | 새 사용자 발화+기존 사건 ref | 대체 관계 대조 성공 |
| `agreement_retracted` | 사용자 철회 발화+기존 사건 ref | 대상 사건을 정확히 지목 |
| `question_opened` | 내용 있는 모델 질문+assistant `TurnRef` | 답을 바꾸는 미정 대상이 명시됨 |
| `question_resolved` | 사용자 답변 `TurnRef` 또는 확인 `ToolReceipt` | 열린 미정 사건 ref와 해소 근거가 결합됨 |
| `execution_completed` | `CompletionContract`+성공 `ToolReceipt` | 모든 완료 검증 통과 |
| `chat_delivered` | CHAT 결과 계약+assistant `TurnRef` | 내용 있는 결과가 실제 지속됨 |

모델은 사건 후보와 근거 ref를 제안할 수 있지만 단독으로 활성 사건을 만들 수 없다. 특히 모델의 `done` 주장은
완료 근거가 아니며, 파일·전송·실행 완료는 반드시 영수증과 완료 계약에서 파생한다. `chat_delivered`는
내용 있는 대화 결과가 전달됐다는 뜻이며, CHAT 결과 계약이 그 산출물 자체를 완료로 정의하지 않는 한 프로젝트
전체 완료를 뜻하지 않는다.

### 기존 상태 구조와의 관계

- `session.workingState`: 영수증에서 파생되는 짧은 실행 현황. WorkEventLedger에 흡수하거나 재저장하지 않는다.
- `activeGoal`: 모델이 이해한 추정 라벨. scope·완료·합의의 근거로 사용하지 않는다.
- `ActiveWorkLane/carryableWork`: 검증된 다른 대화 작업을 공급하는 투영. 원천은 WorkEventLedger와 기존
  receipt 사실이며 독립 수정 권한을 갖지 않는다.
- T-cell: 선호·원리·학습을 소유한다. 프로젝트 합의·미정·완료를 학습 기억으로 승격하지 않는다.

scope는 tagged `ScopeRef`로 둔다. cross-session 공급에는 `principalRef`가 필수이며, 프로젝트·workspace·대상
범위가 실제로 있을 때 `projectRef`, `workspaceRef`, `subjectRef` 중 해당 신분을 결합한다. 단일 대화의 일시적
상태에 존재하지 않는 프로젝트 신분을 지어내지 않는다. 신분 미상 사건은 cross-session에 공급하지 않는다.

### 저장·migration·복구 계약

1. 새 사건은 원자 append하며 기존 사건을 제자리 덮어쓰지 않는다.
2. 옛 세션의 `workingState`·`activeGoal`은 사실을 추측해 소급 사건으로 만들지 않는다. 읽기 호환만 유지한다.
3. migration은 버전·입력 digest·결과 digest·건수를 영수증으로 남긴다. hash chain 손상은 중간 사건을
   건너뛰지 않고 마지막 유효 checkpoint에서 멈춘 뒤 read-only degraded 상태로 전환한다.
4. migration 전 snapshot과 rollback 경로를 둔다. 재시작·중단 뒤 같은 사건이 중복 생성되지 않는다.
5. 수정은 `supersedes` 관계로 표현한다. `changed`를 lifecycle 상태로 저장하지 않는다.
6. 모델 입력에는 현재 요청과 관련된 활성 사실·미정·완료만 상한 안에서 공급한다.
7. 사용자에게 새 관리 카드를 요구하지 않는다. 요청했을 때만 현재 합의·미정·완료를 자연어로 보여준다.
8. 민감정보와 원시 비밀은 사건 원장에 들어가지 않는다. 기존 공용 민감 경계를 그대로 사용한다.
9. 첫 편입은 shadow projection이다. 새 원장에 결합된 작업만 새 cross-session 투영을 사용하고 나머지는
   legacy lane을 유지한다. `workingState.recentOutcome`을 새 투영으로 바꾸는 것은 완료 계약 A/B 뒤다.

구현 순서는 `delivered` 불일치 정정 → ReceiptRef → 완료 계약 신분 결합 → WorkEvent 저장소 → shadow
projection → legacy lane A/B → 제한 cutover다. 순서를 건너뛰어 WorkState부터 저장하지 않는다.

### 선실패 반증

- 철회한 행사명이 30턴 뒤 종합에서 부활한다.
- 35명에서 28명으로 고친 뒤 두 값이 동시에 현재 사실로 남는다.
- 미정 장소를 확정으로, 대화를 통한 초안을 실제 파일 완료로 보고한다.
- 재시작 뒤 완료·미정·철회 관계가 사라진다.
- 무관한 새 대화에 프로젝트 상태가 과잉 입장한다.
- 상태를 많이 쌓을수록 프롬프트 상한과 응답 지연이 계속 증가한다.

### 90점 종료 조건

- 3개 도메인 프로젝트를 각각 30·60·100턴으로 실행한다.
- 중요 확정·수정·철회·완료의 최종 종합 정확도 **100%**, 비핵심 상태 정확도 **95% 이상**.
- 철회 사실 부활 0, 거짓 완료 0, 무관 대화 입장 0, 추가 승인 카드 0.
- 새 대화와 재시작 뒤 현재 작업 복원 3/3.
- Codex 기준 응답과 비교해 사용자 정정 횟수와 종합 누락이 더 많지 않다.

## 4. P90-2 도구 턴 지연과 응답 밀도

### 사용자 목표

T5가 생각 중이라는 표시만 즉시 띄우는 데서 끝나지 않고, 사용자가 기다릴 가치가 있는 첫 내용과 단계별
결과를 빠르게 보여준다. 짧은 답은 짧고, 긴 작업은 무엇을 확인했고 무엇이 남았는지 자연스럽게 흐른다.

### 구현 계약

1. 최적화 전에 계측만 먼저 편입한다. 입력 수신부터 화면 표시까지 아래 사건을 단조 시계로 기록한다.
   원문 프롬프트·비밀·도구 인자는 저장하지 않고 시간·종류·상태·결합 신분만 기록한다.
2. 모델 선택, 연결 확인, 도구 왕복, 후처리 중 실제 병목을 먼저 확정한다. 측정 전에 캐시·병렬화·호출 제거를
   넣지 않는다.
3. 서로 독립이고 읽기 전용인 도구만 제한 병렬화한다. 권한·원장·호출 횟수 상한은 넓히지 않는다.
4. 이미 기계 사실로 끝난 결과는 불필요한 추가 모델 호출 없이 사용자 언어로 투영하되, 판단이 필요한 답은
   모델을 건너뛰지 않는다.
5. 장기 작업은 확인된 중간 결과를 먼저 보여주고 다음 단계를 이어 간다. 실행 전 성공 예고는 금지한다.
6. 응답 밀도는 요청한 개수·형식·길이를 우선하고, 상투 문구와 앞선 내용 반복을 줄인다. 특정 문장 정규식으로
   모델 출력을 고정하지 않는다.

### 측정 기준

| 사건 | 뜻 |
|---|---|
| `input_received` | 서버가 사용자 입력을 수신 |
| `first_feedback_visible` | 첫 진행 표시가 실제 화면에 렌더됨 |
| `first_grounded_content` | 일반 대화의 첫 답 조각 또는 receipt와 결합된 첫 `partial_result`가 화면에 렌더됨 |
| `turn_complete` | 지속 결과·원장·표면이 같은 턴으로 닫힘 |
| `external_wait` | 모델·네트워크·외부 서비스 대기 |
| `t5_overhead` | 컨텍스트 조립·라우팅·투영·표면 처리 |

`first_grounded_content`는 단순한 “확인 중” 문구가 아니다. 도구 턴에서는 receipt 신분 또는 검증된 중간
결과와 결합돼야 한다. 일반 대화에서는 사용자에게 보이는 첫 최종 답 조각이다.

| 경로 | 첫 진행 p95 | 첫 유용한 내용 p95 | 완료 p95 |
|---|---:|---:|---:|
| 일반 대화 | 0.5초 | 3초 | 8초 |
| 로컬 파일·문서 | 0.5초 | 8초 | 20초 |
| 웹 조사·브라우저 | 0.5초 | 12초 | 30초 |
| 제한 에이전트 | 0.5초 | 15초 이내 첫 확인 결과 | 작업 예산 안에서 단계별 결과 제공 |

외부 모델·네트워크 대기는 T5 자체 오버헤드와 분리한다. T5 내부 p95 오버헤드는 1.5초 이하를 목표로 한다.

### 90점 종료 조건

- 경로별 최소 30회, cold/warm을 분리해 위 p95를 기록하고, 빈 답·조각/최종 불일치·거짓 진행 0.
- end-to-end와 `t5_overhead`를 함께 보고한다. 외부 대기를 빼서 사용자 체감 성공으로 주장하지 않는다.
- 현재 기준선 대비 도구 턴 중앙값 30% 이상 단축 또는 절대 기준 충족.
- 사용자가 요청하지 않은 서론·반복 요약·선택지 과잉이 사람 평가 표본의 5% 이하.
- 느린 외부 서비스에서도 취소·재시도·다른 경로 선택이 원장과 화면에 정직하게 남는다.

## 5. P90-3 비개발자 설치·업데이트·제거 생명주기

### 사용자 목표

터미널과 환경변수를 몰라도 설치하고, 계정을 연결하고, 재시작 뒤 자동으로 이어 쓰고, 안전하게 업데이트하거나
이전 버전으로 돌아가며, 제거할 때 자기 데이터를 보존·내보내기·삭제 중 선택할 수 있다.

### 구현 계약

1. 지원 macOS 버전·CPU·신규 설치·기존 개발본 이관 행렬을 먼저 동결한다.
2. 서명·notarization된 macOS 설치 산출물과 설치 manifest를 만든다.
3. background service의 설치·시작·중지·재시작·상태 확인을 하나의 생명주기로 묶는다.
4. 모델·커넥터 자격은 값 노출 없이 Keychain 또는 동등한 OS 비밀 저장소에 둔다. 대화·로그·진단에 원문을
   남기지 않는다.
5. 업데이트 manifest는 서명·해시·버전·호환 스키마를 갖고 임의 하향 설치를 차단한다. 승인된 복구는 별도
   서명된 rollback 경로로만 수행한다.
6. 실행 중 업데이트는 새 턴 수용 중지→진행 작업 quiesce/취소→single-writer 인계→교체 순서를 따른다.
7. migration 전에 데이터 snapshot을 만들고, 결과 영수증과 재개 지점을 남긴다. 새 스키마 적용 뒤 이전
   실행본으로 돌아갈 수 있는 조건과 불가능한 조건을 manifest에 명시한다.
8. 기존 파일 자격을 Keychain으로 이관한 뒤 원본을 안전하게 제거한다. 실패하면 기존 자격을 지우지 않고
   연결되지 않았다고 정직하게 표시한다.
9. 제거는 앱만 제거, 데이터 내보내고 제거, 완전 삭제를 분리한다. 기본값은 사용자 데이터 보존이며 완전
   삭제는 Keychain 항목까지 대상과 결과를 보여준다.
10. 설치 산출물에서 온보딩→첫 대화→재시작→업데이트→복구→제거를 검증한다. 개발 트리 실행을 증거로 쓰지 않는다.
11. 공개 배포·실사용자 데이터 삭제·서명 자격 사용은 오너의 명시 승인 뒤에만 수행한다.

### 90점 종료 조건

- 지원 행렬의 깨끗한 VM 또는 별도 물리 장치에서 설치→첫 대화→재시작을 검증한다. 같은 OS의 사용자
  계정 3개만으로 호환성을 주장하지 않는다.
- 정상 업데이트, 실행 중 업데이트, 손상 패키지 업데이트 각각 복구 3/3.
- 제거 세 선택지에서 데이터 보존·내보내기·삭제 결과가 화면 설명과 100% 일치.
- 터미널 명령 요구 0, 비밀 원문 로그·대화·원장 노출 0, 고아 프로세스·리스너 0.
- 설치·업데이트·제거 실패 시 사용자가 다음 행동을 한 문장으로 이해할 수 있다.

## 6. P90-4 실제 사용 폭과 장기 인간 사용

### 사용자 목표

한 시나리오를 과연마한 제품이 아니라, 일반 사용자가 말로 맡기는 서로 다른 일에서 T5의 일곱 코어가
같이 작동한다. 처음 보는 모델·도구·서비스도 현재 능력과 한계를 파악하고 연결·실행·복구할 수 있다.

### 시나리오 포트폴리오

1. 장기 운영 프로젝트와 마지막 종합
2. 실제 파일·문서 묶음 판단과 별도 산출물
3. 최신 웹 조사와 출처·시간 비교
4. 로그인 또는 동적 화면의 브라우저 관찰·제한 행동
5. OAuth/API/MCP/CLI 중 처음 보는 연결과 연결 해제
6. Telegram·Slack 등 시험 채널의 승인 전송과 원래 자리 회신
7. 자연어 Skill·Trigger·예약·취소·재시작 복구
8. 제한 에이전트의 병렬 조사·통합·중단
9. 파일 없음·권한 없음·네트워크 실패·모델 실패의 다음 행동
10. 민감정보·외부 효과·삭제·업데이트의 권한 경계
11. 데스크톱·좁은 화면·긴 대화의 실제 클릭·입력·스크롤
12. 처음 연결한 지원 모델에서의 동일 핵심 여정

### 실행 규율

- 최소 24개 서로 다른 사용자 여정을 등록하고 실제 브라우저로 수행한다.
- 결정적 여정은 제품 관통 1회+상주 반대시험, 모델 판단 여정은 사전 등록 3회로 측정한다.
- 주 모델과 다른 계열의 보조 모델에서 핵심 8개 여정을 교차한다.
- 외부 서비스는 시험 계정·격리 폴더·허용된 수신처만 사용한다.
- Codex 기준 응답은 자연스러움·밀도·목표 도달 비교에만 사용하고 T5 내부 도구 구조를 흉내 내지 않는다.

### 90점 종료 조건

- 24개 여정의 사용자 목표 달성률 90% 이상, 안전·정직성 P0 0.
- 불필요 카드·질문은 전체 턴의 5% 이하, 위험 실행은 필요한 승인 100%.
- 거짓 성공·확인하지 않은 사실·실행하지 않은 행동 주장 0.
- 처음 보는 연결 3종에서 준비→확인→능력 반영→해제 3/3.
- 4시간 지속 사용과 재시작 뒤 원장·작업·자동화 상태 불일치 0.
- 일반 사용자 3명 이상의 관찰 사용에서 치명적 막힘 0, 도움 없이 핵심 여정 완료율 90% 이상.

## 9. 중단 조건

- 한 사례를 통과시키기 위한 서비스명·문장·낱말 정규식이 제품 판단에 들어간다.

- 원시 비밀·실사용자 파일·외부 수신처가 시험 데이터에 들어간다.
- 측정기가 제품보다 복잡해져 같은 원인을 두 번 이상 잘못 분류한다.
- 통과 숫자를 만들기 위해 실패를 안전한 무반응으로 재분류하거나 문턱을 낮춘다.

## 10. 최종 완료 선언

`T5_PRODUCTION_90_CANDIDATE`는 다음 조건을 모두 충족할 때만 사용한다.

1. P90-1~4가 각각 90점 이상이다.
2. 전체 18개 평가 항목과 일곱 코어 재평가가 각각 90점 이상이다.
3. 현재 회귀·돌연변이·문서·workspace·패키지 게이트가 통과한다.
4. 설치 산출물에서 핵심 12개 사용자 여정이 재현된다.
5. P0는 0이어야 한다. 미해결 P1은 해당 항목의 사전 등록 점수가 여전히 90 이상이고, 사용자 목표·안전·복구를
   막지 않는 경계가 증명된 경우에만 오너가 기록된 제한으로 수용할 수 있다. P1 때문에 어느 항목이 90 미만이면
   후보판을 차단한다.
6. 공개 배포는 별도 오너 승인이다. 후보판 완료가 자동 공개를 뜻하지 않는다.
