- 작성: 2026-08-02
- 상태: `OWNER_DECISION_LOCKED_B`
- 제품 기준선: 현재 브랜치 HEAD (W1~W6 개발 종결 + OAuth H10 라이브 보강)
- 목적: 오너가 확정한 **다듬기 → 구조 정리 → 설치본** 순서를 보존한다.

## 0. 오너 결정 (2026-08-03)

오너는 선택 B를 확정했다. HumanRealTest 다듬기를 먼저 적용하고, 세 과밀 파일을 행동 보존형으로
정리한 뒤 소비자 설치 lifecycle을 시작한다. 아래 A/B 비교는 결정 근거로 보존하며 현재 선택지는 아니다.

## 1. 지금 확정된 사실

| 항목 | 현재 증거 |
|---|---|
| T-cell·PC 손발 | H01~H09 봉인 |
| Automation·Agent | AC-2~AC-7 canonical 경로와 OAuth `gpt-5.5` H10 제한 위임 2자식 제품 관통 |
| 실전 업무 | 문서·보고서·커뮤니케이션·조사·반복업무 등 7개 흐름 |
| 전체 개발 게이트 | 회귀 1830/1830 · 돌연변이 195/195 · 공식 gate PASS(CPU 42.0s/45.75s · 벽시계 19.6s) |
| 최소 배포 산출물 | `npm pack` 151개 파일을 펼쳐 실제 부팅·health·온보딩 PASS |
| 아직 아닌 것 | 서명 설치본 · background service · update · uninstall/recovery · 공개 배포 |

따라서 선택 대상은 “T5가 작동하는가”가 아니다. **작동하는 현재 기준선을 먼저 사용자에게 설치할지,
행동을 보존한 구조 보강을 먼저 할지**다.

## 2. 선택 A — 설치본을 먼저 만든다

### 얻는 것

- 비개발자가 설치·실행·업데이트·제거하는 실제 경로를 빨리 검증한다.
- 코드 구조에 대한 추측보다 실제 사용 마찰과 고장 데이터를 먼저 얻는다.
- 현재 봉인된 제품 행동을 설치본 기준선으로 고정할 수 있다.

### 작업 범위

1. macOS 서명 패키지와 설치 manifest
2. background service 설치·중지·재시작·상태 확인
3. 모델 자격과 데이터 위치를 값 노출 없이 설명하는 `.env.example`/진단 경로
4. 원자적 업데이트·실행 중 교체·이전 버전 복구
5. uninstall 시 데이터 **내보내기·보존·삭제** 선택
6. 깨끗한 컴퓨터에서 설치→온보딩→첫 대화→재시작→제거 관통

### 위험과 통제

- `server.js` 2357줄, `turn.js` 1463줄, `tcell-grow.js` 1215줄의 높은 책임 밀도는 그대로 남는다.
- 설치 중 구조 리팩터링을 섞지 않는다. 설치 결함만 최소 수정하고 구조 문제는 별도 원장에 남긴다.
- 서명·공개·실사용자 데이터 삭제는 오너의 명시 승인 전 실행하지 않는다.

### 종료 조건

서명 산출물에서 설치·첫 실행·재시작·업데이트·복구·제거가 통과하고, 사용자 데이터 선택이 실제로
보존되며, 개발 트리가 아닌 설치 산출물에서 핵심 사용자 여정이 재현된다.

## 3. 선택 B — 구조 보강 뒤 설치본을 만든다

### 얻는 것

- 설치·업데이트·향후 기능 추가 전에 큰 파일의 책임과 변경 영향 범위를 줄인다.
- 새 개발자와 에이전트가 단일 진실·저장·실행 경계를 더 빨리 이해한다.
- 설치 이후 구조 변경으로 생길 데이터 migration 부담을 미리 줄일 수 있다.

### 작업 범위

정본은 [T5 완성 후 구조 건전화 작업](T5-POST-COMPLETION-STRUCTURAL-HARDENING-ko.md)이다.
우선순위는 다음 세 묶음으로 한정한다.

1. `server.js`: 조립·HTTP 표면·scheduler lifecycle의 책임 분리
2. `turn.js`: 대화 조정·도구 실행·완료 계약·표면 투영의 책임 분리
3. 저장/migration과 성장 worker의 단일 진실·복구 경계 정리

### 위험과 통제

- 실제 사용자 피드백 전에 내부 구조를 과도하게 다듬을 위험이 있다.
- 기능 추가·정책 변경·프롬프트 튜닝을 금지하고, 한 책임씩 행동 동등성을 증명한다.
- 질문·카드·클릭·지연·기억·승인·원장 결과가 기준선보다 나빠지면 해당 묶음을 되돌린다.

### 종료 조건

기존 1824개 회귀와 187개 돌연변이, W5 7개 흐름, W6 전체 경로가 그대로 통과하고, 책임 수·중복
판정·의존 방향·변경 영향 범위가 실제로 감소한다. 그 뒤 선택 A의 설치 lifecycle을 그대로 수행한다.

## 4. 비교

| 판단 기준 | A 설치 먼저 | B 구조 먼저 |
|---|---|---|
| 실제 사용자 피드백 | 가장 빠름 | 늦음 |
| 설치 이후 구조 변경 위험 | 더 큼 | 더 작음 |
| 내부 리팩터링 과몰입 위험 | 작음 | 큼 |
| 첫 설치본까지 작업량 | 작음 | 큼 |
| 개발자 인수인계 안정성 | 현재 수준 | 개선 가능 |
| 최종 설치 lifecycle | 반드시 수행 | 구조 보강 뒤 반드시 수행 |

## 5. 결정 당시 Codex 권고 (역사)

**기본 권고는 A, 설치본 우선**이다. 현재 제품 경로와 패키지 산출물은 이미 검증됐고, 다음으로 가장
값진 증거는 실제 설치·재시작·업데이트·제거에서 나온다. 구조 보강의 필요성은 분명하지만, 사용자
사용 전 내부 구조를 먼저 다듬으면 과밀 파일보다 더 큰 위험인 **실제 사용 없는 과연마**가 다시 생길 수 있다.

다만 공개 직후 여러 개발자가 동시에 코어를 수정할 계획이 확정돼 있다면 B가 더 적합하다. 이 경우에도
구조 보강은 위 세 묶음만 먼저 수행하고, 새 기능이나 전체 재작성으로 넓히지 않는다.

## 6. 현재 실행 지시

1. HumanRealTest의 확인된 다듬기와 오너 지정 UI 다듬기를 완료한다.
2. `server.js` → `turn.js` → `tcell-grow.js`를 한 책임씩 행동 보존형으로 정리한다.
3. 기존 제품 검사와 HumanRealTest로 동등성을 확인한다.
4. `P-DIST consumer lifecycle`을 시작한다.

어느 선택도 W1~W6을 재개봉하지 않는다. 설치나 구조 작업에서 재현된 영향 계열만 좁게 다시 연다.
