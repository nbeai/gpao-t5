## 1. 제안 결론

T-cell H01~H07은 최종 봉인됐다. 이제부터는 Claude 한 세션이 조사·구현·검사·감사·문서까지 전부
직렬로 떠안지 않는다. **Claude는 정본 통합 책임자**, 병렬 에이전트는 서로 겹치지 않는 구현·조사·감사
작업선을 맡는다.

병렬화의 목적은 에이전트 수를 늘리는 것이 아니다.

1. 서로 독립인 작업을 동시에 끝낸다.
2. Claude가 한 부분에 깊게 들어갈 때 다른 표면의 누락을 에이전트가 찾는다.
3. 정본 판단과 최종 제품 관통은 한 곳에만 둔다.
4. sidecar의 검증이 정본 저장소와 경쟁하지 않게 한다.
5. 보고서 생산보다 실제 사용자 목적 달성 경로를 먼저 닫는다.

첫 병렬 배치는 **PC 손발 H08~H09**다. 동시에 AC-2 기존 작업선은 읽기 전용 재감사까지만 한다.
H08~H09가 봉인되기 전 Automation 제품 코드를 정본에 합치지 않는다.

## 4. 병렬 개발 운영 모델

### 4.1 역할

| 역할 | 책임 | 하지 않는 일 |
|---|---|---|
| 오너 | 사용자 목적·우선순위·최종 체감·외부 권한 결정 | 기술적 충돌 조정, 반복 검사 실행 |
| Claude 본선 | 공통 계약, 통합 순서, shared file, 제품 관통, 최종 커밋 | 모든 조사와 검사를 혼자 직렬 수행 |
| 구현 에이전트 | 소유 파일 안의 좁은 구현과 집중 검사 | shared file 임의 편집, 정본 직접 병합 |
| 감사 에이전트 | 읽기 전용 재현, 누락·거짓 완료·경계 확인 | 제품 코드 수정, 패치 답안 강제 |
| Codex 감사 | 통합 묶음 종료 후 독립 제품 경로 감사 | 구현 도중 결함을 한 건씩 직렬 투척 |

### 4.2 동시 작업 상한

- Claude 본선 외 **활성 에이전트 최대 4개**.
- 구현 에이전트는 최대 3개, 나머지 1개는 읽기 전용 감사 또는 다음 파동 준비다.
- 같은 파일을 두 작업선이 동시에 소유하지 않는다.
- `src/surface/server.js`, `src/kernel/turn.js`, `src/surface/live-context.js`, 공통 계약, 인수인계,
  진행표는 Claude 본선만 편집한다.
- 전체 회귀·돌연변이·workspace 감사는 정본 통합창에서 직렬로 한 번 실행한다.
- sidecar는 집중 검사만 실행한다. 정본과 동시에 전체 회귀를 경쟁시키지 않는다.

### 4.3 작업선 등록

각 작업선은 시작 전에 인수인계 원장에 아래를 한 줄로 등록한다.

```text
이름 | 목적 | 브랜치/worktree | 소유 파일 | 읽기 전용 파일 | 종료 조건 | 상태
```

상태는 `작업 중 / 통합 대기 / 채택 / 보류 / 폐기`만 쓴다. 에이전트가 끝났다는 사실과 정본에
채택됐다는 사실을 섞지 않는다.

### 4.4 통합 순서

1. Claude가 현재 HEAD와 공통 계약을 동결한다.
2. 에이전트는 별도 worktree에서 수정 전 실패를 확인한다.
3. 에이전트는 소유 범위의 최소 구현·집중 검사·커밋을 제출한다.
4. 감사 에이전트는 해법 없이 문제·재현·영향·보존 조건을 제출한다.
5. Claude가 B(보호·복구) → A(파일 손발) 순서로 커밋을 검토·통합한다.
6. shared file 배선은 Claude가 직접 한다.
7. 제품 경로를 한 번 관통한다.
8. 전체 회귀 → 돌연변이 → plan/docs/workspace 순서로 직렬 실행한다.
9. Codex가 통합 결과를 한 묶음으로 독립 감사한다.
10. 통과한 뒤 sidecar를 닫고 정본·원격·인수인계를 동기화한다.

store 계열은 재사용 후보, `skill-replay-runner`는 현재 T-cell replay 영수증·신분 결합과 중복 가능성이
큰 재구현 후보로 보고 D가 확정한다.

### H08~H09 종료 조건

- H08 실제 사용자 목적 달성
- H08 원본 변경 0, 결과물 별도 생성
- H09 같은 실패 반복 0
- H09 거짓 성공 0
- 카드·필수 클릭 증가 0
- 주 모델 제품 경로 PASS

## 6. Automation Core 병렬 배치

H08~H09가 닫히면 AC-1 대조를 먼저 한 뒤 다음 세 작업선을 동시에 연다.

| 작업선 | 주 소유 | 공통 접점 | 종료 산출물 |
|---|---|---|---|
| AC-2 Skill | `skill-learning.js`, `skill-store.js`, skill 집중 검사 | 통제 채널·server 배선은 본선 | propose→replay→active→rollback 관통 |
| AC-3 Trigger | scheduler, trigger provider, claimer, trigger 검사 | AgentRun 생성 계약 | 재시작·misfire·claim·중복 0 |
| AC-4 Agent | agent profile, runner, registry, agent 검사 | modelFor(role)·authority 교집합 | 제한된 단일/독립 병렬 run |

Claude는 공통 계약과 shared file만 소유한다. AC-2·3·4가 각자 실행기를 만들지 않게 한다.

그다음은 다음 순서로 통합한다.

```text
AC-2 + AC-3 + AC-4
→ AC-5 Unified Automation
→ AC-6 사용자 표면과 AC-7 설치·상주 준비 병렬
→ 제품 통합
→ Automation Core Closure
→ H10
```

AC-5 이전에는 Skill·Trigger·Agent 각각의 성공을 “자동화 완료”라고 부르지 않는다.

## 7. 검증 비용과 종료 규칙

### 유지할 것

- 수정 전 실패
- 좁은 집중 검사
- 실제 제품 경로 관통
- 위험 계약의 돌연변이
- 통합 뒤 전체 회귀
- 실제 모델·실제 화면·실제 파일 상태 확인

### 줄일 것

- 모든 sidecar의 전체 회귀 반복
- 같은 사실을 여러 문서에 장문 복제
- 모델 변동을 코드 결함처럼 무한 수정
- 측정기를 제품보다 크게 만드는 일
- 이미 봉인된 T-cell H02 재실행

### 즉시 중단 조건

- 작업선이 소유하지 않은 shared file을 수정함
- 정본과 sidecar가 동시에 같은 파일을 수정함
- fixture가 사용자 실제 원본을 건드림
- 민감 원문이 증거·로그·원장에 남음
- 실패를 성공으로 기록함
- 기준을 결과 확인 뒤 완화함
- 검증 도구가 활성 소스를 변조함

중단은 작업 포기가 아니다. 원인을 분리한 뒤 해당 작업선만 다시 연다.

## 10. 성공 판정

이 제안이 성공한 것은 에이전트가 많이 돌았을 때가 아니다.

- 서로 기다릴 필요 없는 작업이 실제로 동시에 끝난다.
- 정본 충돌과 검증 오염이 없다.
- Claude가 통합과 제품 완성에 집중한다.
- 오너에게 기술 조정과 반복 검사 부담이 넘어오지 않는다.
- H08~H09 이후 AC-2~H10까지 같은 방식으로 속도와 정확성이 함께 좋아진다.
- 최종적으로 질문·카드·클릭을 늘리지 않고 사용자의 실제 컴퓨터에서 목적을 끝낸다.

이 조건을 만족하지 못하면 에이전트 수를 줄이고, 병렬화 가능한 책임 경계부터 다시 고정한다.
