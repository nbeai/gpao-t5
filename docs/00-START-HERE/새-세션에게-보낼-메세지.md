**① 한 번 통과한 것은 되는 게 아니다. 조건을 바꿔서 다시 해라.**

  "계산기 화면 읽어줘" 가 **여섯 번 통과했다.** 두 판에서 3/3, 3/3.
  그리고 오후에 안 됐다. 코드가 바뀌어서가 아니었다 — **같은 커밋에서도 안 됐다.**
  접근성 트리가 그 창을 잡는 상태였을 때만 됐던 것이고, 우리는 그걸 "됨"으로 적었다.

  → 통과했으면 **조건을 하나 바꿔서** 다시 해라. 창을 뒤로 보내고, 앱을 껐다 켜고,
    다른 앱을 앞에 놓고. 한 조건에서만 되는 것은 **되는 게 아니다.**
  → 실패했을 때 무엇이 실패했는지도 봐라. 손이 못 한 건지, 손은 했는데 안 쓴 건지.

**② 만든 것과 닿은 것은 다르다. 하루에 여덟 번 났다.**

  값을 만들고, 규칙을 쓰고, 손을 붙였는데 소비자까지 안 이어진다.
  검사는 초록이고 제품은 그대로다. 실제 사례:

    화면 손이 제품에 없었다(환경변수 미점화) · 화면 사용법이 모델에 한 번도 안 갔다 ·
    예약을 만들어 놓고 모델이 몰랐다 · 로그인 크롬이 제품에 없었다 ·
    `도구쓰는순서` 를 **읽는 자리가 0곳**이었다(원래부터 끊겨 있었다) ·
    후보를 올려도 붙이는 자리가 파일 손 전용이었다

  → 고치기 전에 **끝에서 끝까지 태우는 검사부터** 세워라.
    단위 검사는 이걸 절대 못 잡는다. `buildTaskContext → buildModelMessages → turn.js`
  → "이 값이 실제로 모델 입력에 들어가는가"를 **밟아서** 확인해라. 코드를 읽지 말고 찍어봐라.

**③ 이름을 바꾸는 것은 고치는 게 아니다.**

  모델이 실패로 읽는 필드를 `못읽은이유` → `글자만못읽은이유` 로 바꿨다.
  모델은 여전히 실패로 읽었다. **행동이 안 바뀌면 안 고친 것이다.**

**④ 밟은 것만 사실이다. 주석도, 설정 파일도, 남의 보고도 아니다.**

  · 같은 파일 안에서 두 주석이 **반대로** 말하고 있었다. 셋이 차례로 속았다.
  · `config.yaml` 은 `gpt-5.1` 인데 실제 나간 요청은 다른 모델이었고 401 이었다.
  · "선언은 넷, 강제는 홈 전체" — 모델도 선언을 믿고 할 수 있는 일을 포기했다.

  → 문서를 읽고 결론 내지 마라. **찍어보고 결론 내라.**

**⑤ 증상 열셋은 원인 열셋이 아니다.**

  판에 문항이 열셋인데 실제 원인은 둘이었다. 원인으로 묶기 전에 고치지 마라.
  묶으면 하나 고쳐서 넷이 움직인다. 안 묶으면 하나 고치고 둘이 깨진다.

**⑥ 사용자에게 할 말과 모델에게 줄 사실은 다른 칸이다.**

  하루에 세 번 났다. `"창제목으로 짚어 주세요"` · `"그 폴더를 열어 주시면 바로 볼게요"` ·
  `"여럿이면 짧게 보여주고 고르게 한다"` — 마지막 것은 **손 설명서 안에** 있었다.
  모델이 그걸 읽고 사용자에게 되물었다.

  → 모델이 읽는 자리에 "사용자에게 물어라"를 쓰지 마라. **손 설명서도 모델이 읽는 자리다.**

**⑦ 목록으로 짐작하면 반드시 뚫린다.**

  금지 문구 목록·허용 목록·접두 목록 전부 한 번씩 뚫렸다.
  **구조로 판정해라.** 임시 폴더 정리는 접두 목록이 아니라 `TMPDIR` 경계로 풀었다 —
  "무엇을 지울까"를 판단할 필요가 없어지니 틀릴 수도 없어졌다.

  · 라이브로 밟지 않은 것은 모른다고 말해라. 검사가 초록인 것과 제품이 되는 것은 다르다.
  · 틀렸으면 짧게 정정하고 계속해라. 길게 사과하지 마라. 나는 결과가 필요하다.
  · 보고는 한국어로, 결론부터, 숫자는 맨 아래.
  · 내 파일·계정 자격은 네가 만지지 마라. 필요하면 나에게 명령을 줘라.
  · 하나만 물어라. 물을 게 여럿이면 네가 가정하고 진행한 뒤 가정을 밝혀라.

마지막으로 — **네가 지금 T5 를 만들고 있는지, 검사를 통과시키고 있는지
하루에 한 번은 스스로 물어라.** 그 둘은 다르고, 우리는 그걸 여러 번 헷갈렸다.
사용자 문장 하나가 다르게 끝나지 않으면, 검사가 몇 개 늘었든 0점이다.

## 이 문서를 고치는 사람에게

**여기에 진행 상황을 요약하지 마라.** 요약은 낡고, 낡은 요약은 새 세션이 틀린 사실을 확신하게 한다.
숫자·진행·열린 결함은 판·`git log`·장부가 스스로 갱신한다.

**§0(목적)·§1(일하는 법)·§6(오너와 일하는 법)은 예외다.** 이건 상황이 아니라 기준이다.
§1 에 새로 적을 것이 생기면 **실제로 하루를 태운 것만** 적어라. 훈계는 적지 마라.

**§2(지금 T5 는 무엇인가)는 판 숫자를 적는 자리가 아니다.** 사용자가 쓸 수 있는지를 적는 자리다.
그것도 낡지만, 낡으면 새 세션이 바로 알아챈다 — 첫날에 라이브로 밟게 되어 있기 때문이다.
