# YOON Flow-Governed Vibe Engineering

- 지위: 초안
- 작성일: 2026-07-31
- 목적: AI와 함께 소프트웨어, 웹앱, 자동화 도구, AI 제품을 만들 때 사용할 수 있는 공개용 개발 이론
- 한 줄 정의: 윤(YOON)의 사용자 감각과 오너 주도 원칙을 바탕으로, 바이브코딩의 속도와 창의성을 살리되 역할·검증·사용자 흐름·인수인계로 제품 완성까지 끌고 가는 AI-native 개발 방법론

## 1. 왜 이 백서가 필요한가

바이브코딩은 강력하다. 개발자는 자연어로 목표를 말하고, AI는 코드를 읽고, 고치고, 실행하고, 테스트한다. 이전보다 훨씬 빠른 속도로 시제품과 기능을 만들 수 있다.

하지만 실제 제품 개발에서는 반복되는 문제가 생긴다.

- AI가 사용자의 의도보다 구현 가능한 작업에 끌려간다.
- 테스트는 통과하지만 실제 화면과 사용자 흐름은 나빠진다.
- 문서와 계약이 늘어나면서 제품은 앞으로 나아가지 못한다.
- 긴 세션에서 맥락이 흐려지고, 이전 결정을 잘못 기억한다.
- AI가 확실하지 않은 내용을 완료처럼 말한다.
- 안전을 이유로 모든 것을 카드, 승인, 확인으로 막아 사용성을 해친다.
- 반대로 자동화를 서두르다 잘못 배운 내용이 실제 행동에 들어간다.

따라서 AI 개발에는 단순한 프롬프트 요령이나 코딩 속도론을 넘어서는 운영 이론이 필요하다.

**YOON Flow-Governed Vibe Engineering**은 그 공백을 채우기 위한 방법론이다. 핵심은 단순하다.

> AI에게 더 많은 코드를 쓰게 하는 것이 목표가 아니다.  
> 인간의 의도가 제품 안에서 자연스럽고 검증 가능하게 실현되도록, 개발 흐름 전체를 설계하는 것이 목표다.

## 2. 업계 흐름에서 본 위치

이 방법론은 기존 AI 개발 흐름을 대체하기보다, 그 위에 제품 완성 규율을 얹는다.

Andrej Karpathy가 대중화한 vibe coding은 자연어와 AI를 통해 코딩의 진입 장벽을 낮췄다. IBM은 vibe coding을 자연어 지시로 AI가 코드를 생성하고, 사람은 결과·테스트·미세 조정에 집중하는 흐름으로 설명한다.

GitHub Copilot 연구는 AI pair programmer가 특정 과제 완료 시간을 크게 줄일 수 있음을 보였다. 반면 Copilot 품질 연구는 AI 제안이 버그를 만들 수 있고, 특히 초보자가 잘못된 제안을 걸러내지 못하면 위험할 수 있다고 지적한다.

Google DORA 2024는 AI 도입이 개인 생산성, 문서 품질, 코드 품질에는 긍정적일 수 있지만, 소프트웨어 전달 안정성과 처리량을 자동으로 개선하지는 않는다고 본다. 핵심은 여전히 작은 배치, 강한 테스트, 사용자 중심성, 안정된 우선순위다.

SWE-bench와 LiveSWEBench 같은 벤치마크는 실제 소프트웨어 엔지니어링이 단순 코드 생성보다 훨씬 어렵다는 점을 보여준다. 실제 문제는 여러 파일, 긴 맥락, 실행 환경, 테스트, 회귀 위험, 모호한 요구사항을 함께 다룬다.

Claude Code와 Codex의 공식 자료도 비슷한 결론을 향한다. 효과적인 agentic coding에는 풍부한 저장소 맥락, 검증 가능한 환경, 테스트, 세션 관리, AGENTS/CLAUDE 문서, 병렬 작업, 명확한 권한 경계가 필요하다.

이 백서의 기여는 그 다음이다.

> AI 개발 도구를 잘 쓰는 법을 넘어, 인간 오너와 AI 구현자와 AI 감사자가 함께 제품을 완성하는 운영 구조를 제시한다.

## 3. 핵심 명제

### 3.1 말귀가 개발 생산성의 출발점이다

AI 개발에서 가장 중요한 능력은 코드를 많이 쓰는 능력이 아니라 **사용자의 말을 제대로 알아듣는 능력**이다.

좋은 개발 흐름은 다음 질문을 계속 붙든다.

- 사용자가 정말 원하는 결과는 무엇인가?
- 사용자가 싫어하는 마찰은 무엇인가?
- 지금 요청은 기능 추가인가, 오해 수정인가, 사용성 개선인가?
- AI가 문제를 기술적으로 바꾸면서 원래 의도를 잃고 있지 않은가?

말귀가 무너지면 AI는 빠르게 엉뚱한 것을 완성한다.

### 3.2 바이브는 시작점이고, 흐름 통제가 완성 조건이다

바이브코딩의 장점은 속도, 상상력, 진입 장벽의 붕괴다. 하지만 제품 완성에는 다음이 더 필요하다.

- 기준선
- 역할 분리
- 반대시험
- 실제 화면 검증
- 인수인계
- 반복 결함 추적
- 사용자 성과 지표

즉 자유로운 생성과 엄격한 판정을 함께 가져가야 한다.

### 3.3 테스트 초록은 제품 성공이 아니다

테스트는 필수지만 충분하지 않다.

AI 개발에서는 특히 다음 착시가 자주 생긴다.

- 함수는 존재하지만 실제 경로에 연결되지 않았다.
- 테스트 fixture가 제품이 실제로 만들지 않는 값을 지어냈다.
- 검사 이름은 넓지만 실제 검사는 좁다.
- mock에서는 통과하지만 실제 모델·실제 브라우저에서는 깨진다.
- 문서에는 완료라고 쓰였지만 인수인계와 코드 상태가 다르다.

따라서 완료 증거는 최소 네 층으로 나눠야 한다.

1. 코드 계약
2. 반대시험
3. 전체 회귀
4. 실제 사용자 시나리오

### 3.4 최소 안전, 최대 자동화

AI 제품은 사람을 보호해야 한다. 그러나 보호가 사용자를 괴롭히는 방식이면 실패다.

기본 원칙은 다음이다.

- 외부 전송, 공개 게시, 결제, 복구 불가능한 삭제, 새 지속 권한은 승인한다.
- 읽기, 정리, 요약, 초안, 가역 로컬 기억, 되돌릴 수 있는 설정은 최대한 자동화한다.
- 카드와 클릭은 위험이 있을 때만 쓴다.
- 사용자가 이미 명시한 선호를 다시 묻는 카드는 마찰이다.
- 되돌릴 수 있는 일은 먼저 돕고, 사후에 고치거나 철회할 수 있게 한다.

### 3.5 모델을 멍청하게 만들지 않는다

AI 개발에서 흔한 실수는 안전과 계약을 늘리면서 모델의 자연스러운 능력을 억누르는 것이다.

좋은 OS나 harness는 모델을 대신 판단하는 검문소가 아니다. 모델이 더 잘할 수 있게 현실을 공급하는 장치다.

- 정확한 현재 맥락
- 사용 가능한 도구
- 권한 경계
- 이전 작업 산출물
- 실패 사실
- 사용자 선호
- 검증된 원리

이런 현실을 잘 공급하면 모델은 더 자연스럽고 강해진다. 반대로 규칙으로만 압박하면 딱딱하고 방어적인 응답이 늘어난다.

## 4. 역할 구조

YOON Flow-Governed Vibe Engineering은 한 AI가 모든 역할을 맡는 구조를 피한다. 역할을 분리해야 자기 확신과 맥락 오염을 줄일 수 있다.

| 역할 | 책임 | 실패하면 생기는 문제 |
|---|---|---|
| 인간 오너 | 목적, 사용자 감각, 우선순위, 최종 판정 | 기능은 많지만 쓸모 없는 제품 |
| AI 구현자 | 코드 작성, 실행, 테스트, 커밋 | 속도 저하, 연결 부재 |
| AI 감사자 | 결함 계열, 계획 충돌, 사용자 성과 검증 | 거짓 완료, 테스트 착시 |
| 비교군 분석자 | 다른 도구와 제품의 강점·위험 분석 | 독선, 재발견 |
| 인수인계 관리자 | 현재 사실, 기준선, 다음 행동 유지 | 세션 교체 때 붕괴 |
| 실제 사용자 시나리오 | 화면과 흐름에서 최종 판정 | 내부 성공, 외부 실패 |

한 사람이 여러 역할을 겸할 수는 있지만, 한 턴 안에서 구현과 감사를 같은 관성으로 처리하면 위험하다. 특히 AI가 직접 만든 구조를 같은 AI가 감사하면 누락 가능성이 커진다.

## 5. 개발 프로토콜

### 5.1 기준선 확정

먼저 현재 제품이 무엇을 잘하고 무엇을 못하는지 실제로 잰다.

- 현재 동작
- 실패 시나리오
- 사용자 마찰
- 성능
- 권한·안전 경계
- 비교군 관찰

기준선 없이 개발하면 “좋아진 느낌”만 남는다.

### 5.2 세로 슬라이스

큰 시스템을 한꺼번에 만들지 않는다. 하나의 사용자 문장을 기준으로 닫힌 슬라이스를 만든다.

예:

> “앞으로 보고서는 목록으로 정리해줘.”  
> 선언 → 반영 → 다음 턴 적용 → 되돌리기 → 원장 → 회귀 금지

슬라이스는 다음을 모두 포함해야 한다.

- 실제 사용자 발화
- 제품 경로
- 저장 또는 실행 결과
- 사용자 표면
- 실패·복구
- 반대시험
- 라이브 검증

### 5.3 반대시험 우선

AI 구현은 쉽게 “되는 길”만 만든다. 그래서 반드시 “되면 안 되는 길”을 먼저 써야 한다.

- 위조된 receipt가 통과하면 안 된다.
- 관련 없는 기억이 들어오면 안 된다.
- 실패한 replay가 승격되면 안 된다.
- 권한 없는 채널이 같은 오너처럼 보이면 안 된다.
- 테스트 fixture가 제품이 만들지 않는 값을 지어내면 안 된다.

반대시험은 AI 개발의 제동 장치가 아니라 속도를 유지하기 위한 안전 난간이다.

### 5.4 라이브 검증

실제 모델, 실제 브라우저, 실제 파일, 실제 터미널에서 검증해야 한다.

mock과 단위 테스트는 구조를 지키지만, 라이브는 다음을 잡는다.

- 모델이 스키마를 가끔 생략하는 문제
- 응답이 잘리는 문제
- 화면에 카드가 남는 문제
- 사용자가 본 말과 내부 상태가 다른 문제
- fixture가 제품 현실과 어긋난 문제
- 오래 걸리는 작업이 전경을 막는 문제

AI 제품은 실제 사용 환경에서만 드러나는 결함이 많다.

### 5.5 인수인계는 현재 진실이다

AI 개발은 긴 세션에서 맥락이 무너진다. 그래서 인수인계서는 부속 문서가 아니라 개발 시스템의 일부다.

인수인계에는 다음이 있어야 한다.

- 현재 브랜치와 커밋
- 작업 트리 상태
- 완료·진행·차단 상태
- 최신 정본 문서
- 폐기된 설계
- 검증 결과
- 알려진 한계
- 다음 행동
- 건드리면 안 되는 범위

중요 결정이나 작업 종료 때마다 갱신하지 않으면, 다음 AI는 과거의 유령을 현재 사실로 되살린다.

## 6. 감사 원칙

감사는 흠집 찾기 놀이가 아니다. 감사는 제품 목표를 지키는 역할이다.

좋은 감사는 다음 원칙을 따른다.

1. 범위를 먼저 동결한다.
2. 개별 결함이 아니라 결함 계열을 본다.
3. 문제, 재현, 실제 결과, 기대 결과, 영향을 말한다.
4. 해법은 구현자가 구조적으로 설계하게 둔다.
5. 제품 종단을 우선 본다.
6. 차단 결함과 개선 아이디어를 분리한다.
7. 반복 결함은 `REPEAT_PREVENTABLE`로 표시한다.
8. 같은 시나리오가 세 번 열리면 패치가 아니라 회복 절차를 발동한다.

감사의 목표는 개발자를 느리게 하는 것이 아니다. 같은 실수를 다시 열지 않게 해서 전체 속도를 높이는 것이다.

## 7. 비교군을 쓰는 법

비교군은 순위를 매기기 위해 쓰는 것이 아니다. 흡수할 구조와 흡수하지 않을 위험을 찾기 위해 쓴다.

좋은 비교는 다음을 분리한다.

- 제품이 실제로 잘한 것
- 모델 차이 때문에 생긴 것
- 환경 차이 때문에 생긴 것
- 우리 제품에 흡수할 수 있는 구조
- 흡수하면 안 되는 위험

예를 들어 어떤 도구가 자동 기억은 잘하지만 민감정보를 그대로 저장한다면, 우리는 자동 기억의 흐름은 흡수하고 민감정보 admission 경계는 더 강하게 만들어야 한다.

## 8. 비개발자 오너의 역할

비개발자 오너는 약점이 아니다. AI-native 개발에서 오히려 강점이 될 수 있다.

개발자는 구조와 코드에 몰입한다. AI는 구현 가능한 방향으로 흐른다. 이때 오너가 붙잡아야 하는 것은 사용자 감각이다.

- 이게 정말 편한가?
- 이 답이 내 말을 알아들은 건가?
- 이 카드는 필요한가?
- 이 클릭은 지킨 위험이 있는가?
- 이 기능이 실제 내 컴퓨터에서 쓸모가 있는가?
- 이 자동화가 나를 대신해 손발이 되었는가?

AI 시대의 오너십은 코드를 직접 쓰는 능력만이 아니다. 제품이 사람에게 닿는 방식을 끝까지 놓치지 않는 능력이다.

## 9. 적용 체크리스트

새 AI 개발 프로젝트를 시작할 때 다음을 고정한다.

- 사용자의 실제 문장 5~10개
- 현재 기준선
- 완료 조건
- 승인해야 할 위험 경계
- 자동화해야 할 가역 영역
- 구현 AI와 감사 AI의 역할
- 인수인계 문서
- 테스트 명령
- 라이브 검증 방식
- 비교군 또는 참고 도구

각 슬라이스가 끝날 때 다음을 확인한다.

- 사용자 문장이 실제로 좋아졌는가?
- 질문, 카드, 클릭, 대기 시간이 줄었는가?
- 실패해도 정직하게 말하고 복구되는가?
- 테스트가 제품 경로를 증명하는가?
- fixture가 실제 제품 산출물과 같은가?
- 문서와 커밋과 인수인계가 같은 사실을 말하는가?

## 10. T5 사례 연구에서 얻은 교훈

T5 개발은 이 이론의 출발 사례다. 핵심 교훈은 다음과 같다.

- 가역 로컬 기억에 승인 카드를 붙이면 사용자는 괴롭다.
- 기억 철회가 파일 되돌리기로 오인되면 말귀가 무너진다.
- 응답 뒤 관찰은 전경을 막지 않아야 한다.
- 새 대화에서 “아까 그 최종본”을 이어받으려면 모델 기억이 아니라 OS가 사실을 놓아야 한다.
- 반복 학습은 원리 후보를 만들 수 있어도, replay가 과잉 일반화를 막아야 한다.
- 테스트가 통과해도 실제 모델·화면에서만 드러나는 결함이 있다.
- AI 구현자는 빠르게 만든다. AI 감사자는 방향과 사실을 붙잡아야 한다.
- 비개발자 오너의 사용자 감각이 제품 철학을 지키는 최후의 기준이 된다.

T5는 이 백서의 근거 중 하나지만, 이 방법론은 T5에 한정되지 않는다. 웹앱, 업무 자동화, 내부 도구, 개인 AI OS, agentic workflow, AI-native SaaS 모두에 적용할 수 있다.

## 11. 결론

바이브코딩은 개발의 문을 넓혔다. 그러나 문을 통과한 뒤 제품을 완성하려면 다른 능력이 필요하다.

YOON Flow-Governed Vibe Engineering은 그 능력을 다음 문장으로 요약한다.

> 인간은 의도와 사용자 감각을 지키고,  
> AI는 구현과 탐색의 속도를 만들고,  
> 감사는 사실과 방향을 붙잡고,  
> 실제 사용 흐름이 최종 판정을 내린다.

AI 개발의 미래는 “AI가 코드를 얼마나 많이 쓰는가”가 아니라 “인간의 의도가 얼마나 자연스럽고 안전하고 유용하게 제품 안에서 살아나는가”에 달려 있다.
