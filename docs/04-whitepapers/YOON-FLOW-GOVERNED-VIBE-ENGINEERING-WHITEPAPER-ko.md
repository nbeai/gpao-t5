# YOON Flow-Governed Vibe Engineering

- 지위: 초안
- 작성일: 2026-07-31
- 목적: AI와 함께 소프트웨어, 웹앱, 자동화 도구, AI 제품을 만들 때 사용할 수 있는 공개용 개발 이론
- 한 줄 정의: 윤(YOON)의 사용자 감각과 오너 주도 원칙을 바탕으로, 바이브코딩의 속도와 창의성을 살리되 역할·검증·사용자 흐름·인수인계로 제품 완성까지 끌고 가는 AI-native 개발 방법론

## 1. 왜 이 백서가 필요한가

바이브코딩은 강력하다. 개발자는 자연어로 목표를 말하고, AI는 코드를 읽고, 고치고, 실행하고, 테스트한다. 이전보다 훨씬 빠른 속도로 시제품과 기능을 만들 수 있다.

하지만 실제 제품 개발에서는 반복되는 문제가 생긴다.

- AI가 사용자의 의도보다 구현 가능한 작업에 끌려간다.
- 테스트는 통과하지만 실제 화면과 사용자 흐름은 나빠진다.
- 문서와 계약이 늘어나면서 제품은 앞으로 나아가지 못한다.
- 긴 세션에서 맥락이 흐려지고, 이전 결정을 잘못 기억한다.
- AI가 확실하지 않은 내용을 완료처럼 말한다.
- 안전을 이유로 모든 것을 카드, 승인, 확인으로 막아 사용성을 해친다.
- 반대로 자동화를 서두르다 잘못 배운 내용이 실제 행동에 들어간다.

따라서 AI 개발에는 단순한 프롬프트 요령이나 코딩 속도론을 넘어서는 운영 이론이 필요하다.

**YOON Flow-Governed Vibe Engineering**은 그 공백을 채우기 위한 방법론이다. 핵심은 단순하다.

> AI에게 더 많은 코드를 쓰게 하는 것이 목표가 아니다.  
> 인간의 의도가 제품 안에서 자연스럽고 검증 가능하게 실현되도록, 개발 흐름 전체를 설계하는 것이 목표다.

## 2. 업계 흐름에서 본 위치

이 방법론은 기존 AI 개발 흐름을 대체하기보다, 그 위에 제품 완성 규율을 얹는다.

Andrej Karpathy가 대중화한 vibe coding은 자연어와 AI를 통해 코딩의 진입 장벽을 낮췄다. IBM은 vibe coding을 자연어 지시로 AI가 코드를 생성하고, 사람은 결과·테스트·미세 조정에 집중하는 흐름으로 설명한다.

GitHub Copilot 연구는 AI pair programmer가 특정 과제 완료 시간을 크게 줄일 수 있음을 보였다. 반면 Copilot 품질 연구는 AI 제안이 버그를 만들 수 있고, 특히 초보자가 잘못된 제안을 걸러내지 못하면 위험할 수 있다고 지적한다.

Google DORA 2024는 AI 도입이 개인 생산성, 문서 품질, 코드 품질에는 긍정적일 수 있지만, 소프트웨어 전달 안정성과 처리량을 자동으로 개선하지는 않는다고 본다. 핵심은 여전히 작은 배치, 강한 테스트, 사용자 중심성, 안정된 우선순위다.

SWE-bench와 LiveSWEBench 같은 벤치마크는 실제 소프트웨어 엔지니어링이 단순 코드 생성보다 훨씬 어렵다는 점을 보여준다. 실제 문제는 여러 파일, 긴 맥락, 실행 환경, 테스트, 회귀 위험, 모호한 요구사항을 함께 다룬다.

Claude Code와 Codex의 공식 자료도 비슷한 결론을 향한다. 효과적인 agentic coding에는 풍부한 저장소 맥락, 검증 가능한 환경, 테스트, 세션 관리, AGENTS/CLAUDE 문서, 병렬 작업, 명확한 권한 경계가 필요하다.

이 백서의 기여는 그 다음이다.

> AI 개발 도구를 잘 쓰는 법을 넘어, 인간 오너와 AI 구현자와 AI 감사자가 함께 제품을 완성하는 운영 구조를 제시한다.

## 3. 핵심 개념과 원칙

### 3.1 핵심 개념

| 용어 | 정의 |
|---|---|
| Flow Governance | 사용자의 의도가 요구사항, 구현, 검증, 사용자 표면, 인수인계로 이동하는 동안 왜곡되지 않도록 증거와 책임을 연결하는 운영 구조 |
| Intent Fidelity | 사용자의 실제 목적, 불편, 맥락이 구현 과정과 제품 결과 안에서 보존되는 정도. 이 백서의 구어적 표현으로는 "말귀"다 |
| Flow Loop | AI가 한 작업 단위를 처리할 때 따르는 Frame → Locate → Baseline → Counter-Test → Implement → Verify → Audit → Handoff 순환 |
| Counter-Test | 원하는 동작이 아니라 금지해야 할 경로, 재발 위험, 위조 가능성, 과잉 일반화를 먼저 실패로 만드는 테스트 |
| Flow Friction | 사용자가 목표를 달성하기 위해 겪는 불필요한 질문, 카드, 클릭, 대기, 재설명, 복구 비용 |
| Direction Audit | 일반 코드 리뷰와 달리 구현이 사용자 목표, 안전 경계, 증거, 실제 흐름을 함께 만족하는지 판단하는 감사 |

### 3.2 YOON Flow의 5대 원칙

1. **Intent First**  
   사용자의 의도가 코드와 내부 구조보다 우선한다.

2. **Flow over Features**  
   기능 수보다 사용자 흐름의 개선을 더 중요한 성과로 본다.

3. **Negative First**  
   반대시험을 먼저 만들어 잘못된 성공을 막는다.

4. **Reality over Mocks**  
   mock과 단위 테스트보다 실제 모델, 브라우저, 파일, 터미널, 사용자 흐름을 최종 판정에 더 가깝게 둔다.

5. **Shared Truth**  
   코드, 테스트, 문서, 커밋, 인수인계가 같은 현재 사실을 말해야 한다.

## 4. 핵심 명제

### 4.1 말귀가 개발 생산성의 출발점이다

AI-native 개발에서는 사용자의 의도를 정확히 해석하는 능력이 코드 생성 능력보다 전체 생산성에 더 큰 영향을 미친다. 이 백서에서 **말귀(Intent Fidelity)**란 사용자의 원래 목적과 불편, 맥락이 구현·검증·표면화 과정에서 왜곡되지 않는 정도를 뜻한다.

좋은 개발 흐름은 다음 질문을 계속 붙든다.

- 사용자가 정말 원하는 결과는 무엇인가?
- 사용자가 싫어하는 마찰은 무엇인가?
- 지금 요청은 기능 추가인가, 오해 수정인가, 사용성 개선인가?
- AI가 문제를 기술적으로 바꾸면서 원래 의도를 잃고 있지 않은가?

말귀가 무너지면 AI는 빠르게 엉뚱한 것을 완성한다.

### 4.2 바이브는 시작점이고, 흐름 통제가 완성 조건이다

바이브코딩의 장점은 속도, 상상력, 진입 장벽의 붕괴다. 하지만 제품 완성에는 다음이 더 필요하다.

- 기준선
- 역할 분리
- 반대시험
- 실제 화면 검증
- 인수인계
- 반복 결함 추적
- 사용자 성과 지표

즉 자유로운 생성과 엄격한 판정을 함께 가져가야 한다.

### 4.3 테스트 초록은 제품 성공이 아니다

테스트는 필수지만 충분하지 않다.

AI 개발에서는 특히 다음 착시가 자주 생긴다.

- 함수는 존재하지만 실제 경로에 연결되지 않았다.
- 테스트 fixture가 제품이 실제로 만들지 않는 값을 지어냈다.
- 검사 이름은 넓지만 실제 검사는 좁다.
- mock에서는 통과하지만 실제 모델·실제 브라우저에서는 깨진다.
- 문서에는 완료라고 쓰였지만 인수인계와 코드 상태가 다르다.

따라서 완료 증거는 최소 네 층으로 나눠야 한다.

1. 코드 계약
2. 반대시험
3. 전체 회귀
4. 실제 사용자 시나리오

### 4.4 최소 안전, 최대 자동화

AI 제품은 사람을 보호해야 한다. 그러나 보호가 사용자를 괴롭히는 방식이면 실패다.

기본 원칙은 다음이다.

- 외부 전송, 공개 게시, 결제, 복구 불가능한 삭제, 새 지속 권한은 승인한다.
- 읽기, 정리, 요약, 초안, 가역 로컬 기억, 되돌릴 수 있는 설정은 최대한 자동화한다.
- 카드와 클릭은 위험이 있을 때만 쓴다.
- 사용자가 이미 명시한 선호를 다시 묻는 카드는 마찰이다.
- 되돌릴 수 있는 일은 먼저 돕고, 사후에 고치거나 철회할 수 있게 한다.

### 4.5 모델을 멍청하게 만들지 않는다

AI 개발에서 흔한 실수는 안전과 계약을 늘리면서 모델의 자연스러운 능력을 억누르는 것이다.

좋은 OS나 harness는 모델을 대신 판단하는 검문소가 아니다. 모델이 더 잘할 수 있게 현실을 공급하는 장치다.

- 정확한 현재 맥락
- 사용 가능한 도구
- 권한 경계
- 이전 작업 산출물
- 실패 사실
- 사용자 선호
- 검증된 원리

이런 현실을 잘 공급하면 모델은 더 자연스럽고 강해진다. 반대로 규칙으로만 압박하면 딱딱하고 방어적인 응답이 늘어난다.

## 5. 역할 구조

YOON Flow-Governed Vibe Engineering은 한 AI가 모든 역할을 맡는 구조를 피한다. 역할을 분리해야 자기 확신과 맥락 오염을 줄일 수 있다.

| 역할 | 책임 | 실패하면 생기는 문제 |
|---|---|---|
| 인간 오너 | 목적, 사용자 감각, 우선순위, 최종 판정 | 기능은 많지만 쓸모 없는 제품 |
| AI 구현자 | 코드 작성, 실행, 테스트, 커밋 | 속도 저하, 연결 부재 |
| AI 감사자 | 결함 계열, 계획 충돌, 사용자 성과 검증 | 거짓 완료, 테스트 착시 |
| 비교군 분석자 | 다른 도구와 제품의 강점·위험 분석 | 독선, 재발견 |
| 인수인계 관리자 | 현재 사실, 기준선, 다음 행동 유지 | 세션 교체 때 붕괴 |
| 실제 사용자 시나리오 | 화면과 흐름에서 최종 판정 | 내부 성공, 외부 실패 |

한 사람이 여러 역할을 겸할 수는 있지만, 한 턴 안에서 구현과 감사를 같은 관성으로 처리하면 위험하다. 특히 AI가 직접 만든 구조를 같은 AI가 감사하면 누락 가능성이 커진다.

## 6. 개발 프로토콜

이 방법론의 기본 실행 단위는 **8단계 Flow Loop**다. 루프는 얇아야 한다. 다음 구현을 돕지 않거나 실제 반복 실패를 막지 않는 문서와 게이트는 만들지 않는다.

8단계인 이유는 AI 개발에서 자주 끊기는 책임 경계를 모두 닫기 위해서다. Frame은 의도를 고정하고, Locate는 기존 현실을 읽으며, Baseline은 현재 실패를 재현한다. Counter-Test는 잘못된 성공을 막고, Implement는 실제 제품 경로를 바꾼다. Verify는 동작 증거를 모으고, Audit는 그 증거가 제품 목표를 만족하는지 판단한다. Handoff는 다음 루프가 같은 사실에서 시작하게 한다. 하나라도 빠지면 AI는 빠르지만 쉽게 방향을 잃는다.

```text
Frame
  ↓
Locate
  ↓
Baseline
  ↓
Counter-Test
  ↓
Implement
  ↓
Verify
  ↓
Audit
  ↓
Handoff
  ↓
next Frame
```

| 단계 | 이름 | 질문 |
|---|---|---|
| 1 | Frame | 지금 사용자가 얻어야 하는 실제 결과는 무엇인가? |
| 2 | Locate | 기존 코드·문서·테스트·인수인계는 무엇을 말하는가? |
| 3 | Baseline | 현재 제품은 같은 사용자 문장에서 어떻게 실패하거나 성공하는가? |
| 4 | Counter-Test | 되면 안 되는 길과 재발 위험을 먼저 붉게 만들었는가? |
| 5 | Implement | 실제 제품 경로를 가장 작게 고쳤는가? |
| 6 | Verify | 구현이 동작한다는 증거를 모았는가? |
| 7 | Audit | 구현이 제품 목표와 사용자 흐름을 만족한다고 판단할 수 있는가? |
| 8 | Handoff | 다음 세션이 같은 사실에서 바로 이어갈 수 있는가? |

이 루프의 목적은 AI를 절차로 묶는 것이 아니다. 오히려 AI가 빠르게 움직이되, 방향 상실·테스트 착시·문서놀이·맥락 붕괴를 반복하지 않게 하는 최소 흐름이다.

Verify와 Audit는 다르다. Verify는 **구현이 동작하는지 증명**한다. Audit는 **그 동작이 사용자 목표, 안전 경계, 증거 정직성, 실제 흐름을 만족하는지 판단**한다.

### 6.1 기준선 확정

먼저 현재 제품이 무엇을 잘하고 무엇을 못하는지 실제로 잰다.

- 현재 동작
- 실패 시나리오
- 사용자 마찰
- 성능
- 권한·안전 경계
- 비교군 관찰

기준선 없이 개발하면 “좋아진 느낌”만 남는다.

### 6.2 세로 슬라이스

큰 시스템을 한꺼번에 만들지 않는다. 하나의 사용자 문장을 기준으로 닫힌 슬라이스를 만든다.

예:

> “앞으로 보고서는 목록으로 정리해줘.”  
> 선언 → 반영 → 다음 턴 적용 → 되돌리기 → 원장 → 회귀 금지

슬라이스는 다음을 모두 포함해야 한다.

- 실제 사용자 발화
- 제품 경로
- 저장 또는 실행 결과
- 사용자 표면
- 실패·복구
- 반대시험
- 라이브 검증

### 6.3 반대시험 우선

AI 구현은 쉽게 “되는 길”만 만든다. 그래서 반드시 “되면 안 되는 길”을 먼저 써야 한다.

- 위조된 receipt가 통과하면 안 된다.
- 관련 없는 기억이 들어오면 안 된다.
- 실패한 replay가 승격되면 안 된다.
- 권한 없는 채널이 같은 오너처럼 보이면 안 된다.
- 테스트 fixture가 제품이 만들지 않는 값을 지어내면 안 된다.

반대시험은 AI 개발의 제동 장치가 아니라 속도를 유지하기 위한 안전 난간이다.

### 6.4 라이브 검증

실제 모델, 실제 브라우저, 실제 파일, 실제 터미널에서 검증해야 한다.

mock과 단위 테스트는 구조를 지키지만, 라이브는 다음을 잡는다.

- 모델이 스키마를 가끔 생략하는 문제
- 응답이 잘리는 문제
- 화면에 카드가 남는 문제
- 사용자가 본 말과 내부 상태가 다른 문제
- fixture가 제품 현실과 어긋난 문제
- 오래 걸리는 작업이 전경을 막는 문제

AI 제품은 실제 사용 환경에서만 드러나는 결함이 많다.

### 6.5 인수인계는 현재 진실이다

AI 개발은 긴 세션에서 맥락이 무너진다. 그래서 인수인계서는 부속 문서가 아니라 개발 시스템의 일부다.

인수인계에는 다음이 있어야 한다.

- 현재 브랜치와 커밋
- 작업 트리 상태
- 완료·진행·차단 상태
- 최신 정본 문서
- 폐기된 설계
- 검증 결과
- 알려진 한계
- 다음 행동
- 건드리면 안 되는 범위

중요 결정이나 작업 종료 때마다 갱신하지 않으면, 다음 AI는 과거의 유령을 현재 사실로 되살린다.

## 7. 감사 원칙

감사는 흠집 찾기 놀이가 아니다. 감사는 제품 목표를 지키는 역할이다.

좋은 감사는 다음 원칙을 따른다.

1. 범위를 먼저 동결한다.
2. 개별 결함이 아니라 결함 계열을 본다.
3. 문제, 재현, 실제 결과, 기대 결과, 영향을 말한다.
4. 해법은 구현자가 구조적으로 설계하게 둔다.
5. 제품 종단을 우선 본다.
6. 차단 결함과 개선 아이디어를 분리한다.
7. 반복 결함은 `REPEAT_PREVENTABLE`로 표시한다.
8. 같은 시나리오가 세 번 열리면 패치가 아니라 회복 절차를 발동한다.

감사의 목표는 개발자를 느리게 하는 것이 아니다. 같은 실수를 다시 열지 않게 해서 전체 속도를 높이는 것이다.

## 8. 비교군을 쓰는 법

비교군은 순위를 매기기 위해 쓰는 것이 아니다. 흡수할 구조와 흡수하지 않을 위험을 찾기 위해 쓴다.

좋은 비교는 다음을 분리한다.

- 제품이 실제로 잘한 것
- 모델 차이 때문에 생긴 것
- 환경 차이 때문에 생긴 것
- 우리 제품에 흡수할 수 있는 구조
- 흡수하면 안 되는 위험

예를 들어 어떤 도구가 자동 기억은 잘하지만 민감정보를 그대로 저장한다면, 우리는 자동 기억의 흐름은 흡수하고 민감정보 admission 경계는 더 강하게 만들어야 한다.

## 9. 지표와 성숙도

YOON Flow는 느낌만으로 "좋아졌다"고 말하지 않는다. 최소한 다음 지표를 본다.

| 지표 | 의미 |
|---|---|
| User Outcome Rate | 실제 사용자 문장이 목표 결과에 도달한 비율 |
| Flow Friction | 불필요한 질문, 카드, 클릭, 대기, 재설명 수 |
| First-Pass Success | 첫 시도에서 목표를 달성한 비율 |
| Recovery Honesty | 실패 후 사실을 숨기지 않고 복구 경로를 제공한 비율 |
| Test-Live Gap | 테스트 통과와 실제 환경 결과가 어긋난 비율 |
| Repeat Preventable Defect Rate | 이미 배운 유형의 결함이 재발한 비율 |
| Handoff Rework Rate | 세션 교체 뒤 인수인계 부정확성 때문에 다시 한 작업의 비율 |

초기 개인 프로젝트는 모든 값을 수치화하지 않아도 된다. 다만 질문, 카드, 클릭, 대기, 재작업, 재발 결함은 작업 기록에 남겨야 한다.

## 10. 기존 방법론과의 관계

| 방법론 | 중심 단위 | 주된 판정 | YOON Flow와의 차이 |
|---|---|---|---|
| Agile | 반복 개발 | 팀·고객 피드백 | AI의 맥락 변질, 거짓 완료, 세션 인수인계를 직접 다루지 않는다 |
| Lean UX | 가설과 사용자 학습 | 빠른 실험 | AI 구현자·감사자 역할 분리와 코드 증거 계층은 약하다 |
| TDD | 코드 행동 | 자동화 테스트 | 실제 모델·브라우저·사용자 흐름과 테스트-live gap을 충분히 다루지 않는다 |
| BDD | 행동 시나리오 | 명세화된 동작 | AI의 fixture 착시, 장기 세션 맥락, 인수인계 진실을 별도 운영하지 않는다 |
| DevOps/DORA | 전달 시스템 | 배포·안정성·흐름 | 사용자 발화와 AI 역할 구조를 개발 단위로 삼지 않는다 |
| Vibe Coding | 자연어 생성 | 빠른 결과 | 검증·감사·인수인계·사용자 흐름 통제가 약하다 |
| YOON Flow | 사용자 의도의 제품화 | 사용자 흐름과 다층 증거 | 생성 속도와 제품 통제를 한 루프로 통합한다 |

## 11. 비개발자 오너의 역할

비개발자 오너는 약점이 아니다. AI-native 개발에서 오히려 강점이 될 수 있다.

개발자는 구조와 코드에 몰입한다. AI는 구현 가능한 방향으로 흐른다. 이때 오너가 붙잡아야 하는 것은 사용자 감각이다.

- 이게 정말 편한가?
- 이 답이 내 말을 알아들은 건가?
- 이 카드는 필요한가?
- 이 클릭은 지킨 위험이 있는가?
- 이 기능이 실제 내 컴퓨터에서 쓸모가 있는가?
- 이 자동화가 나를 대신해 손발이 되었는가?

AI 시대의 오너십은 코드를 직접 쓰는 능력만이 아니다. 제품이 사람에게 닿는 방식을 끝까지 놓치지 않는 능력이다.

## 12. 적용 체크리스트

새 AI 개발 프로젝트를 시작할 때 다음을 고정한다.

- 사용자의 실제 문장 5~10개
- 현재 기준선
- 완료 조건
- 승인해야 할 위험 경계
- 자동화해야 할 가역 영역
- 구현 AI와 감사 AI의 역할
- 인수인계 문서
- 테스트 명령
- 라이브 검증 방식
- 비교군 또는 참고 도구

각 슬라이스가 끝날 때 다음을 확인한다.

- 사용자 문장이 실제로 좋아졌는가?
- 질문, 카드, 클릭, 대기 시간이 줄었는가?
- 실패해도 정직하게 말하고 복구되는가?
- 테스트가 제품 경로를 증명하는가?
- fixture가 실제 제품 산출물과 같은가?
- 문서와 커밋과 인수인계가 같은 사실을 말하는가?

작업을 AI에게 맡길 때는 다음 실행 루프를 그대로 붙여도 된다.

```text
Frame: 목표와 실제 사용자 문장을 다시 말하라.
Locate: 관련 코드, 문서, 테스트, 최근 인수인계를 읽어라.
Baseline: 현재 동작을 재현하거나 재현 불가 이유를 밝혀라.
Counter-Test: 수정 전 실패하는 반대시험을 먼저 만들어라.
Implement: 실제 제품 경로를 가장 작게 고쳐라.
Verify: 표적 검사, 필요한 회귀, 실제 환경 검증을 구분해 수행하라.
Audit: 검사가 주장보다 좁지 않은지, 사용자 마찰이 줄었는지 확인하라.
Handoff: 커밋, 검증, 한계, 다음 행동을 기록하라.
```

## 13. 익명 현장 사례에서 얻은 교훈

이 방법론은 장기 AI 제품 개발에서 반복 관찰된 실패와 수정을 바탕으로 정리됐다. 공개판에서는 특정 제품명이나 내부 구조를 드러내지 않고, 재사용 가능한 패턴만 남긴다.

| 익명 사례 | 기존 실패 | 방법론이 요구하는 수정 |
|---|---|---|
| 가역 로컬 선호 저장 | 사용자가 이미 "앞으로 이렇게 해줘"라고 말했는데도 확인 카드와 클릭을 요구했다 | 위험이 없는 가역 기억은 자동 반영하고, 되돌리기와 원장으로 보호한다 |
| 기억 철회 | "방금 기억한 선호는 취소해줘"가 다른 도구의 되돌리기 요청으로 오인됐다 | 말귀(Intent Fidelity)를 기준으로 intent taxonomy를 보강하고, 철회는 한 턴에 상태·표면·기록이 일치해야 한다 |
| 응답 뒤 관찰 | 학습·관찰이 전경 응답을 붙잡거나 사용자 턴을 느리게 만들 위험이 있었다 | 백그라운드 워커는 전경 큐를 잡지 않고, 모델 호출과 저장 전이를 분리한다 |
| 새 대화 승계 | "아까 그 최종본 이어서" 같은 요청에서 이전 산출물을 찾지 못했다 | 모델이 추측하게 두지 말고, OS가 검증된 산출물 사실을 다음 대화에 공급한다 |
| 반복 학습 | 반복된 사용 패턴을 원리로 만들 수는 있었지만 과잉 일반화 위험이 있었다 | 원리 후보는 replay와 negative/boundary 사례를 통과하기 전에는 행동에 들어가지 않는다 |
| 테스트 착시 | 검사 fixture가 실제 제품이 만들지 않는 값을 지어내 통과했다 | 테스트는 실제 제품 산출물과 같은 형태를 써야 하고, 라이브 검증으로 mock과 현실의 차이를 잡는다 |

이 사례들은 특정 제품을 홍보하기 위한 것이 아니다. 웹앱, 업무 자동화, 내부 도구, 개인 AI OS, agentic workflow, AI-native SaaS 모두에서 반복될 수 있는 패턴이다.

## 14. 적용 범위와 한계

이 방법론은 특정 모델, IDE, 회사, 프레임워크에 의존하지 않는다. LLM이 코드를 생성하거나 파일·터미널·브라우저·테스트 환경을 다루는 곳이라면 Claude Code, Codex, Gemini CLI, Cursor, Copilot, 사내 agentic harness 등 어떤 도구에서도 적용할 수 있다.

한계도 있다.

- 작은 일회성 스크립트에는 전체 역할 분리가 과할 수 있다.
- 감사 AI가 구현 AI와 다른 모델이라고 해서 독립성이 자동 보장되지는 않는다.
- live 검증은 비용과 시간이 들며, 민감한 환경에서는 별도 격리가 필요하다.
- Flow Loop는 제품 완성의 운영 구조이지, 좋은 제품 감각 자체를 자동으로 만들어주지는 않는다.

그래서 이 방법론은 절차가 아니라 판단을 돕는 흐름이어야 한다. 상황이 작으면 줄이고, 위험이 크면 강화한다.

## 15. 결론

바이브코딩은 개발의 문을 넓혔다. 그러나 문을 통과한 뒤 제품을 완성하려면 다른 능력이 필요하다.

YOON Flow-Governed Vibe Engineering은 그 능력을 다음 문장으로 요약한다.

> 인간은 의도와 사용자 감각을 지키고,  
> AI는 구현과 탐색의 속도를 만들고,  
> 감사는 사실과 방향을 붙잡고,  
> 실제 사용 흐름이 최종 판정을 내린다.

AI 개발의 미래는 “AI가 코드를 얼마나 많이 쓰는가”가 아니라 “인간의 의도가 얼마나 자연스럽고 안전하고 유용하게 제품 안에서 살아나는가”에 달려 있다.
