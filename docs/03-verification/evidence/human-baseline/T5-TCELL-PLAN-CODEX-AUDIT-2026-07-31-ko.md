# 새 T-cell 개발계획 Codex 독립 감사

- 대상: `design/T5-TCELL-DEVELOPMENT-PLAN-2026-07-31-ko.md` (`0db4005`)
- 판정: **BLOCKED_BEFORE_OWNER_APPROVAL**
- 제품 코드 변경: 0
- 감사 방식: 계획 문구를 현재 코어의 생산자·저장·응답 경계·소비자·사용자 표면과 역추적

## 1. REPEAT_PREVENTABLE

이번 초안에는 이미 이전 TG/CX 흐름에서 확인하고 문서화한 실패 구조가 세 종류 재발했다.

### RP-1 · P0 — `응답 뒤`라고 지정한 접점이 실제로는 응답 전 직렬 구간이다

- 계획 `§2:52`, `§5:112`는 `server.js:370-382`를 응답 뒤 관찰 훅으로 지정한다.
- 실제로 일반 턴은 `server.js:563-569`에서 `runAndPersistTurn()` 전체를 기다린 뒤 응답한다.
- 스트림도 `server.js:621-654`에서 같은 함수를 기다린 뒤 `complete`를 보낸다.
- 후보 저장 `server.js:370-381`과 세션 저장 `:392`는 두 경로 모두 사용자 완료 전이다.

따라서 계획대로 구현하면 S2의 관찰 쓰기가 전경 I/O가 되고, 계획이 동시에 선언한
`전경 durable I/O 추가 0`과 충돌한다. 과거 TG-5에서 "호출은 이었지만 실제 생산 경계가
아니었다"가 반복된 것과 같은 유형이다.

### RP-2 · P0 — 명시 발화의 신분 없이 자동 승격을 연다

- 계획 `§5:101-103`은 "발화 자체가 확인"이라며 자동 승격을 연다.
- 현재 후보는 정규식 `detectCandidate` 또는 모델 `memory.propose` 양쪽에서 오고
  (`turn.js:346-401`), 제안 계약은 `kind·statement`만 보존한다
  (`model-control.js:15-29, 52-63`).
- 사용자 선언, 질문, 인용, 부정, 철회, 모델 제안을 구분하거나 후보 근거에 결합하는 필드가 없다.

이 상태에서는 질문·인용·부정문을 모델 또는 정규식이 후보로 돌려준 경우도 "사용자 발화"라는
이유로 durable 기억이 될 수 있다. 이전 CX-01에서 문자열 일치와 출처만으로 명시성을 대신했던
동일 실패 구조다.

### RP-3 · P0 — 계약의 모양은 있으나 자동 성장의 닫힌 생산 상태기계가 없다

- 계획 `§4:92-94`, `§5:128-135`는 모델 replay와 `principle` 입장을 선언한다.
- 현재 승격 단일 통로는 운영 원리에 `userConfirmed===true`와 `replayPassed===true`를 함께
  요구한다(`context-mesh.js:33-43, 118-157`).
- 초안에는 관찰 묶음이 어느 저장 근거를 조회해 ReplayCase가 되는지, 실행 증거가 어떻게 생기는지,
  모델 verdict를 어떤 OS 사실로 검증하는지, 어떤 단일 전이가 M1을 영향 가능한 상태로 바꾸는지,
  실패·중단 뒤 어디서 재개하는지가 없다.
- 세션별 큐, persistent checkpoint, 멱등 키, 부팅 재개, 과부하·기아·재시도 계약도 없다.

따라서 S4는 "백그라운드 모델이 통과라고 답했다"와 실제 승격 사이가 비어 있다. 이전 TG-4의
호출자 주장 패킷, TG-3의 생산 미배선, CX-02의 묶음 checkpoint 유실을 다시 만들 수 있는 상태다.

### RP-4 · P1 — 방금 교정한 정본 투영 누락이 즉시 재발했다

- 인수인계 `§0-A:85-94`에는 초안 작성이 기록돼 있다.
- 그러나 같은 문서 `§4:337`은 여전히 "새 T-cell 개발 계획 미작성"이라고 쓰고,
  `§9:421-428`은 이미 종료된 비교 준비부터 다시 실행하라고 하며,
  `§10`의 시작 여섯 줄도 비교 준비가 현재 차단이라고 기록한다.

직전 최종 감사에서 `runs:1`만 고치고 나머지 투영을 놓친 같은 유형을 Codex가 직접 정정했는데,
다음 문서 변경에서 바로 재발했다. 새 세션이 옛 비교 작업으로 돌아갈 수 있는 실행 왜곡이다.

## 2. 신규 차단 결함

### P0-1 — S5가 어느 기억·원리가 실제로 적용됐는지 식별할 수 없다

계획 `§5:139-143`은 적용 효과를 감사해 감쇠·격리한다고 한다. 그러나 현재 입장 함수는 항목을
문자열로 축소하고(`context-mesh.js:71-75`), 모델 입력도 문자열만 싣는다
(`model-provider.js:113-115`). 응답·영수증에는 적용된 `candidateId`나 provenance가 없다.
이 상태에서는 사용자 정정이 어느 원리의 효과였는지 추적할 수 없어 무관한 기억을 약화시키거나,
아무것도 약화시키지 못한다.

### P0-2 — 저장소 정합성의 전제가 현재 코드와 반대다

계획 `§4:95`는 "기존 memory-store 관례"에 따라 migration과 손상 격리를 한다고 적었다.
실제 `MemoryStore.load()`는 ENOENT뿐 아니라 권한 오류·I/O 오류·JSON 손상을 전부 빈 상태로
위장한다(`memory-store.js:30-36`). 저장도 `observed`만 직렬화한다(`:39-47`).

초안의 `observations`, tier, provenance, decay, lane을 이 경계에 얹으면 읽기 실패 뒤 빈 상태를
정상으로 보고 저장해 기존 기억을 덮을 수 있다. 또한 기존 `observed`와 신규 `observations`의
소유권·이관 관계가 정의되지 않아 두 개의 관찰 정본이 생긴다.

### P0-3 — 백그라운드 모델의 신뢰·비밀 경계가 없다

계획은 `발화 digest 참조`를 저장한다고 하면서(`§4:77-80`) 동시에 "원문·반례 보존" 묶음과
백그라운드 모델 판정을 요구한다(`§5:112, 130`). 성장 모델이 사용자 응답 모델과 같은 자격인지,
다른 provider일 때 어떤 정보만 전달하는지, 비밀·일반 원문의 휘발성 경계와 저장 금지가 정의돼
있지 않다. H07 저장 경계만으로는 외부 모델 송신 경계를 증명하지 못한다.

### P1-1 — ActiveWorkLane의 사실·범위·선택 계약이 H05 목표를 지탱하지 못한다

계획 `§4:81-84`의 원천은 receipt와 `activeGoal`뿐이다. 현재 `workingState`는 세션 내부의
receipt 파생 뷰이고, 완료·최근성·대상 감쇠를 그 세션 턴 수로 계산한다. 초안에는 사용자·workspace·
project scope 신분, lane TTL·상한·완료·archive, 다중 후보 중 실제 선택된 lane의 trace,
원본 artifact와 "최종본"의 연결 신분이 없다. 새 대화에서 lane을 나열하는 것만으로는 H05의
정확한 이어받기와 다른 프로젝트 미노출을 동시에 증명할 수 없다.

### P1-2 — "접점 다섯 곳 밖 수정 금지"가 필요한 생산 경로와 충돌한다

계획 `§2:42-56`은 다섯 접점 밖의 코어 수정을 금지한다. 그러나 계획 자체가 요구하는 저장
migration, 웹 사후 표면, 모델 입력의 lane·provenance, scheduler/queue 수명주기, 부팅 재개,
검사와 사용자 투영은 `memory-store.js`, `model-provider.js`, `web/index.html`, 서버 부팅부 등
추가 소유면을 필연적으로 지난다. 현재 경계는 코어 보호가 아니라 필요한 배선을 누락시키거나
예외를 반복 생성할 가능성이 높다.

### P1-3 — 비교에서 배운 자동성 안전망과 사용자 통제 표면이 계획에 닫히지 않았다

Hermes에서 확인한 archive-only, pinned 우회, "미사용은 노후 증거가 아님", bounded human-readable
memory의 원리가 초안의 `decay` 한 필드로 축약됐다. registry·observations·lane의 상한 수치,
grace floor, pin, archive/restore, 사용자가 배운 원리와 lane을 보고 고치고 지우는 통합 표면이
완료 조건에 없다. 자동 감쇠만 있으면 자동성의 안전망보다 조용한 소실이 먼저 생길 수 있다.

## 3. 완료 기준의 모순·불안정

- `전경 시간 증가 0`은 계측 잡음 때문에 수치 완료 조건으로 판별할 수 없다. 문서에는 구조 불변식
  (추가 awaited 모델/I/O 없음)과 실제 지연 판정이 섞여 있다(`§1:36`, `§3:67-68`).
- S2는 감사의 "명시 승인"을 착수 조건으로 둔다(`§5:114-115`). 독립 감사가 착수 허가제가 아니라는
  협업 계약과 충돌한다.
- 필수 결과 3의 POM은 대응표에 이름만 있고(`§6:154`), POM의 데이터·생산자·소비자·사용자 효과가
  어느 슬라이스에도 정의되지 않았다.
- T-cell 이후 계획 `§7:163-167`은 순서만 있고, T-cell이 Skill·Trigger·Agent에 어떤 성장 신호와
  입장 결과를 제공하는지 연결 계약이 없다. 오너가 요구한 "이후 개발이 누락되지 않게 안배"하기에는
  부족하다.

## 4. 보존되는 장점

- H01·H04·H02·H05를 사용자 문장과 카드·클릭·재질문 수치로 정의한 방향은 유효하다.
- 가역 로컬 학습은 자동, 치명적 외부 영향과 새 지속 권한만 좁게 승인한다는 원칙은 오너 철학과 맞다.
- 현재 지시 우선, H07 민감정보 회귀 금지, H08·H09·H10의 원인 분리는 유지할 가치가 있다.
- 현재 커밋은 문서만 바꿨고 제품 T-cell 코드는 유입되지 않았다.

## 5. 판정

이 초안은 **철학·성과 방향은 채택 가능하지만 구현 계약으로는 승인 불가**다. 특히 S1의 명시성,
S2의 실제 응답 후 경계, S4의 저장 근거 기반 자동 성장 상태기계, S5의 적용 trace가 닫히지 않으면
과거 TG/CX의 반복을 구조적으로 피할 수 없다.

다음 제출은 개별 문구 패치가 아니라 위 차단을 한 번에 반영한 계획 전체본이어야 한다. Codex는
세부 구현 해법을 지정하지 않으며, Claude 구현선이 생산자→저장→백그라운드 처리→게시→전경 소비→
효과 감사→사용자 교정·복구의 전 수명주기를 다시 설계한다. 오너 확인과 제품 구현은 그 다음이다.
