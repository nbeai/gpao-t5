# S2 증거 — 응답 뒤 관찰 shadow

- 날짜: 2026-07-31 (Asia/Seoul) · 실행: 구현선 Claude
- 슬라이스 성격: **사용자 체감 기능을 늘리지 않는다.** 관찰은 이미 저장된 durable 산출물의
  소비자이며 기존 tick 위에서 돈다. 범위는 observation·bundle 까지다 —
  candidate·replay·admitted·기억 영향·성장 모델 호출은 S2 범위 밖이며 구현하지 않았다.

## 1. 구조 증명 — "응답 뒤"는 코드 위치가 아니라 불변식

턴 경로에 관찰 코드가 **한 줄도 없다**(기계 확인):

| 검사 대상 | `observeSessions` 호출 | 관찰 워커 호출 |
|---|---|---|
| `runAndPersistTurn` (웹·SSE 턴 전체) | 0 | 0 |
| `runChannelInboundTurn` (채널 턴 전체) | 0 | 0 |

관찰이 불리는 자리는 `server.js:238` 하나뿐이고, 그것은 `runTrustedTick` 안이다.

| 턴 3회 직후 | **0** | **0** | 0 |

  "턴 직후 관찰 0"** 이다.

## 4-A. 감사 P1 — 같은 tick 안의 상호 격리 (2026-07-31 보강)

첫 제출의 실패 격리 검사는 자동화 실패 **뒤에 `observeSessions` 를 따로 호출**해 통과했다.
그것은 "관찰 함수가 따로 돌 수 있다"는 증명이지 **"같은 tick 안에서 서로의 실행 기회를 뺏지
않는다"** 가 아니다. 실제 배선도 자동화 load/tick/save 가 먼저 예외를 던지면 관찰워커까지
도달하지 못했다(계획 §4.8 미충족).

- 검사 교체: 한 번의 `runtimeTick()` 안에서만 판정하도록 4건을 다시 썼다(자동화 실패 시
  관찰 실행 · 관찰 실패 시 자동화 결과 보존 · 동시 실패 시 두 실패 모두 보고 · 실패 tick 뒤
  사용자 턴 무영향). 수정 전 3건 실패를 실측했다.
- 배선 교체: 자동화도 자기 오류 경계를 갖는 워커로 분리했다. 두 워커가 한 tick 안에서 각자
  돌고, 실패는 숨기지 않고 결과(`automation.failed`·`observe.failed`)에 실린다.
- 반증: 자동화 격리를 없애 예전 배선으로 되돌리면 3건이 실패한다.

## 4-B. 감사 P2 — 소스의 NUL 문자 제거

`tcell-observe.js` 23·47행의 digest 구분자가 **원문 NUL** 로 들어가 Git 이 파일을 binary 로
봤다. 런타임 의미(NUL 구분자)는 그대로 두고 소스 표기만 이스케이프(`'\0'`)로 바꿨다.
파일은 이제 UTF-8 텍스트이며 이후 diff 는 텍스트로 보인다.
