## 2. 차단 발견

### P0-1 · F3 — 실행 영수증이 해당 replay 실행과 결합되지 않는다

계획 §4-3의 OS 가드는 `run.modelCallReceipt`가 존재하고 모델 신분 검증을 통과했는지만
확인한다. 그 영수증이 해당 `caseId`·`principleId`·case input을 실제로 실행한 호출인지,
그 호출의 출력이 저장된 `outputDigest`와 같은지는 가드에 없다.

따라서 저장소에 존재하는 무관한 정상 모델 호출 영수증을 ReplayCase에 붙여도 ①·②를
충족할 수 있다. 계보 실존과 모델 신분은 증명되지만 **그 원리를 그 사례로 replay했다는 사실**은
증명되지 않는다. `negative 0`도 반례 사례 수가 0이어도 된다는 뜻인지, 반례 실행 실패가
0이어야 한다는 뜻인지 두 해석이 가능하다.

F3의 종료 조건인 검증된 replay 실행 증거가 아직 성립하지 않는다.

### P0-2 · F5 — 연결 이름이 실제 자격·응답 신분을 증명하지 않는다

계획 §4-6은 요청 `connection id`와 endpoint·model, 응답 model을 기록한다고 한다. 현재 코어의
`connectionId()`는 `${provider}:${modelId}`여서 같은 provider/model의 다른 자격이나 다른
endpoint를 구분하지 않는다. 역할 fallback이 실제 어느 자격을 탔는지 이 값만으로 증명할 수 없다.

또한 현재 provider client는 응답 본문에서 model 신분을 반환하지 않고 최종 텍스트만 반환한다.
provider별로 응답 model 필드가 없거나 현재 스트림 파서가 버리는 경우의 판정도 계획에 없다.
따라서 요청 라벨과 실제 호출 자격·응답 신분의 대조가 생산 가능한 증거 계약으로 닫히지 않았다.

F5가 동결된 원인인 “라벨은 여러 개지만 실제로는 활성 연결 하나가 답함”을 이 계획만으로
재발 방지할 수 없다.

### P1-1 · F6 — 같은 오너의 웹·채널 신분을 결합하는 생산 계약이 없다

계획 §4-7은 웹 `userRef`를 로컬 오너 상수로, 채널 `userRef`를 `channelUserId`로 만든다.
두 값은 생산 경로에서 서로 다른 신분인데, 동시에 “같은 userRef면 채널↔웹 승계 공급”을
완료 조건으로 둔다.

동일 오너임을 결합하는 사실 원천이 없으므로 실제 제품에서는 교차 표면의 같은 사람을 같은
`userRef`로 만들 수 없다. 시험 fixture가 양쪽에 같은 값을 직접 주입하면 반대시험은 통과하지만
제품 배선은 성립하지 않는 모양이다. F6의 사용자 scope가 아직 필드 선언에 머문다.

### P1-2 · `REPEAT_PREVENTABLE` — “전체본”이 현재 정본만으로 실행 가능하지 않다

v3는 스스로 “전체본”이라고 선언하지만 다음 핵심을 `v2 유지`로 대체한다.

- 전제 P1~P6과 원칙 번역
- 응답 뒤 소비·저장 정직성·수정 허용/금지 구역의 완전한 계약
- S1~S5의 범위와 완료 조건
- 필수 결과 10항, POM 데이터 계약, 이후 연결
- 중단 신호와 종료 조건의 원문

v2는 같은 경로에서 v3로 덮어쓴 과거 커밋이며 현재 활성 정본이 아니다. 구현자는 v3 파일만으로
작업할 수 없고 Git 과거본을 찾아 두 문서를 수작업 병합해야 한다. 이 상태에서는 v3가 바꾼 F1~F6과
v2의 옛 계약 중 어느 쪽이 우선인지 구현 중 다시 판단하게 된다.

이는 앞서 반복된 정본 투영 누락과 같은 유형이다. 확장된 `audit:docs` 7종도 이 불완전한 전체본을
PASS했으므로, 그 검사의 실제 보장 범위는 여전히 “현재 계획의 구현 완결성”을 포함하지 않는다.
