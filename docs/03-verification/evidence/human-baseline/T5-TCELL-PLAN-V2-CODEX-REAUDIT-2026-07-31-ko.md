## 1. REPEAT_PREVENTABLE

### RP-1 · P1 — 정본 투영 검사가 실제 남은 투영 오류를 통과시킨다

`npm run audit:docs`는 5개 반대시험을 통과하고 끊긴 경로·상태 선언 중복·지위 토큰 부재·퇴역
토큰 두 종류를 잡는다. 이 범위의 검사는 실효가 있다.

그러나 같은 현재 인수인계에는 아래 낡은 현재 투영이 남아 있는데 검사 결과는 PASS다.

- `§4:179` 현재 작업이 여전히 "T-cell 재착수 전 기준선·성능 측정 계약 정립"
- `§9:437` 다음 작업이 여전히 "v2 전체본 재제출"
- `§10:457-462` 새 세션 여섯 줄이 여전히 v1 차단 반영·전체 보강을 다음 작업으로 지시

검사는 `§0-A`의 "현재 상태는" 한 문장 개수와 계획 지위 토큰이 문서 **어딘가에 존재하는지**만
본다(`audit-docs.mjs:63-79`). 현재 작업·차단·다음 행동의 의미 일치는 검사하지 않는다.
직전 두 차례의 정본 투영 누락과 같은 구조가 "구조적 종결"을 선언한 바로 그 제출에서 다시
통과했다.

### RP-2 · P0 — `admitted`를 `applied`라고 다시 이름 붙였다

계획 `§4-4:112-115`는 `[반영된 기억]` 블록에 들어간 모든 ID를 `appliedMemoryRefs`로 기록하고,
다음 정정 때 그 항목을 감쇠 후보로 삼는다. 그러나 프롬프트에 입장한 사실은 모델이 실제 판단에
사용했다는 사실이 아니다.

이는 `retrieved ≠ admitted`를 지키면서 바로 다음 축에서 `admitted = applied`를 만든 것이다.
모델이 무시한 기억도 "적용됨"으로 기록돼 정정의 책임을 뒤집어쓸 수 있다. 이름과 내부 필드를
검증된 사실로 취급했던 이전 TG-4 계열과 같다.

### RP-3 · P0 — 모델 신분을 실제 호출이 아니라 구성 이름으로 다시 증명한다

계획 `§4-6:129-130`은 provider를 전경과 같은 구성으로 제한하고 모델 식별자를 원장에 적는다.
하지만 같은 provider 설정이나 역할 이름은 실제 요청 대상·자격·응답 모델 신분의 증거가 아니다.
이 프로젝트는 이미 `modelFor(role)`의 활성 연결 fallback 때문에 여러 계열 라벨이 실제로는 한
OpenAI 연결이었던 실패를 겪었다. v2에는 실제 호출 신분을 판정 근거와 묶는 계약이 없다.

## 2. 동결 차단 목록

다음 여섯 항목은 다음 재제출·재감사의 **동결 범위**다. 이 범위 밖의 개선 아이디어는 핵심 성공
조건을 무효화하는 재개봉 사유가 아니면 후속 관찰로만 분류한다.

### F1 · P0 — 관찰 원천에 전 표면 공통의 불변 turn 신분과 순서가 없다

계획 `§4-1:68-71`은 단일 `{lastProcessedRef}` 이후의 세션 턴·원장을 처리한다고 한다.
현재 일반 `/turn`과 채널 transcript는 불변 `turnId`를 저장하지 않고, 세션 JSON은 제자리 상태
투영이다. `EventLog`의 `turnId`는 스트림 경로에만 존재한다. 여러 세션 파일 사이에는
`lastProcessedRef` 하나가 기준으로 삼을 전역 순서도 없다.

따라서 현재 계약만으로는 웹 일반 턴·SSE·채널을 모두 정확히 한 번 처리했다는 사실, 크래시 뒤
어디서 재개해야 하는지, 늦게 저장된 다른 세션 턴을 건너뛰지 않았는지를 증명할 수 없다.

### F2 · P0 — 선언 인용과 실제 기억 내용의 결합이 없다

계획 `§4-2:80-85`는 `utteranceQuote`가 사용자 원문의 부분 문자열인지와
`speechAct=declaration`인지만 검증한다. 모델이 제출한 `statement`가 그 인용문의 의미에서
나왔는지, 같은 대상·범위인지 묶는 계약은 없다.

모델은 실제 선언 한 조각을 quote로 싣고 더 넓거나 다른 statement를 제안할 수 있다. 질문·인용
네 예시의 회귀시험이 통과해도 새로운 표현에서 같은 구조가 남는다.

### F3 · P0 — 상태 이름은 생겼지만 replay의 검증된 실행 증거가 없다

계획 `§4-3:93-108`, `S4:183-189`는 상태와 positive/negative/boundary 수를 정의한다. 그러나
ReplayCase의 근거 스키마, 실제 실행 여부, 기대 사실과 발생 사실, baseline/candidate 비교,
저장소 조회를 통한 계보 확인이 없다. 모델 verdict가 어떤 OS 사실을 충족해야 `replay_passed`가
되는지도 없다.

이 상태에서는 모델이 "통과"라고 답한 것이 자동 입장의 근거가 된다. 상태 이름과 watermark가
있어도 검증된 replay 수명주기는 아니다.

### F4 · P0 — 효과 감사가 실제 적용을 식별할 수 없다

F4는 RP-2의 제품 영향이다. S5는 정정과 오적용을 특정 원리에 귀속해야 하지만, v2가 가진 것은
프롬프트 입장 목록뿐이다. 실제 응답·계획·도구 선택에 어느 원리가 사용됐는지 확인할 사실이 없어
무관 기억 감쇠 0이라는 완료 조건을 증명할 수 없다.

### F5 · P0 — 백그라운드 모델의 실제 요청 신분이 검증되지 않는다

F5는 RP-3의 제품 영향이다. 별도 자격 경로를 만들지 않는 것, usage와 모델 이름을 기록하는 것만으로
실제 성장 호출이 전경과 같은 자격·모델 경계를 탔다는 사실이 되지 않는다. provider fallback이나
응답 모델 변경이 일어나도 replay·후보 결과가 정상 증거처럼 남을 수 있다.

### F6 · P1 — ActiveWorkLane의 scope가 프로젝트와 사용자를 식별하지 못한다

계획 `§4-7:133-140`의 `scopeRef{surface, channelUserId?, sessionOrigin}`에는 workspace/project
신분이 없다. 웹 표면에는 사용자 신분도 없다. `sessionOrigin`은 대화 유입 채널이지 작업
프로젝트가 아니다. 또한 원천으로 든 `activeGoal`은 현재 모델/계획이 만든 값이라 "모델 추정의
durable 승격 금지" 선언과도 어긋난다.

이 계약으로는 같은 표면의 다른 프로젝트 lane 미노출, 같은 사용자의 다른 채널 승계, "최종본"의
artifact 신분을 동시에 증명할 수 없다.

## 3. 차단은 아니지만 구현 전에 수치로 고정할 항목

- observations·bundles·lane 상한, TTL, grace floor, replay 표본 기준이 "구현 시 제안" 또는
  초안으로 남아 있다(`§4-3:107-108`, `S4:185-187`).
- `1ms도 늦추지 않음`은 계측 잡음과 프롬프트 길이 증가 때문에 관찰 가능한 완료 기준이 아니다
  (`§1`, `§4-1`). 구조 불변식과 실제 성능 판정이 아직 같은 문장에 섞여 있다.
- tick의 기존 자동화와 T-cell 워커 중 한쪽 실패가 다른 쪽 실행을 막지 않는 실패 격리 계약이 없다.
- archive/restore, pin, "미사용은 노후 증거가 아님", 사용자가 원리·lane을 직접 보고 고치는
  표면은 v1 감사 후에도 계획 완료 조건에 닫히지 않았다.
- S2는 여전히 감사의 "명시 승인"을 착수 조건으로 둔다(`S2:173`). 감사가 착수 허가제가 아니라는
  협업 계약과 맞지 않는다.

이 항목들은 동결 F1~F6을 해결하는 과정에서 핵심 계약을 무효화하지 않는 한 새 감사 왕복 사유로
확대하지 않고, 구현 전 계획 수치·후속 항목으로 함께 확정한다.
