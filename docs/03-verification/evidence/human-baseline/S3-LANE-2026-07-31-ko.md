## 2. 라이브가 잡은 결함 — 지어낸 필드로 검사만 통과하고 있었다

첫 라이브에서 **lane 이 3회 모두 아무것도 공급하지 않았다.** 원인은 제 검사가 제품이 만들지
않는 `receipt.artifact` 필드를 픽스처로 지어냈기 때문이다. 실제 파일 손은 해석된 절대경로를
`result.path` 에 남긴다(`local-file.js` 의 `subjectOf` 와 같은 진실).

- 수정: lane 파생을 **실제 receipt 형태**(`actualCall.tool === 'local.file'` + 산출 액션 +
  `result.path`)에서만 하도록 바꾸고, 검사 픽스처도 제품이 남기는 그대로 맞췄다.
- 이 계열은 이전 슬라이스에서도 나왔다(검사가 이름보다 넓게 주장). 라이브가 아니면 못 잡았을
  결함이라 그대로 기록한다.

## 4-A. 감사 P1 — 채널 경로 배선 누락 (2026-07-31 보강)

웹 `/turn` 만 `carryableWork` 를 갱신하고 `runChannelInboundTurn` 은 갱신하지 않았다. 그래서
같은 오너·허용된 채널 사용자라도 새 채널 대화에서는 lane 사실을 모델 입력으로 받지 못했다
(계획 §4.7 "같은 오너 웹↔binding 채널 승계" 미충족). 표면마다 다른 현실이 생긴 자리다.

- 반대시험 3건을 먼저 추가해 수정 전 실패를 실측했다(허용 채널 사용자 공급 · 허용목록 밖
  사용자 공급 0 · payload 의 `principalRef` 주장 무효).
- 배선: 채널 턴도 ctx 생성 전에 같은 방식으로 `carryableWork` 를 계산한다.
- 제품 경로로 확인: `handleChannelMessage` 로 실제 채널 턴을 돌려 웹에서 만든 산출물 이름이
  모델 입력에 오는 것, 원시 절대경로가 없는 것, 낯선 사용자에게는 0인 것을 검사한다.
- 반증: 채널 배선을 제거하면 1건 실패, 채널 principal 해석을 무조건 오너로 바꾸면 2건 실패.

## 5. 남은 한계 (감사 판정 요청 · P1 이하)

- 이번 라이브에서 승계된 산출물은 **대화 산출물(response)** 이었다. 파일 산출물 경로가 lane 에
  잡히려면 성공한 `local.file` receipt 가 `result.path` 를 남겨야 하는데, 승인 관통 흐름에서
  그 값이 원장에 남지 않은 회차가 있었다. 파일 손 자체의 결함(H08 뿌리)은 T-cell 밖 별도
  슬라이스이므로 여기서 건드리지 않았다.
- lane 의 `subject` 는 세션 제목(사용자 첫 발화 앞 30자)이라 문장이 다소 투박하다. 사실 문장의
  중복은 정리했으나 제목 자체의 품질은 S5 표면 단계에서 다룰 항목으로 남긴다.
