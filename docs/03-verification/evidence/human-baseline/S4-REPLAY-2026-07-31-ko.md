후보 원리는 "여러 달 수치를 주면 **표로** 정리하고 지표를 계산한다"였다. 세 가지가 겹쳤다.

같은 모델 대역 함수로 두 경우를 돌렸다. 앞 실패가 입력에 **없으면** 같은 넓은 원리가 다시
나와 또 떨어지고, **있으면** 좁혀서 통과한다. 갈린 변수는 실패 이력 하나뿐이다.

없던 내 발명이었다. suite 불통과는 일시적 장애가 아니라 같은 입력이면 같은 결과다 — 기다린다고
나아지지 않고, 나아지게 하는 것은 앞 회차 실패 이력뿐이며 그건 즉시 손에 있다. 페이싱은 예산이,
멈추는 것은 회차 상한이 한다. 시계는 **빌림(죽은 워커 판정)** 에만 남겼다.

걷어낸 뒤 라이브에서 **시계 조작 없이** round 0 → 1 → 2 가 연달아 돌았다(예산 20 → 38/50).

| 회차 | 결과 | 사유 |
|---|---|---|
| 0 | 불통과 | `positive_failed, forbidden_fact_occurred, boundary_sample` — 과잉 일반화 |
| 1 | 불통과 | **`boundary_sample`** — 원리는 좁아졌는데 사례가 모자랐다 |
| 2 | 불통과 → `exhausted` | 같은 계열 |

round 1 의 원리는 실제로 좁아졌다: "…**새로 제시된 그 달 한 달치에 한해** 다섯 지표만…".
실패 축이 **과잉 일반화에서 표본 부족으로 옮겨갔다** — 이력 전달이 원리 품질에는 실제로
작용했다는 뜻이다. 다만 그 회차는 표본을 못 채워 통과하지 못했다.

### 라이브가 잡은 결함 3건 (전부 검사에서는 통과하고 있었다)

| # | 증상 | 원인 | 수정 |
|---|---|---|---|
| 5 | 옛 저장본이 회차를 계속 막음 | 없어진 cooldown 의 대기 시각이 `nextAttemptAt` 에 남아 있었다 | `nextAttemptAt` 을 **빌림 전용**으로 못박고, 재시도 상태는 대기 없이 열리게 |
| 6 | `bundle_gone` 으로 회차가 헛되이 탐 | 묶음 신분을 **구성원 전체**로 만들어, 관찰이 하나 붙을 때마다 ID 가 바뀌어 job 이 고아가 됐다 | 신분을 **씨앗(정렬 첫 구성원)** 으로. 반복이 늘면 `count` 만 는다 — 학습이 누적된다 |
| 7 | 표본 부족을 10호출 다 쓴 뒤에야 앎 | 제안 단계에서 셀 수 있는 것을 안 셌다 | 최소 표본을 못 채운 제안은 **사례를 돌리기 전에** 접고, 무엇이 모자랐는지를 다음 회차에 전한다 |

6번이 특히 무겁다. 묶음 신분이 불안정하면 배운 표식도 무의미해지고 같은 현상을 처음부터 다시
배운다 — 학습이 쌓이지 않는다.

### 현재 상태

두 job 모두 `exhausted`(회차 3 소진). 승격·반영 **0**. 위 세 수정은 이 라이브 뒤에 들어갔으므로,
**다음 판정은 새 반복으로 새 묶음을 만들어 다시 재야 한다** — 시간을 기다리는 것이 아니라
반복을 더 시키는 것이 다음 걸음이다.

## 12. **S4 미완 — 막는 것은 한 계열이다**

승격된 원리가 **모델 입장에 실패했다.**

```
admittedContext(기억, "12월 것도. 1800 / 1100 / 신규 17 / 이탈 5") → 0건
```

원인은 관련성 판정이 **낱말 겹침**이라는 데 있다(`isRelevant`: 원리 문장의 낱말이 요청에
들어 있는가). 실측:

| 발화 | 좁은 원리(28낱말) | 넓은 원리 |
|---|---|---|
| `12월 것도. 1800 / 1100 / 신규 17 / 이탈 5` (11낱말) | **false** | false |
| `12월 매출·비용·신규·이탈 정리해줘` | true | false |

**좁힐수록 문장이 길고 구체적이어서, 축약된 실제 발화와 낱말이 겹치지 않는다.** S4 가 원리를
좁히도록 요구하는 방향과, 기존 입장 관문이 낱말 겹침으로 좁게 여는 방향이 정면으로 부딪힌다.

그래서 이번 라이브의 새 대화 답이 원리를 안 따른 것은 모델이 무시한 게 아니라 **원리를 본 적이
없기 때문**이다. 그리고 재질문 0 은 이번에도 `carryableWork` 가 채워져 있어 **S3 lane 기여를
배제할 수 없다** — S4 성과로 쓰지 않는다.

### 사다리에서 지금 서 있는 칸

```
후보 O → suite 통과 O → 승격 O → 입장 X → 실제 기여 X → 과잉 적용 없음 O(입장이 없어 자명)
```

`입장` 칸에서 막혔다. 이건 S4 안에서 고칠 수 있는 자리가 아니라 **기존 입장 관문(§4.5 계열)의
관련성 판정을 건드리는 일**이라, 계획·범위 판단이 필요하다. 임의로 넓히면 "좁게 입장" 계약이
무너지므로 감사·오너 판정을 요청한다.

## 13. A급 결함 수정 — 검증된 원리의 입장 판정 (2026-07-31)

막던 것: 원리를 좁힐수록 문장이 길고 구체적이 되는데, 관련성 판정이 **낱말 겹침**이라 축약된
실제 발화와 안 겹쳐 입장 자체를 못 했다. 낱말 판정을 느슨하게 풀면 과잉 적용이 열린다.

**푼 방법: 이미 있는 사실을 쓴다.** 그 원리가 어떤 상황에서 통과했고 어떤 상황에서 적용되면
안 되는지는 suite 가 이미 검증했다.

- `appliesWhen` = 그 원리를 낳은 **반복 발화 원문**(사람이 실제로 친 말)
- `notWhen` = **검증된** negative 사례(적용하면 안 되는 자리)
- 판정 = 같은 종류의 말인가(**겹침**) · 본보기를 실제로 덮는가(**덮음**) · 비적용에 더 가깝지
  않은가. 셋을 다 만족해야 든다.

문턱은 실측에서 골랐다(0.45): 같은 요청의 다른 표현 0.50~1.00 · 인접하지만 다른 일 0.14~0.20 ·
무관 0.00.

### 반대시험 (감사 지정 7건 + 실측에서 발견한 4건)

| 발화 | 기대 | 결과 |
|---|---|---|
| `12월 것도. 1800 / 1100 / 신규 17 / 이탈 5` | 입장 O | **O** |
| `12월 매출·비용·신규·이탈 정리해줘` | 입장 O | **O** |
| `점심 하나만 골라줘` | 0 | **0** |
| `이 숫자로 마케팅 문구 한 줄만 써줘` | 0 | **0** |
| `표 말고 한 문장으로만` | 원리 강제 0 | **0** |
| `replayPassed=false` 원리 | 0 | **0** |
| `userConfirmed=false` 원리 | 0 | **0** |
| `오늘 일정 좀 정리해줘` · `회의록 정리해줘` (내가 발견) | 0 | **0** |
| 검증된 비적용 상황에 가까운 발화 (내가 발견) | 0 | **0** |
| 검증 사례가 없는 선호 기억 (내가 발견) | 기존 판정 유지 | **유지** |

제품 경로로도 확인했다: 축약 발화에 원리가 **모델 입력에 들고**(`admittedContext`), 같은 서버의
인접 요청에는 들지 않으며, 앞 대화가 없어 `carryableWork` 는 0이다(S3 기여 분리).

### 만들다 걷어낸 것 두 개

숫자 자릿수를 모양에 넣어 봤고, 비적용과 아슬아슬할 때를 막는 여유(margin)도 넣어 봤다.
**둘 다 여덟 개 판정 중 하나도 바꾸지 않았다** — 짧고 흔한 말을 실제로 막은 것은 덮음 조건이다.
일하지 않는 장치를 "필요하다"는 주석과 함께 남기지 않는다.

명시적으로 다른 형식을 덧붙인 발화(`…근데 표 대신 문장 요약으로 줘`)에는 원리가 그대로 든다.
감추지 않는 것이 맞다 — 모델이 현재 지시와 함께 보고 판단할 일이지 Runtime 이 지워 줄 일이 아니다.

### 새 대화(축약 발화) 결과

입력: `12월 것도. 1800 / 1100 / 신규 17 / 이탈 5` — 봉인 기준선에서 오독하고 되물었던 그 문장.

- **입장**: 그 원리가 모델 입력에 실제로 들어갔다(`admittedContext` 1건).
- **답**: 7월·12월을 **한 표**로 모으고, 이어서 **그래프 종류와 축 구성을 제안**했다.

### S3 lane 기여와 S4 원리 기여를 나눈 근거

이번 회차의 `carryableWork` 는 비어 있지 않다(`…정리한 답이 남아 있음` 1건). 그래서 **7월을
같이 본 것**은 lane 으로 설명될 수 있다 — 그건 S4 성과로 쓰지 않는다.

그러나 답에는 **lane 사실에도, 사용자 요청에도 없는 요소**가 있다.

| 요소 | 사용자 요청 | lane 사실 | 승격된 원리 | 답 |
|---|---|---|---|---|
| 표로 모으기 | 없음 | 없음 | **있음** | 있음 |
| **그래프 종류·축 제안** | **없음** | **없음** | **있음** | **있음** |

그래프 제안은 오직 그 원리에만 있는 지시이고, 답에 그대로 나타났다. **이 요소는 lane 으로
설명되지 않는다** — S4 원리의 기여다.

### 회차 변동은 구조가 흡수했다

같은 절차로 앞서 두 번 돌렸을 때 한 번은 round 1 통과, 한 번은 3회차 소진이었다. 이번엔
round 2 통과다. **suite 통과 시점은 모델에 따라 갈리고, 회차 구조가 그 변동을 흡수한다.**
한 번에 되는 것을 성과라 부르지 않는다.

## 16. 판정 — **S4 PASS** (2026-07-31)

완료 흐름이 같은 제품 경로·같은 회차에서 이어졌다.

```
후보 O → suite O → 승격 O → 입장 O → 실제 H02 기여 O → 과잉 적용 0 O
```

### 명시하는 한계 — 이 PASS 가 말하지 않는 것

1. **suite 통과 회차는 변동한다.** 같은 절차를 세 번 실측했고 각각 round 1 통과 ·
   3회차 소진(`exhausted`) · round 2 통과였다. "반복 3회면 원리가 선다"가 아니다.
2. **그 변동은 `maxRounds`(3) 안에서만 흡수된다.** 세 회차를 다 쓰고도 못 세우면 그 묶음은
   종단이고, 자동으로 되살아나지 않는다. 즉 **한 묶음에서 원리가 서지 못하는 경우가 실제로
   있다** — 세 번 중 한 번이 그랬다.
3. 통과 여부는 모델이 얼마나 좁은 원리를 쓰느냐에 달렸다. OS 가 보장하는 것은 "잘못 배운
   원리가 들어가지 않는다"이지 "반드시 배운다"가 아니다.
4. 라이브 기여 판정에서 `carryableWork` 가 비어 있지 않았다. **"7월을 같이 본 것"은 S4 성과가
   아니다** — S4 기여로 세는 것은 lane·요청 어디에도 없는 요소(그래프 종류·축 제안)뿐이다.

## 17. S5-2/S5-3 라이브 보강 — 통제 채널 호출률 실측 (2026-07-31)

**문제**: S5-2·S5-3 은 반대시험 27건이 전부 초록인데, 실제 `gpt-5.1` 제품 경로에서
`memory.cite` **0/1**, `memory.correction` **0/1** — 두 채널 다 한 번도 호출되지 않았다.
모델이 부르지 않는 통제 채널은 죽은 코드다.

### 원인 (순서대로 확인)

1. **배선은 정상**이었다. 무과금으로 확인: 실제 턴 경로의 모델 호출에 손 5개와 통제 채널 4개
   (`memory.propose`·`cite`·`correction`·`withdraw`)가 전부 붙어 있었다.
2. **원인은 내가 쓴 설명**이었다. `cite` 에 "참고하지 않았으면 부르지 않는다 — 안 부르는 것이
   정상이고, 부르지 않아도 아무 문제 없다", `correction` 에 "확신이 없으면 부르지 않는다"라고
   써 뒀다. 안전하게 쓴다는 것이 모델에게는 **건너뛰어도 되는 것**으로 읽힌다.

### 고친 방향 — 금지가 아니라 사실 공급

압박 문구("반드시 불러라")로 바꾸지 않았다. 그러면 참고하지도 않은 것을 적어 통계가 통째로
거짓이 된다. 대신 **T5 가 무엇을 모르는지**를 알려 준다.

- `cite`: "T5 는 어떤 기억을 보여줬는지는 알지만, 그중 무엇이 실제로 도움이 됐는지는 모른다."
- `correction`: "T5 는 이 표식으로 어떤 기억이 자꾸 어긋나는지를 본다. 한 번으로는 아무 것도
  바뀌지 않는다."
- 그리고 **쓸 자리에서** 안내한다: 기억을 보여주는 그 자리에 인용 안내를, 직전 답이 기억을
  참고한 다음 턴에만 정정 안내를 놓는다(아무 턴에나 놓으면 없는 정정을 만들어 내게 된다).

### 실측 (실제 `gpt-5.1`, 제품 HTTP 경로)

| 채널 | 보강 전 | 보강 후 |
|---|---|---|
| `memory.cite` — 지정 시나리오(원리 입장 + 답이 원리를 따름) | 0/1 | **0/3** |
| `memory.cite` — 기억이 보인 전체 턴 | 0/1 | **3/9** |
| `memory.correction` — 지정 시나리오(명백한 정정) | 0/1 | **1/3** |

**두 채널 다 살아났지만 신뢰할 수 없다.** 특히 cite 는 지정 시나리오 0/3 인데 전체로는 3/9 다 —
같은 문장을 넣어도 부를 때와 안 부를 때가 갈린다(모델 변동). 보강 전후로 0 → 비0 이 된 것은
사실이지만, "원리가 반영된 턴에서 cite 가 호출된다"는 완료 조건은 **아직 못 채웠다.**

### 그래서 감쇠로 넘어가지 않는다

S5-3 의 상관은 `shown ∩ cited` 위에 서 있다. cite 가 3턴 중 1번꼴로만 오면 상관은 그만큼
드물게 쌓이고, 그 위의 감쇠는 **"기억이 나빠서"가 아니라 "모델이 그날 인용을 했느냐"** 에
좌우된다. 이 신뢰도로 감쇠를 붙이면 안 된다.

판정 요청: 자기보고(cite)가 본질적으로 최선노력(best-effort)이라면, 상관의 근거를 그것 하나에
둘 수 있는지 — 아니면 S5-3 의 근거를 바꿔야 하는지에 대한 범위 판단이 필요하다.

## 18. 계약 보정 — 상관의 근거를 인용에서 **지목**으로 (2026-07-31 범위 판정)

cite 는 "네가 뭘 참고했냐"를 묻는 자기보고라 원리적으로 100% 가 안 나온다(지정 시나리오 0/3).
그 위에 감쇠를 세우면 **"기억이 나빠서"가 아니라 "모델이 그날 인용을 했느냐"** 가 감쇠를 정한다.
그래서 근거를 옮겼다.

| | 보정 전 | 보정 후 |
|---|---|---|
| 상관의 근거 | `shown ∩ cited` | **정정의 지목 ∩ 직전 턴 shown** |
| cite | 필수 | **보조** — 있으면 `confidence: 'cited'`, 없으면 `'claimed'` |
| 감쇠 문턱 | 독립 2회 | **독립 2회(불변)** — confidence 가 문턱을 낮추지 않는다 |

### 보태야 했던 것 — 지목하려면 지목할 목록이 있어야 한다

지목만 요구하고 목록을 안 주면 모델은 기억으로 지어내고, 지어낸 것은 전부 대조에서 떨어진다 —
**cite 가 죽어 있던 것과 똑같은 모양**이다. 그래서 직전 턴에 보인 문장을 이번 턴 입력에
사실로 놓는다(`[직전 답이 놓고 쓴 것]`). 그 자리에서만 정정 채널을 안내한다.

그 과정에서 결함이 하나 드러났다: 커널은 `input.turnRef` 를 받지 못하고 있었다. S5-1 에서는
서버가 저장할 때 자기 `turnRef` 로 덮어써서 가려져 있었다. 턴 신분을 아는 쪽(서버)이 계산하게
옮겼고, 웹·채널 두 경로가 각자의 신분을 쓴다.

### 실측 (실제 `gpt-5.1`, 제품 HTTP 경로)

| 항목 | 결과 |
|---|---|
| `correction` 지정 시나리오(명백한 정정) | **2/3** (보강 전 0/3 → 지목 도입 후) |
| 지목이 shown 과 대조돼 상관이 섰는가 | **O** — `p-원리 × 2` |
| `cite` (보조 근거) | 3/9 — 필수가 아니므로 상관을 막지 않는다 |
| 독립 2회에서 감쇠 후보 | **O** — `correlations: 2, confidence: ['cited','cited']` |
| 감쇠 실행 | **0** — 후보 목록만 있고 아무 것도 내리지 않았다 |
| 내부 ID 노출 | 저장에만, 사용자면·모델 입력 **0** |

**cite 3/9 인데도 상관이 섰다** — 이것이 이번 보정의 요점이다. 인용이 없어도 지목이 맞으면
상관이 서고, 인용이 있으면 확신만 올라간다.

## 19. S5-4 · 가역 감쇠 회로 (2026-07-31)

오너 경고: "기억을 내리는 기능은 잘못 만들면 말귀를 좋게 하는 게 아니라 멀쩡한 기억을 조용히
죽이는 독이 된다." 그래서 **내리는 것보다 잘못 내리지 않는 것**을 훨씬 많이 검사했다.
회로는 다섯 조각 한 묶음이다: 후보 → 감쇠 → 원장 → 복원 → 표면.

### 잘못 내리지 않기 위해 지킨 것

| 경계 | 방식 |
|---|---|
| 독립 정정 2회 문턱 | **판정 자리를 한 곳에만** 뒀다. 두 군데면 하나가 무너져도 다른 하나가 가려 준다 |
| `cite` 확신이 문턱을 낮춤 | 금지 — 확신 종류를 보지 않는다(모델 자기보고가 뒷문이 되지 않게) |
| 미사용·오래됨 | **근거가 아니다**(§4.10). 안 쓴 기억과 틀린 기억은 다르다 |
| pin | 자동 감쇠 면제 — 사용자가 붙든 것을 OS 가 떼지 않는다 |
| 신호 없음 | "문제 없음"이 아니라 **모르는 상태** — 어느 쪽으로도 안 움직인다 |
| 시각을 모르는 상관 | 새것으로 세지 않는다(불확실하면 안 내리는 쪽) |
| 한 번에 내리는 수 | 상한 3 — 몰아 내리면 사용자가 무슨 일인지 알 수 없다 |
| 복원 뒤 재감쇠 | 같은 근거로는 안 내린다. **복원은 "이 근거로는 두라"는 사용자의 답이다** |

### 감쇠는 삭제가 아니다

문장도 신분도 그대로 남고 표식(`decayedAt`)만 붙는다. 입장 게이트(`isInfluenceEligible`)가
그 표식 하나만 보면 되도록 했다 — 레인을 늘리지 않았다. 복원은 표식을 걷는 것뿐이다.

### 라이브 관통 (실제 `gpt-5.1`, 제품 경로 · 시계 조작 0)

| 단계 | 결과 |
|---|---|
| 감쇠 전 입장 | **O** |
| 정정 상관 누적 | `p-원리 × 3` (lane 항목은 ×1 — 문턱 미달로 안 내려감) |
| tick 이 내림 | **O** — `correction_correlation:2`, 카드 0·승인 0 |
| 표면에 보임 | **O** — 문장과 사유가 사람 말로 |
| **감쇠 후 입장** | **X** ← 잘못된 기억이 실제로 덜 들어간다 |
| 복원 | **O** |
| **복원 후 입장** | **O** ← 되돌아온다 |
| 원장 | `decayed` · `restored` 기록(원문 없이 지문만) |

첫 회차는 모델이 정정을 안 알려 상관이 0이라 감쇠가 촉발되지 않았다. 그건 실패가 아니라
**안 쌓인 것**이다 — 잘못 쌓인 것이 아니므로 안전한 실패다. 두 번째 회차에서 전 구간이 이어졌다.

### 반대시험 15건 · 돌연변이 10종

문턱 붕괴 · cite 뒷문 · pin 자동 감쇠 · 상한 제거 · 감쇠를 삭제로 · 복원해도 표식 안 걷힘 ·
무한 왕복 · 입장 게이트 무력화 · 표면에서 감춤 · 원장 누락 — 전부 물림(스윕 66건 PASS).

## 20. S5-5 · 성장 표면 (2026-07-31)

새 학습 기능이 아니다. **이미 있는 상태를 사용자가 보고 고치고 되돌리는 자리**다.
S5-4 까지 만든 감쇠·붙듦·치움은 전부 OS 안의 표식이었는데, 표식이 보이지 않으면 사용자는
왜 어느 날부터 안 되는지 알 수 없다. 그 상태에서 감쇠는 "조용히 죽이는 것"과 같다.

### 목록은 하나다

| 상태 | 사람 말 | 뜻 |
|---|---|---|
| `active` | 쓰이는 중 | 지금 행동에 들 수 있다 |
| `pinned` | 붙들어 둠 | 사용자가 붙들었다 — 자동 감쇠 면제 |
| `archived` | 치워 둠 | **사용자가** 치웠다. 들지 않지만 지워지지 않았다 |
| `decayed` | 내려감 | **OS 가** 정정 상관을 보고 내렸다. 역시 되돌릴 수 있다 |

기억·원리·이어받을 작업이 한 목록에 종류 표시와 함께 선다. 상태를 두 군데서 말하면 언젠가
다르게 말하고, 그때 사용자는 어느 쪽을 믿어야 할지 모른다.

### 이번에 실제로 갈라져 있던 것 — 옛 요약이 거짓말을 하고 있었다

화면을 세우고 보니 옛 요약(`/overview`)이 **내려간 항목을 "반영 중"이라고 말하고 있었다.**
그 자리엔 상태 칸이 없어 "반영 중"이라고만 말할 수 있는데, 물러난 항목이 거기 남아 있었다.
새 목록은 `decayed` 라 하고 옛 요약은 `반영 중` 이라 하는 — 같은 항목을 두고 두 화면이 다른
현실을 말하는 상태였다. 표면을 만들지 않았으면 아무도 몰랐을 것이다.

고친 방식은 화면 두 곳을 각각 손보는 것이 아니라 **판정을 한 곳으로 옮긴 것**이다.
`물러남(entry)` 이 `context-mesh` 에 하나 서고, 입장 게이트·옛 투영·성장 표면이 전부 그것을
읽는다. 각자 재는 한 언젠가 또 갈라진다.

### 라이브 관통 (제품 화면 · 실제 버튼 클릭)

| 단계 | 결과 |
|---|---|
| 치워 둠 상태 | 옛 요약 **반영 중 0** · 새 목록 `선호 · 치워 둠` |
| 내려감 상태 | 옛 요약 **반영 중 0** · 새 목록 `원리 · 내려감` |
| 화면의 `되돌리기` 클릭 | `pref-1: archived → active` |
| 되돌린 뒤 실제 턴 | 그 문장이 **실제로 모델 앞에 놓임**(`shownRefs`) |
| 원장 | `pinned` · `restored` — 원문 없이 지문만 |
| 카드·승인 | **0** (설정에서 열 때만 보는 자리) |
| 내부 신분 노출 | **0** (답변·모델 입력 어느 쪽에도) |

### 반대시험 11건 · 돌연변이 8종

구분 표시 · 상태 갈림 · 치움→입장 0→복원→입장 O · pinned 자동 감쇠 면제 · 치운 lane 미공급 ·
원장 4종 · 카드 0 · 내부 ID 미노출 · 기존 확인·되돌리기 경로 무충돌 · 없는 것 조작 시 조용한
실패 · **두 표면이 다른 현실을 말하지 않음**. 돌연변이는 치움을 게이트가 무시 · 옛 요약이
"반영 중"이라 말함 · 치운 lane 계속 공급 · 치우기를 삭제로 · 상태 뭉갬 · 붙듦 표식 소실 ·
복원 불가 · 원장 누락 — 전부 물림(스윕 **74건 PASS**, 회귀 1508 통과).

## 21. 남은 것 (후속 슬라이스)

- **원리는 아직 한 번도 승격되지 않았다.** H02 의 두 수치(재질문 0 · 과잉 일반화 0)는 나왔지만,
  재질문 0 을 만든 것은 S3 lane 승계이고 S4 의 원리 승격은 아니다. "게이트가 옳게 막았다"와
  "원리로 배워서 좋아졌다"는 다른 사실이고, 뒤엣것은 아직 없다.
- 불통과한 묶음은 닫히지 않았다(`cooldown`, round 0). 6시간 뒤 다음 회차가 열리고, 회차 3을
  다 쓰면 종단이다. 다음 회차에서 다른 원리가 서면 그때 다시 잰다.
- 라이브 회차 6회(모델 호출 약 85건). 1~5회차는 위 표의 결함 수정 회차다.
