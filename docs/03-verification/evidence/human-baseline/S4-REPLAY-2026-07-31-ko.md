후보 원리는 "여러 달 수치를 주면 **표로** 정리하고 지표를 계산한다"였다. 세 가지가 겹쳤다.

같은 모델 대역 함수로 두 경우를 돌렸다. 앞 실패가 입력에 **없으면** 같은 넓은 원리가 다시
나와 또 떨어지고, **있으면** 좁혀서 통과한다. 갈린 변수는 실패 이력 하나뿐이다.

## 10. 시계를 걷어내고 회차를 돌린 라이브 결과 (2026-07-31)

오너 지적: **"프로그램이 시간 개념이 왜 필요해. 그냥 횟수지."** 맞다. 6시간 cooldown 은 계획에
없던 내 발명이었다. suite 불통과는 일시적 장애가 아니라 같은 입력이면 같은 결과다 — 기다린다고
나아지지 않고, 나아지게 하는 것은 앞 회차 실패 이력뿐이며 그건 즉시 손에 있다. 페이싱은 예산이,
멈추는 것은 회차 상한이 한다. 시계는 **빌림(죽은 워커 판정)** 에만 남겼다.

걷어낸 뒤 라이브에서 **시계 조작 없이** round 0 → 1 → 2 가 연달아 돌았다(예산 20 → 38/50).

| 회차 | 결과 | 사유 |
|---|---|---|
| 0 | 불통과 | `positive_failed, forbidden_fact_occurred, boundary_sample` — 과잉 일반화 |
| 1 | 불통과 | **`boundary_sample`** — 원리는 좁아졌는데 사례가 모자랐다 |
| 2 | 불통과 → `exhausted` | 같은 계열 |

round 1 의 원리는 실제로 좁아졌다: "…**새로 제시된 그 달 한 달치에 한해** 다섯 지표만…".
실패 축이 **과잉 일반화에서 표본 부족으로 옮겨갔다** — 이력 전달이 원리 품질에는 실제로
작용했다는 뜻이다. 다만 그 회차는 표본을 못 채워 통과하지 못했다.

### 라이브가 잡은 결함 3건 (전부 검사에서는 통과하고 있었다)

| # | 증상 | 원인 | 수정 |
|---|---|---|---|
| 5 | 옛 저장본이 회차를 계속 막음 | 없어진 cooldown 의 대기 시각이 `nextAttemptAt` 에 남아 있었다 | `nextAttemptAt` 을 **빌림 전용**으로 못박고, 재시도 상태는 대기 없이 열리게 |
| 6 | `bundle_gone` 으로 회차가 헛되이 탐 | 묶음 신분을 **구성원 전체**로 만들어, 관찰이 하나 붙을 때마다 ID 가 바뀌어 job 이 고아가 됐다 | 신분을 **씨앗(정렬 첫 구성원)** 으로. 반복이 늘면 `count` 만 는다 — 학습이 누적된다 |
| 7 | 표본 부족을 10호출 다 쓴 뒤에야 앎 | 제안 단계에서 셀 수 있는 것을 안 셌다 | 최소 표본을 못 채운 제안은 **사례를 돌리기 전에** 접고, 무엇이 모자랐는지를 다음 회차에 전한다 |

6번이 특히 무겁다. 묶음 신분이 불안정하면 배운 표식도 무의미해지고 같은 현상을 처음부터 다시
배운다 — 학습이 쌓이지 않는다.

### 현재 상태

두 job 모두 `exhausted`(회차 3 소진). 승격·반영 **0**. 위 세 수정은 이 라이브 뒤에 들어갔으므로,
**다음 판정은 새 반복으로 새 묶음을 만들어 다시 재야 한다** — 시간을 기다리는 것이 아니라
반복을 더 시키는 것이 다음 걸음이다.

## 11. 반복 입력으로 회차를 돌린 라이브 (2026-07-31, 격리 폴더 `r2-data`)

기다리지 않고 **반복을 더 넣어** 새 묶음을 만들고 회차를 돌렸다. 시간 대기 0.

| 확인 항목 | 결과 |
|---|---|
| ① 반복 입력으로 새 묶음 | O — 5턴, 카드 0, 턴 5.2~11.5s |
| ② 묶음 신분 안정 | **O** — `55f24752` 가 관찰 2→3→4 내내 동일, `count` 만 증가 |
| ③ 제안 단계 표본 차단 | 이 회차에서는 발동 안 함(두 회차 모두 표본을 채웠다) |
| ④ 대기 없이 round 0→1 | **O** — 0 불통과(40s) → 1 통과(104s), 예산 22/50 |
| ⑤ 실패 이력이 원리에 반영 | **O** — 아래 |
| ⑥ suite 통과 | **O** — round 1 `pass:true, missing:[]` |
| ⑦ `/memory/confirm` | **O** — `ok:true`, promoted 1건 |
| ⑧ H02 lane 분리 | **X** — `carryableWork` 가 비어 있지 않아 분리 못 함 |
| ⑨ 인접 요청 과잉 적용 | **O** — `냉메밀국수.` 한 줄 |

### ⑤ 실패 이력이 원리 문장을 실제로 바꿨다

- round 0 (불통과 `boundary_violated`):
  > 사용자가 여러 기간의 동일한 지표를 숫자 나열로 주면, **각 기간을 한 표에 모아** 비교 가능하게 정리해 준다
- round 1 (통과):
  > 사용자가 여러 달의 매출·비용·신규·이탈을 연속으로 요청하며 숫자와 함께 '정리해줘/부탁/같이'라고
  > 말할 **때에만**, 이미 정리한 앞달 표에 해당 달 행만 덧붙인 한 개의 비교표로 답하고
  > **새 설명 요약은 붙이지 않는다**

적용 조건("때에만")과 금지("붙이지 않는다")가 문장 안에 들어왔다. 이력 전달이 원리 품질에
작용한다는 것을 라이브에서 확인했다.

## 12. **S4 미완 — 막는 것은 한 계열이다**

승격된 원리가 **모델 입장에 실패했다.**

```
admittedContext(기억, "12월 것도. 1800 / 1100 / 신규 17 / 이탈 5") → 0건
```

원인은 관련성 판정이 **낱말 겹침**이라는 데 있다(`isRelevant`: 원리 문장의 낱말이 요청에
들어 있는가). 실측:

| 발화 | 좁은 원리(28낱말) | 넓은 원리 |
|---|---|---|
| `12월 것도. 1800 / 1100 / 신규 17 / 이탈 5` (11낱말) | **false** | false |
| `12월 매출·비용·신규·이탈 정리해줘` | true | false |

**좁힐수록 문장이 길고 구체적이어서, 축약된 실제 발화와 낱말이 겹치지 않는다.** S4 가 원리를
좁히도록 요구하는 방향과, 기존 입장 관문이 낱말 겹침으로 좁게 여는 방향이 정면으로 부딪힌다.

그래서 이번 라이브의 새 대화 답이 원리를 안 따른 것은 모델이 무시한 게 아니라 **원리를 본 적이
없기 때문**이다. 그리고 재질문 0 은 이번에도 `carryableWork` 가 채워져 있어 **S3 lane 기여를
배제할 수 없다** — S4 성과로 쓰지 않는다.

### 사다리에서 지금 서 있는 칸

```
후보 O → suite 통과 O → 승격 O → 입장 X → 실제 기여 X → 과잉 적용 없음 O(입장이 없어 자명)
```

`입장` 칸에서 막혔다. 이건 S4 안에서 고칠 수 있는 자리가 아니라 **기존 입장 관문(§4.5 계열)의
관련성 판정을 건드리는 일**이라, 계획·범위 판단이 필요하다. 임의로 넓히면 "좁게 입장" 계약이
무너지므로 감사·오너 판정을 요청한다.

## 13. 남은 것 (감사 판정 요청)

- **원리는 아직 한 번도 승격되지 않았다.** H02 의 두 수치(재질문 0 · 과잉 일반화 0)는 나왔지만,
  재질문 0 을 만든 것은 S3 lane 승계이고 S4 의 원리 승격은 아니다. "게이트가 옳게 막았다"와
  "원리로 배워서 좋아졌다"는 다른 사실이고, 뒤엣것은 아직 없다.
- 불통과한 묶음은 닫히지 않았다(`cooldown`, round 0). 6시간 뒤 다음 회차가 열리고, 회차 3을
  다 쓰면 종단이다. 다음 회차에서 다른 원리가 서면 그때 다시 잰다.
- 라이브 회차 6회(모델 호출 약 85건). 1~5회차는 위 표의 결함 수정 회차다.
