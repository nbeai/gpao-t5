## 0. 이번 제출에서 새로 찾아 고친 것 — **같은 결함이 세 자리에 있었다**

S5-5 를 세우면서 성장 표면과 옛 요약이 **같은 항목을 두고 다른 상태를 말하는** 것을 찾았다.
감사 질문 2·3번을 스스로 다시 훑다가, 같은 결함이 **세 번째 자리에도** 있는 것을 찾았다.

| 자리 | 무엇이라 말했나 | 실제 |
|---|---|---|
| `/overview` (옛 요약) | 반영 중 | 내려감 / 치워 둠 — 들지 않음 |
| `/memory` (옛 기억 목록) | `promoted` = 반영 중 | 치워 둔 것도 그대로 실려 있었다 |
| `/memory/state` (성장 표면) | 내려감 / 치워 둠 | 맞다 |

세 자리가 각자 `decayedAt` 을 재고 있었고, `archivedAt` 은 그중 한 곳만 알았다.
고친 방식은 **화면을 각각 손보는 것이 아니라 판정을 하나로 모은 것**이다 —
`물러남(entry)` 이 [`context-mesh.js`](../../../../src/kernel/l1-intent/context-mesh.js) 에 한 번 서고,
입장 게이트·옛 투영·옛 목록·성장 표면이 전부 그것을 읽는다. 각자 재는 한 언젠가 또 갈라진다.

돌연변이 2종이 이 계약을 지킨다: 게이트가 치움을 무시 / `/memory` 가 따로 잼.

## 1. S5-1~5 가 서로 모순 없이 이어지는가

조각마다 자기 시험이 있었지만 **이어 붙인 시험이 없었다.** 그게 위 결함을 아무도 못 본 이유다.
그래서 하나의 기억 위에서 제품 경로로 처음부터 끝까지 가는 봉인 시험을 세웠다:
[`test/tcell-s5-seal.test.js`](../../../../test/tcell-s5-seal.test.js)

```
보임 → 인용 → 정정 ×2 → tick 이 감쇠 → 입장 0 → 복원 → 입장 O
      → 붙듦 → 같은 근거가 또 쌓여도 감쇠 면제 → 치움 → 입장 0 → 되돌림 → 입장 O
```

대역은 **모델 하나뿐**이다(무엇을 인용하고 무엇을 고칠지는 모델의 판단이라 시험이 정한다).
턴 실행·기록·상관·감쇠 워커·표면·원장은 전부 제품 코드다. 감쇠도 `applyDecay` 를 직접 부르지
않고 **제품 tick**(`server.runtimeTick()`)으로 돌린다 — 직접 부르면 원장·워커 경계를 건너뛰어
실제로는 안 남는 영수증을 남는다고 믿게 된다(초안에서 실제로 그렇게 썼다가 잡았다).

## 2. shown / cited / correction / decay / restore / pin / archive 가 한 진실을 보는가

| 사실 | 유일한 자리 | 다른 곳에서 다시 재는가 |
|---|---|---|
| 지금 물러나 있는가 | `물러남` (context-mesh) | 아니오 — 게이트·투영·`/memory`·표면이 전부 이것을 읽는다 |
| 지금 영향 가능한가 | `isInfluenceEligible` | 아니오 |
| 입장 판정 | `admittedEntries` | `admittedContext` 는 이것을 문장으로 감싼 얇은 껍질 |
| 상관 문턱 | `CORRELATION_MIN` (correction) | 감쇠가 import 해서 쓴다. **판정 자리는 한 곳** |
| 상태 목록 | `상태목록` (surface) | 화면·API 가 그대로 쓴다 |

`session-store` 의 `archivedAt` 은 **대화 세션 보관**으로 이름만 같고 다른 것이다(기억과 무관).

## 3. 사용자 표면과 실제 admission 이 같은 상태를 보는가

봉인 시험 ⑤⑥ 단계가 매 전이마다 **같은 회차에서** 둘을 나란히 잰다:
`admittedContext`(모델이 실제로 본 것) 와 `/overview`·`/memory`·`/memory/state`(사용자가 본 것).

실제 화면 실측(제품 서버 `127.0.0.1:4185`, 실제 버튼 클릭):

| 항목 상태 | 옛 요약 | 성장 표면 | 다음 턴 모델 입력 |
|---|---|---|---|
| 치워 둠 | 반영 중 0 | `선호 · 치워 둠` | 안 들어감 |
| 내려감 | 반영 중 0 | `원리 · 내려감` | 안 들어감 |
| `되돌리기` 클릭 뒤 | 반영 중 O | `쓰이는 중` | **실제로 들어감**(`shownRefs` 확인) |

## 4. 카드·승인·클릭이 늘지 않았는가

봉인 시험 2번이 사슬을 다 돌린 뒤 확인 카드 수가 **그대로**임을 잰다.
감쇠는 승인을 요구하지 않는다(자동성이 의무다) — 대신 원장과 표면에 남는다.
성장 표면은 매턴 화면이 아니라 **설정에서 열 때만 보는 자리**다.

## 5. 잘못된 기억을 내리고 복원하는 경로가 실제 제품에서 되는가

라이브 관통 2회. S5-4 회차(실제 `gpt-5.1`, 시계 조작 0): 감쇠 전 입장 O → tick 이 내림
(`correction_correlation:2`) → **감쇠 후 입장 X** → 복원 → **복원 후 입장 O**.
S5-5 회차(제품 화면 실제 클릭): 위 3번 표.

## 6. pin 이 감쇠 면제로 실제 작동하는가

봉인 시험 ⑧: 붙든 뒤 **같은 근거를 다시 두 번 쌓고** tick 을 돌려도 내려가지 않는다.
"쌓이지 않아서 안 내려간 것"이 아니라 "쌓였는데도 안 내려간 것"을 잰다.
돌연변이 2종(`pin` 무시 / 붙듦 표식 소실)이 이 계약을 지킨다.

## 7. archive 가 실제 admission 에서 빠지는가 · 8. restore 가 실제로 되살리는가

봉인 시험 ⑨. 치움 직후 `admittedContext` 0, 상태 `archived`, 되돌린 직후 다시 입장.
lane 은 별도 상태 지도에 살고(`laneAllowed`), 치운 lane 은 승계 공급에서 빠진다.
`restore` 는 치운 것과 내려간 것 **둘 다** 받는다 — 사용자에게는 같은 "되돌리기"다.

## 9. 원장이 원문 없이 필요한 사실을 남기는가

봉인 시험 ⑩: `decayed`·`restored`·`pinned`·`archived` 가 전부 남고, 원장 전체를 문자열로
훑어 **문장 원문이 없음**을 확인한다(지문만). 원장 실패가 감쇠를 되돌리지는 않는다 —
상태가 행동의 진실이고, 원장은 그 뒤에 쓴다.

## 10. H 단계로 넘길 한계 — **정직하게**

이건 감사가 봐야 할 가장 중요한 칸이라고 본다. S 는 "구조가 섰다"이고 H 는 "사용자가 실제로
좋아졌다"이다. 지금 서 있는 것과 아직 없는 것을 섞지 않는다.

1. **원리는 라이브에서 아직 한 번도 승격되지 않았다.** H02 의 두 수치(재질문 0 · 과잉 일반화 0)는
   나왔지만, 재질문 0 을 만든 것은 S3 lane 승계다. "게이트가 옳게 막았다"와 "원리로 배워서
   좋아졌다"는 다른 사실이고, 뒤엣것은 아직 증거가 없다.
2. **`memory.cite` 는 보조 신호다.** 실측 호출률 3/9. 감쇠의 필수 근거로 쓰지 않는다.
   상관의 근거는 **정정의 지목 + 실제로 보인 것**이고 인용은 확신만 올린다.
3. **감쇠가 라이브에서 촉발된 회차는 1회다.** 첫 회차는 모델이 정정을 안 알려 상관이 0이라
   아무 일도 안 일어났다. 그건 실패가 아니라 **안 쌓인 것**이지만, 표본이 작다는 사실은 남는다.
4. **정정 판정은 모델에게 달려 있다.** 낱말 규칙을 두지 않은 것은 의도다(규칙이 조용히 틀리는
   것보다 아무 일도 안 하는 편이 낫다). 대신 모델이 안 알려 주면 감쇠는 영원히 안 돈다.
5. **성장 표면은 사용자 실사용 실측이 없다.** 버튼이 동작하는 것과 사용자가 그걸 찾아 쓰는
   것은 다르다. 이건 H 단계에서만 잴 수 있다.
6. **불통과한 묶음은 아직 닫히지 않았다**(round 잔여). 회차 3 을 다 쓰면 종단이다.

## 부록 B. 병렬 회귀 간헐 실패 — **우리 서버가 아닌 곳에서 답이 왔다** (감사 지시 처리)

`test/automation.test.js:174` 가 JSON 자리에서 `<!doctype …>` 을 받았다. 단독 26/26·직렬
1511/1511 이니 병렬에서만 나는 계열이 맞았다. **테스트 직렬화로 숨기거나 JSON 재시도로
넘기지 않았다.** 제품 코드도 건드리지 않았다.

### 먼저 좁힌 것

서버가 HTML 을 내는 자리는 `GET /` 와 `GET /index.html` **둘뿐**이다(그 외 미매칭은 404
text/plain). 그러니 POST 가 HTML 을 받는 것은 **우리 서버에서는 일어날 수 없다.**
답은 하나뿐이었다 — 그 응답은 우리 서버가 준 것이 아니다.

### 관측력 보강 (감사 지시 2)

`.json()` 을 `json응답()` 으로 바꿔, 실패하면 요청 URL·method·status·content-type·본문
앞 200자를 함께 던지게 했다. 예전에는 "JSON.parse 실패"만 남아 **어느 요청이 무엇을 받았는지
알 수 없었다.** 원인을 못 찾으면 남는 선택이 직렬화나 재시도뿐인데 둘 다 사실을 지우는 짓이다.

### 재현 (감사 지시 3) — 기전을 그대로 만들었다

병렬도 32 로 6회 돌려도 안 나서, 무차별 반복 대신 기전을 직접 세웠다:

```
A: http.createServer(...).listen(0, '127.0.0.1')   ← 남의 도구(SPA 폴백, 아무 경로에나 HTML)
B: http.createServer(...).listen(P)                ← 우리 시험 방식(주소 없음 = 와일드카드)

A = 127.0.0.1:56024 (먼저) · B = :::56024 (나중) — 둘 다 붙었다
POST http://127.0.0.1:56024/automation/cancel
  → 응답 주인: other-tool | content-type: text/html
  → 본문: <!doctype html>…
```

**macOS·BSD 는 SO_REUSEADDR 로 이 공존을 허용한다.** 그러면 우리 서버는 포트 P 가 제
것이라 믿지만, `127.0.0.1:P` 로 간 요청은 전부 더 구체적인 바인딩인 A 가 받는다.
증상이 감사가 본 것과 정확히 같다.

### 원인을 닫은 방식 (감사 지시 4·5)

시험 서버를 **루프백에 명시적으로** 붙인다 — `listen(0)` → `listen(0, '127.0.0.1')`.
87자리(55파일). 같은 실험을 다시 하면:

| | 결과 |
|---|---|
| 와일드카드(예전) | 바인딩 성공 → **남의 서버가 응답** (조용한 오답) |
| 루프백(지금) | `EADDRINUSE` 로 거부. 포트 0 이면 OS 가 **정말 빈 포트**를 준다 |

조용히 틀리던 것이 시끄럽게 멈추는 것으로 바뀌었다. 이 부류가 다시 들어오지 못하게
`audit:workspace` 에 검사를 넣었다 — 한 자리를 되돌려 실제로 무는 것을 확인했다.

수명주기·타이머도 같은 계열로 확인했다: 스케줄러 타이머는 `unref` 되어 프로세스를 잡지
않고 생성자는 아무것도 켜지 않는다(시험은 `fire()` 를 직접 부른다), 하트비트도 `unref`,
`close` 호출(164)이 `makeServer`(95)보다 많다.

### 남기는 관찰 두 가지

1. **어느 프로세스가 그때 그 포트를 쥐고 있었는지는 특정하지 못했다.** 사후에 알 수 있는
   사실이 아니다. 다만 기전은 재현했고 부류는 닫혔으며, 다시 나면 이제 `EADDRINUSE` 로
   드러난다 — 조용히 지나가지 않는다.
2. **제품 서버(`src/surface/server.js`)는 여전히 와일드카드로 붙는다.** 개인 AI OS 의 기억·
   API 가 같은 망의 다른 기기에 열린다는 뜻이다. 원인 없이 제품을 바꾸지 말라는 지시대로
   손대지 않았고, **판단이 필요한 사안으로 올린다.**
