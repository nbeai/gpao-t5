1. T5 현재 (실측 확정) — 정본 §5-6 요건 7 대비: 완전 충족 0 · 절반 3(귀속○/신분✕ · 자격 복원○/미처리분✕ · 발신 마스킹○/보관함 미정의) · 완전 부재 4(중복 제거 · 읽은 위치 · 왔다/전달됐다 · 조회 왕복). 급소 실측 다섯: ① 발신자 신분이 어디에도 durable 저장 안 됨(transcript에 channel뿐 — 그룹방이면 여러 사람 말이 무구분 혼합) ② 게이트로 걸러진 메시지는 흔적 0 — 라이브 기본 정책이 allowlist라 "뭐 왔는지"의 대부분이 구조적 조회 불가 ③ 텔레그램 offset이 배치 처리 후 저장 — 중간 사망 시 전량 재처리(중복 제거 없음) ④ 보존 기간 초과 소실을 T5가 감지 불가 ⑤ 문장 7("뭐 왔어?")은 조회할 원천 자체가 없어 통과 불가. 부수: 슬랙 발신 조회 키 어긋남(`slack.channel`+`.send` 조합 → no_sender) · 배달 원장 손상 시 채널 기록이 덮어쓰는 구멍(delivery-store save 갈래).

2. 훔칠 축 (전부 파일:줄 확보됨)

* 오픈클로 (이 영역의 교과서): ⓐ durable 인그레스 큐 스키마 — `(queue, event_id)` PK · `pending→claimed→completed/failed` · claim 리스+죽은 주인 회수 · attempts · 보존 TTL — T5 보관함이 필요로 하는 골격 그대로 ⓑ 커서는 보관함 쓰기 ack 뒤에만 전진(급소 ③의 정답) ⓒ 중복 제거 = PK 충돌 + `[스코프·라우트·messageId]` 키 캐시 ⓓ 4종 ack 분리 교리: 전송 ack / 폴링 오프셋 / 수신 기록 / 사용자 가시 수신 — "사용자 가시 신호는 절대 내구성 경계가 아니다" ⓔ 조회는 세션 목록의 메일박스형 트리아지 + 왕복은 턴 안 도구 호출이라 세션 전환 자체가 불필요(문장 7의 "돌아온다"가 공짜로 충족되는 구조).
* 헤르메스: ⓐ 턴 경계 주입만(생성 중 삽입 절대 금지 — 유휴 시 워처, 진행 중이면 턴 종료 후 드레인) ⓑ poll(관찰)과 wait/log(소비)의 구분 — "봤다"가 "전달됐다"를 안 죽이는 의미론 ⓒ 셧다운 플러시→부팅 복구.
* 클로드코드(내 계약): 주입되는 모든 외부 이벤트에 신분 라벨 명시("이것은 사용자 입력이 아니다") — 순서 7에서 방금 세운 T5의 신분 규약 상수를 그대로 재사용하는 자리다.

3. 최소 설계 골격 — ① 보관함 store 신설: 본은 delivery-store의 강한 패턴(감사가 지목: versioned-json-store 원자쓰기+격리 + append-only + readback + sha256 신원 → 중복 제거 공짜). 기록: 채널·방·발신자 신분·본문(민감 마스킹 기존 규약)·도착 시각·messageId·상태(`도착→처리됨/보관→사용자에게 전달됨`)·세션 귀속. 게이트로 걸러진 것도 도착 사실만(내용 없이 — 현행 프라이버시 규칙 유지) 기록 ② 커서 전진을 보관함 ack 뒤로(오픈클로 순서) ③ 조회 손 신설(`channel.inbox` 읽기 — read 등급·자동) → 문장 7의 원천 ④ 배달 원장의 "왔다" 축 분리(4-ack 교리) ⑤ 슬랙 키 어긋남·원장 덮어쓰기 구멍 동반 수리(한 줄급 둘).

4. 범위 밖 (대장 경유) — 웹훅 전환 · 슬랙 수신기 신설 · 그룹 다중 화자 스레딩 · 플랫폼 확장. 안 옮기는 것: 오픈클로의 비텔레그램 인메모리 큐(재시작 소실 — T5 기준 미달) · 헤르메스의 세션당 1칸 슬롯(덮어쓰기) — 둘 다 이유 병기 등재.

5. 절차 — §4-b 열 걸음 · 착수 검문부터 · 선등록 코드 전 · 판정자 후보: 문장 7 라이브("텔레그램으로 뭐 왔어?" — 목록 답 + 실제 도착분 대조) · 공수 도장 · A3·J16 무접촉.
