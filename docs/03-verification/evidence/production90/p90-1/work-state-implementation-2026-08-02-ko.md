# P90-1 장기 작업상태 결정적 구현 증거

- 날짜: 2026-08-02 (Asia/Seoul)
- 구현 기준: `f9a96d7`·`1a950c3` 이후 감사 보완(이 문서와 같은 커밋)
- 역할: Codex 5.6 Sol 겸임 구현·자체검증 + 별도 5.6 Sol 읽기 전용 적대 감사
- 판정: `DETERMINISTIC_IMPLEMENTATION_PASS / FORMAL_PRODUCT_SCORE_PENDING`

## 1. 사용자에게 달라지는 것

긴 프로젝트에서 확정한 것, 바꾼 것, 철회한 것, 아직 답이 필요한 것, 실제로 끝난 것을 별도 사건으로
남긴다. 새 대화와 재시작에서도 현재 사실만 이어지고, 다른 사용자·다른 프로젝트의 상태는 섞이지 않는다.
이 과정에 새 승인 카드가 생기지 않는다.

## 2. 단일 진실

- 정본은 `work-events.json`의 append-only `WorkEventLedger` 하나다.
- 현재 WorkState는 매 턴 사건에서 투영한다. 세션에 두 번째 현재 상태를 저장하지 않는다.
- 모델은 `work.state`로 후보와 사용자 원문을 제시할 뿐 내부 ref나 완료를 발급하지 못한다.
- 실행 완료는 같은 WorkRef의 `CompletionContractRef`와 실제 `delivered` ToolReceipt의 `ReceiptRef`가
  결합하고 검증을 통과할 때만 선다.
- 내용 있는 대화 답은 `chat_delivered`이며 프로젝트 전체 실행 완료를 가장하지 않는다.

## 3. 복구와 경계

- WorkRef·ReceiptRef·CompletionContractRef·subjectRef는 로컬 32바이트 키의 HMAC 서명으로 발급한다.
- 사건 hash chain이 손상되면 마지막 유효 checkpoint까지만 복구하고 저장소를 읽기 전용으로 둔다.
- 저장 키 손상은 자동 교체하지 않는다. JSON·hash 손상도 원본을 덮지 않는다.
- cross-session은 principalRef와 실제 WorkRef scope가 정확히 같은 경우만 허용한다.
- 새 대화는 모델에게 보여준 활성 합의·미정 원문을 정확히 지목해야 기존 WorkRef를 이어받는다.
- 내부 통제 후보, ref, digest, 원시 절대경로는 사용자 답과 모델 사실 뷰에 노출하지 않는다.
- 옛 세션의 workingState·activeGoal을 추측해 소급 사건으로 만들지 않는다.

## 5. 구현 중 발견해 함께 닫은 결함

1. ActiveWorkLane이 제품 영수증 `delivered`가 아니라 fixture 전용 `executed`를 성공으로 보던 불일치.
2. 매 턴 계산한 carryableWork를 세션 정본처럼 저장할 수 있던 두 번째 진실 위험.
3. 모델의 `work.state` 내부 후보가 transcript 저장 뒤 제거돼 기존 프로젝트 수정 턴에 남을 수 있던 순서 결함.
4. 작업상태 저장 실패의 내부 오류 원문이 사용자 응답 진단 칸에 노출될 수 있던 경계.
5. 서버가 실행 영수증을 본 뒤 `deliverableRefs`만으로 완료 계약을 만들어 현재 WorkRef에 붙이던
   사후 오결합. 완료 계약을 ActionPlan 확정 시점에 발급하고 영수증이 같은 WorkRef·계약을 직접
   상속하도록 바꿨다.
6. 한 `work.state` 후보의 여러 사건을 하나씩 저장해 중간 실패 때 앞 사건만 남던 부분 저장.
   전량 검증 뒤 파일 한 번 쓰기로 원자 커밋한다.
7. 한 응답의 여러 `work.state`와 도구 뒤 모델 호출의 후보가 마지막 값으로 덮이거나 유실되던 경로.
   호출 순서 병합·정확 중복 제거·6개 상한·질문/이어받기 충돌 전체 거부 계약으로 바꿨다.
8. UUID 세션 신분 안의 숫자 조각이 우연히 Luhn 검사를 통과하면 민감정보로 가려져 TurnRef가
   깨지던 간헐 결함. 카드 후보 판정에서 UUID만 제외하고, 같은 문장에 실제 카드번호가 있으면 계속
   차단하도록 반증과 돌연변이를 함께 고정했다.
9. 공개 영수증 발급 경로가 실행 뒤 만들어진 정상 모양 완료 계약도 서명할 수 있던 결함. 완료 계약을
   실행 전에 검증하고 도구 콜백 직후 영수증을 봉인하는 `runCompletionExecution` 경로만 완료
   ReceiptRef를 발급하도록 제한했다.
10. 승인 전후 `work.state`가 조기 노출되거나, 승인 클릭에서 원래 발화와 최초 WorkRef를 잃어
    입장·완료 사건이 서로 다른 작업을 가리키던 결함. 원래 발화·최초 WorkRef·후보 묶음을 pending에
    함께 봉인하고 승인 뒤 한 번만 입장시켰다.

읽기 전용 적대 감사는 1차에서 9번과 승인 묶음 결함을, 재감사에서 10번의 원문·WorkRef 유실을
실제 HTTP 제품 경로로 재현했다. 각 수정 뒤 최종 재감사는 완료 결합 7/7, 집중 제품 경로 22/22와
`completionReceipt.workRef === session.workRef`, `execution_completed` 존재를 대조해 `PASS`했다.

## 6. 주장 범위

이 증거의 30·60·100 수치는 **결정적 사건 시뮬레이션**이다. 실제 사용자 발화→모델 `work.state`
후보→입장 경로를 30·60·100턴 운용한 증거가 아니며, 라이브 모델의 장기 대화 성능도 증명하지 않는다.
실제 모델의 모든 도메인·모든 길이에서 절대 정확도를 증명한 것은 아니다. 공식 절대점수가 없는 90점 대신
기존 Hermes·OpenClaw 실측 이상의 관련 기능을 상대 종료 기준으로 사용한다. Production 90 후보판이나
전체 제품 완료는 선언하지 않는다.

## 7. 전역 보완 호출 회귀와 구조 재봉인

커밋 `22c2533` 격리 기준선은 **2,008/2,008**, 당시 미커밋 트리는 **2,025/2,043**이었다.
18건은 첫 응답이 `work.state`를 생략할 때 모든 턴에서 추가 모델 호출을 실행해 호출 순서 기반 제품
대본을 한 칸씩 소비한 파급이었다. 수정 뒤 기준선 2,008건이 모두 복구됐고 신규 8건까지
최종 **2,023/2,023**을 통과해 단일 원인을 확정했다.

재봉인 계약은 다음과 같다.

- 상태 검토는 실행과 실제 ToolReceipt 생성 뒤, 전달 후보 확정 뒤, 사용자 전달 전의 종단 정산 경계에 선다.
- 기존 WorkRef, 승인 재개, 또는 턴 종료 사실로 좁힌 최초 지속 작업 후보에서만 한 번 연다.
- `activeGoal`은 추정 라벨이라 단독 게이트나 사건 근거가 아니다.
- 첫 응답의 `work.state` 또는 `noChange` 보고가 있으면 정산 호출을 중복하지 않는다.
- 정산 입력은 사용자 원문, 전달 후보, 그 턴의 실제 영수증, Current Work Brief뿐이다.
- 정산 모델의 텍스트는 전달 후보를 바꾸지 못한다. 사용자에게 실제로 전달되지 않은 질문도 기록하지 않는다.
- 승인 재개는 클릭의 빈 원문이 아니라 pending에 봉인된 최초 요청 원문으로 검증한다.

전체 돌연변이 **268/268**에는 전역 게이트 복귀, 첫 모델 응답 경계 복귀, `activeGoal` 단독 개방,
정산 텍스트의 전달 후보 덮어쓰기와 모르는 승계 선택자 수용을 각각 주입하는 반대시험이 포함된다.

실제 모델 승계 probe와 문서 12턴은 모두 PASS했다. 12턴은 상태 변화 8/8, 누락 0, 철회값 부활 0,
새 대화 승계 1/1이다. 필요한 정산 추가 호출은 1회이며 7.200초였다. 기존 Hermes·OpenClaw 비교에서
둘 다 실패한 새 대화 완전 승계를 T5가 성공했고 재시작·철회는 동등 이상이므로 상태명은
`P90_1_COMPETITIVE_SEAL_PASS_WITH_RECORDED_LIMITS`다. 상세 비교는
`competitive-seal-2026-08-02-ko.md`를 따른다.
