# T5 문서 권위 리팩터 증거

- 날짜: 2026-07-30
- 상태: `document_authority_refactor_evidence`
- 범위: 제품·개발·감사·승계의 주요 정본과 역사 문서

## 1. 재현된 문제

같은 저장소에 다음 문장이 동시에 남아 새 세션이 서로 다른 현재를 읽었다.

- P-OP가 현재 유일한 우선순위다.
- P-OP-7이 진행 중이다.
- P-OP A~H와 P-OP-7은 완료됐다.
- T-cell이 현재 정본 구현이다.
- 모든 파일 변경과 기억·스킬 반영은 승인 대상이다.
- 최소 안전 바닥 밖만 확인하고 나머지는 자동으로 끝낸다.

문서가 많아서가 아니라 **현재 정본·역사·증거의 지위와 우선순위가 없었던 것**이 원인이었다.

## 2. 구조 변경

1. `GPAO-T5-DOCUMENT-AUTHORITY-MAP-2026-07-30-ko.md`를 단일 진입점으로 만들었다.
2. 모든 작업의 공통 필독을 다섯 문서로 줄이고 작업별 명세는 해당 시점에만 읽게 했다.
3. 현재 사실은 `GPAO-T5-CURRENT-SESSION-HANDOFF-ko.md` §0 한 곳만 갖게 했다.
4. 완료된 계획과 검증 문서에 역사 상태를 붙여 현재 차단을 결정하지 못하게 했다.
5. 승인·감사·자동화·T-cell 문서를 최소 안전 바닥 안 최대 자율성 기준으로 정렬했다.
6. 문서와 실제 코드·검사가 다른 곳은 통과로 꾸미지 않고 지정 정합화 간극으로 기록했다.
7. Hermes 실코드 재검토를 반영해 기억 쓰기 기본 자동성은 흡수하되, 비밀·민감·권한·전역화만 자동
   영향에서 제외하는 효과 기반 계약으로 구체화했다.

## 3. 제거한 실패 유도

- 구현·감사마다 모든 과거 계획서를 처음부터 읽게 하는 필독 과잉
- 감사자가 구현 해법까지 선점해 구현자의 사고를 축소하는 계약
- 없는 신규 기능에 “수정 전 실패” 증거를 요구하는 형식 검사
- P-OP 완료 뒤에도 현재 작업처럼 읽히는 상태 문구
- 명시적 저위험 자동화를 다시 승인 카드로 보내는 자동화 시나리오
- 문서보다 검사 수와 봉인 횟수가 품질을 대표하는 표현

## 4. 숨기지 않은 구현 간극

현재 Authority 코드와 일부 회귀검사는 P-OP 당시의 넓은 승인 경계를 유지한다.

- 모든 `write`·`promote_memory`·unknown kind의 A2 취급
- 읽기·목록 외 파일 작업의 광범위 승인
- 명시 요청과 추정 학습을 구분하지 않는 스킬 반영 확인

이는 최신 상위 원칙과 지정 정합화가 필요한 실제 코드 간극이다. 문서 리팩터가 제품 코드 수정을
가장하지 않으며, 인간 베타 전 효과·가역성·명시 지시·권한 확대 기준으로 재분류한다.

## 5. 기계적 재발 방지

- `npm run audit:docs`
- `test/document-authority-audit.test.js`
- 필수 상태·상위 원칙·금지된 낡은 문구를 검사한다.
- 반대시험은 완료된 P-OP를 다시 현재 유일 우선순위로 넣으면 실패한다.

자동 검사는 문서 의미 전체를 대신하지 않는다. 현재 Git·런타임·인간 사용 흐름은 통합 책임자가
인수인계 §0에서 독립 확인한다.

- 문서 감사 worktree에서만 변경했으며 Claude 본진 dirty 파일은 수정하지 않음

구조 감사는 현재 본진에 아래 네 생산 간극을 명시적으로 보고한다.

- foreground durable I/O
- published snapshot producer/consumer 부재
- background per-session lane 부재
- replay case/transition 생산 소비자 부재

이 네 항목은 문서 작업의 실패가 아니라 TG 구현이 닫아야 할 현재 코드 사실이다. 함수 선언이나 단위
검사만으로는 통과하지 않고 실제 생산 호출 양쪽이 연결돼야 한다.
