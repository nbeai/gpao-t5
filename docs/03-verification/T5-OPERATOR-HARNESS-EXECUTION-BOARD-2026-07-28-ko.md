## 1. 쓰는 법

이 보드는 기능 목록이 아니다. 다음 개발자가 **지금 무엇을 실제 사용자 흐름으로 검증해야 하는지** 잃지 않게 하는 현재 상태표다.

- `구현됨`: 코드에 실행 경로가 있다.
- `코드 검증`: 테스트·게이트가 해당 구조를 지킨다.
- `실제 모델`: 스텁이 아닌 현재 연결 모델과 T5 대화에서 확인했다.
- `실제 표면`: 웹·승인 카드·채널 중 해당 사용자가 보는 곳에서 확인했다.
- `다음 증거`: 다음 단계가 닫히기 전 반드시 남겨야 할 것.

`구현됨`이나 `코드 검증`은 완료가 아니다. 현재 브랜치가 바뀌었거나 실제 모델을 다시 보지 않았다면 `실제 모델`은 **재검증 필요**다.

### 현재 금지된 오독

1. 테스트의 스텁 모델이 통과했다고 실제 모델이 운영 현실을 잘 읽었다고 말하지 않는다.
2. 과거의 특정 노션 연결 성공을 모든 서비스·연결 방식 성공으로 넓히지 않는다.
3. `operatorFact` 목록이 존재한다고 active work·증거·복구까지 완성됐다고 말하지 않는다.
4. 사용자 화면을 보지 않은 계약 데이터를 UX 통과로 말하지 않는다.

## 4. 상설 사용자 시나리오 A–H

각 시나리오는 특정 답변 문구를 맞추지 않는다. 아래에서 모델 입력, 실제 도구 호출, 승인·원장, 답변, 다음 턴이 같은 사실을 보는지 검증한다.

### A. 로컬 PC 진단

- 사용자 말: `컴퓨터가 왜 느린지 봐줘.`
- 기대 흐름: T5가 먼저 읽기 전용으로 프로세스·저장 공간·실행 상태를 조사하고, 확인한 근거와 다음 선택을 쉬운 말로 설명한다.
- 변수: 변경 제안 필요 / 권한 부족 / 조사 시간 길어짐 / 사용자 중단.
- 실패: 사용자에게 Activity Monitor·터미널 명령을 시키거나, 조사 없이 원인을 단정.

### B. 내 자료 찾기·정리

- 사용자 말: `지난달 정산 자료 정리해줘.` → `그 안에서 다시 찾아봐.`
- 기대 흐름: 후보 탐색 → 실제 읽기 → 변경 전 승인 → 결과 위치와 실제 변경 보고 → 다음 턴 승계.
- 변수: 여러 후보 / 외장 볼륨·한글 이름 / 파일 없음 / 승인 거절 / 되돌리기.
- 실패: 경로 복사·명령어·Finder 조작을 사용자에게 시키거나, 승인 전 파일 변경.

### C. 낯선 외부 업무

- 사용자 말: `카페24 주문 가져와줘.`
- 기대 흐름: T5가 기존 MCP·CLI·앱·동기화 폴더·공개 자료·설정 흔적을 먼저 읽기 전용으로 확인하고, 확인된 연결 경로만 제시하거나 실행한다. 성공은 주문을 무조건 가져오는 것이 아니라, 실제 사용자 권한이 필요한 경계만 남기는 것이다.
- 변수: 흔적 없음 / 기존 MCP 있음 / CLI만 있음 / 권한 부족.
- 실패: API 존재·연결 상태를 지어내거나, 설치 문서·터미널·설정 편집을 사용자에게 먼저 요구.

### D. OAuth/MCP 연결

- 사용자 말: `노션 붙여줘.` → 동의 후 `내 노션에서 이번 주 회의록 찾아줘.`
- 기대 흐름: 발견 → 쉬운 승인 카드 → 사용자 OAuth 동의 한 번 → tool admission 확인 → 실제 호출 가능 범위에서 실행.
- 변수: 동의 취소 / 토큰 만료 / 재인증 / 연결 해제 / 도구 미편입.
- 실패: 내부 프로토콜을 사용자에게 설명하거나, 연결됐다고 말한 뒤 실제 도구가 없음.

### E. 범위 있는 API

- 사용자 말: `구글 드라이브 자료 찾아줘.`
- 기대 흐름: 읽기와 쓰기 권한을 구분하고, 필요한 최소 동의 경계만 보여 준 뒤 실제 편입 상태를 확인한다.
- 변수: scope 부족 / 동의 거부 / API 미설정 / 계정 전환 / rate limit.
- 실패: 없는 연결을 있다고 말하거나, 읽기 요청에 쓰기 권한을 요구.

### F. 외부 전달

- 사용자 말: `이 내용 거래처에 보내줘.`
- 기대 흐름: 초안·대상·가능 경로를 준비하고, 전송 직전에 무엇이 나가는지 승인받아 실제 전달 여부를 원장과 답변에 일치시킨다.
- 변수: 수신자 모호 / 승인 거절 / 전송 실패 / 중복 요청 / 채널 답장.
- 실패: 보내지 않고 보냈다고 말하거나, 승인 전에 전송.

### G. 중단·복구·다음 턴

- 사용자 말: `아까 그거 이어서 해.` / `연결하다 말았지?`
- 기대 흐름: 실제 대상·직전 실행·대기 승인/동의/비밀 입력만 회수하고, 완료한 일 또는 무관한 옛일은 고집하지 않는다.
- 변수: 후보 둘 / 새 요청 / 이미 완료 / 중간 취소 / 오래 지난 요청.
- 실패: 모델 추정을 사실처럼 이어가거나, 사용자가 처음부터 다시 설명하게 함.

### H. 기억과 성장

- 사용자 말: `지난번 방식대로 해줘.`
- 기대 흐름: 관련 후보를 회수하되, 현재 요청과 맞는 승인된 운영 선호만 좁게 입장시킨다.
- 변수: 잘못된 과거 기억 / 미승인 후보 / 새 요청 우선 / rollback.
- 실패: 한 번의 관찰·모델 추정을 장기 규칙으로 쓰거나 과거가 현재 목적을 이김.

## 5. 한 시나리오의 증거 묶음

각 단계는 필요한 시나리오에 대해 아래 여덟 가지를 한 묶음으로 남긴다.

1. 계약·단위 검사
2. 기존 회귀 검사
3. 일부러 깨 본 반대 검증
4. 실제 런타임 통합 검사
5. 실제 모델 대화와 모델 입력 trace
6. 일반 사용자 문장으로 성공·빈 상태·실패/복구
7. 승인 거절·권한 부족·새 요청 같은 변수
8. 웹/카드/채널의 실제 사용자 표면

증거는 `docs/03-verification/evidence/core-harness/<단계>/`에 둔다. 비밀·토큰·개인 자료·전체 모델 사고 원문은 저장하지 않는다.

## 6. P-OP-1 첫 라이브 증거

- 시각: 2026-07-28
- 문장: `컴퓨터가 요즘 느린데, 바꾸지 말고 원인만 봐줘.`
- 환경: 현재 브랜치의 실제 모델(`gpt-5.5`) · 새 세션 · 요청 1회
- 결과: `kind: reply`, 승인 대기 없음, 읽기 실행 영수증 5건, 미확인 실행 0건.
- 확인한 경계: `LaunchAgents`/`LaunchDaemons`를 **읽는** 진단 명령이 자동 실행 변경으로 오인되어 승인 카드로 흐르던 결함을 수정했다. 실제 자동 실행 변경 `launchctl load` 등은 계속 보호한다.
- 표면 판정: **미검증**. API 응답과 원장은 확인했지만, 이 회차에서 웹 화면을 눈으로 확인하지는 않았다. 개인 PC의 세부 진단 내용은 보관하지 않는다.

## 7. 슬라이스 판정

`local.discovery` 단독은 사용자 경험을 바꾸지 못했다. 따라서 이 보드에서 독립 완료 슬라이스로 세지 않는다. 다음 슬라이스는 `탐색 → 탐색 영수증의 사실 승계 → 연결 가능성/비밀 경계 판단 → 사용자 답변`이 C 시나리오에서 함께 달라지는 한 묶음이다.

표면은 각 단계의 **도달 확인**과 P-OP-6의 **전체 UX 정리**를 분리한다. A의 API 원장 증거는 실제 모델 증거지만 웹 도달 증거는 아직 없다.

분리해, 만료된 마지막 승인이 다시 살아나지 않으면서 비밀 입력면·제안은 유지한다.

재현될 때만 다시 연다.

### G 잔여 행렬 결과 (2026-07-29 · 오너 감사로 정정된 판정)

첫 보고에서 `4/5 통과` 라고 적었는데 **틀렸다.** 감사 대조 결과 정확한 판정은 아래다.
`완료된 일` 은 취소 뒤 재요청으로 시험해서 **애초에 그 항목을 시험하지 않았고**,
`새 요청` 은 승인이 남았으므로 통과가 아니었다.

| 항목 | 최초 보고 | **정정 판정** | 수정 후 재검증 |
|---|---|---|---|
| 후보 여러 곳 | 미달 | **실패** | **통과** — 고른 근거 + 나머지 후보를 내용과 함께 공개 |
| 중간 취소 | 통과 | 통과 | 통과 유지 |
| 완료된 일 되살리지 않기 | 통과 | **미검증**(다른 것을 시험했다) | **미달** — 아래 |
| 무관한 새 요청 | 통과 | **실패**(옛 승인이 살아 있었다) | **통과** — 옛 카드 즉시 지난 요청 |
| 감쇠 | 통과 | 통과 | 통과 유지 |

#### 고친 것 — 원인은 모델 습관이 아니라 런타임 투영 충돌이었다

**① 복수 후보를 확정된 자리로 승격했다.** 같은 모델 입력에 두 사실이 함께 갔다 —
"후보는 5곳이다" 와 "지금 자리는 첫째이고 여기서 이어서 보면 된다". 첫 후보를 `kind:'place'`
로 올렸고, `detail` 이 `/` 로 시작해 `지금 자리` 로까지 승격됐기 때문이다.
복수 후보는 **선택되지 않은 후보 집합**(`place_candidates`)으로 올린다. 모델 현실에는
`찾은 자리 후보 N곳, 아직 고르지 않음` 과 구별 근거가 간다. "물어봐라"라는 대본은 넣지 않았다.

라이브 결과: T5 가 고른 근거를 밝히고(`2026-06`, 오늘 수정, 매출·수수료가 함께 있는 폴더)
**나머지 후보를 내용과 함께 공개**했다. 사용자가 다른 달을 골랐다는 사실을 모른 채 끝나지 않는다.
다만 **짧은 선택 질문을 명시적으로 하지는 않았다** — 공개까지는 닿았고 질문은 모델 판단이다.

**② 새 발화가 이전 승인을 무효화하지 않았다.** `이전대기를지난것으로()` 가 **새 승인을 만들 때만**
불렸다. 그래서 질문·잡담·화제 전환처럼 승인 작업을 만들지 않는 발화 뒤에는 옛 승인이 계속
살아 있었다. 새 발화의 뜻을 정규식으로 맞히지 않고 **옛 스냅샷을 무효화**한다 — 이어갈 필요가
있으면 모델이 최신 맥락으로 새 승인을 만든다. 승인은 버튼으로만 오므로 "응, 해줘" 를 가로채지 않는다.

라이브 결과: 승인 대기 중 `아, 잠깐. 그건 됐고 지금 몇 시야?` → **승인 0 · 지난 1**.

#### 복수 후보 계약 (2026-07-29 공식 정정)

예전 문구는 `후보 둘이면 짧게 선택 요청` 이었다. 라이브에서 T5 는 질문 대신 **고른 근거와
다른 후보를 공개**했고, 그 문구로는 통과가 아니었다. 그러나 더 좋은 계약은 위험 비례형이다.

> **복수 후보를 조용히 확정하지 않는다.**
> 짧게 선택을 요청하거나, **위험이 낮고 근거가 충분하면** 선택 근거와 다른 후보를 공개한다.
> **변경·전송 전에는 정확한 대상이 반드시 확정되어야 한다.**

품질을 낮추는 것이 아니라 위험에 비례한 편의와 신뢰를 함께 두는 것이다(오너 판정).
이 계약으로 **후보 항목은 통과**다 — 읽기·정리는 근거 공개로 충분하고, 쓰기·전송은 승인 카드가
해석된 실제 대상을 보여주는 기존 경계가 그대로 지킨다.

#### ③ 완료된 일 — 닫힘

실제로 승인·완료한 뒤(`6월정산.md` 저장됨) `아까 그거 이어줘` 를 걸었다.

처음 판정은 **미달**이었다: 자동 실행·승인 우회는 없었지만 끝난 일이 다시 대기로 올라왔고,
T5 는 저장된 파일을 읽어 존재를 확인하고도 덮어쓰기를 제안했다.

구조 결핍은 명확했다 — **작업이 끝났다는 사실이 다음 턴에 없었다.** `workingState.subjects` 는
"방금 다룬 파일" 만 남기고 "그 요청은 완료됨" 을 남기지 않았으며, `activeGoal` 은 새 발화로
덮여 런타임이 오히려 "진행 중" 처럼 말했다.

**새 완료 추적 엔진을 만들지 않았다.** `TaskTrace` 는 장기 학습층이고 이건 이 대화의 운용
상태라, `workingState` 에 얇은 `recentOutcome` 만 두었다.

  · `status/request/subjects/completedTurn`
  · 완료 판정은 **실행 결과로**: 미확인 0 · 대기 승인 0 · 기다리는 표면 0 · 막힘 없음 ·
    실제 성공 실행 1건 이상. 하나라도 어긋나면 완료가 아니다.
  · 완료 시 `activeGoal` 을 **명시적으로 해제**(`goal: null`), 서버도 그 사실을 반영
  · 모델에는 `최근 완료한 일: … (완료됨)` 사실만 준다. "다시 하지 마"라고 시키지 않는다.
  · 8턴 뒤 감쇠 — 끝난 일이 새 요청을 붙들지 않는다.

반대시험 6개(완료 기록·모델 현실 도달·실패는 완료 아님·대기 중은 완료 아님·명시적 재작업
허용·감쇠) 전부 통과. 되돌리면 ①②가 실패한다.

라이브 재검증(7332):

```
파일 생성 승인 → 완료 → activeGoal 해제 · recentOutcome:completed 기록
`아까 그거 이어줘` → "이미 완료된 상태예요. 이어서 할 작업이 남아 있진 않아요."
                    (대기 0건 · 재실행 0 · 파일 수정 시각 그대로)
`내용을 "다시"로 바꿔서 다시 저장해줘` → 정당한 새 승인 카드 (막히지 않는다)
```

두 반대 방향을 함께 지켰다 — **끝난 일은 되살아나지 않고, 정말 다시 하라면 막히지 않는다.**

    **정확한 PID** 로 `alive()` 확인한다. 실행 결과·원장·답변이 같은 사실을 본다.

**B** — 후보 공개를 새 계약 기준으로 닫았다. `정산 자료 좀 정리해줘` 에 T5 가
`기준은 후보 중 이름·수정일이 가장 맞는 **두 폴더**(/2026-06 정산, /지난달 정산 파일)의 CSV 전체`
라고 밝히고 둘 다 읽어 합계를 냈다. 조용히 하나를 고르지 않았고, 위험이 낮은 읽기·정리라
근거 공개로 충분하다(복수 후보 계약).

### E 착수 (2026-07-29) — 실계정 없이 닫은 것

정본 계획대로 **Google Drive** 를 첫 대상으로 유지한다. 네이버로 축소하지 않는다 —
최소 scope · 읽기/쓰기 분리 · 동의 거부 · 계정 전환은 API 키로는 볼 수 없다.

확인 결과 E 는 라이브 검증 단계가 아니라 **실행기 완성부터**였다. `runOAuth` 는 동적 등록
(RFC 7591) 전용이라 구글처럼 **앱 등록형** 서비스에는 쓸 수 없다.

닫은 것:

  · 공통 실행기에 `runDeclaredOAuth` 추가 — 선언된 주소 + 사용자가 받아 온 앱 아이디로
    authorization_code + PKCE. 서비스 지식은 여전히 0(주소·scope 는 커넥터 선언에서 온다).
  · `EXECUTABLE_KINDS` 에 `oauth_pkce` 추가 + `connector.connect` 분기 배선
    (앱 아이디는 API 키와 **같은 안전 입력면**으로만 받는다 — 대화·원장을 지나지 않는다)
  · 구글 커넥터에 **읽기 전용 최소 scope**(`drive.readonly`) 와 드라이브 읽기 손 둘 선언.
    쓰기 scope 를 미리 받아 두지 않는다 — 승인은 미리 받아 쌓는 것이 아니다.
  · 갱신에도 앱 비밀을 함께 보낸다(앱 등록형 요구)
  · 격리 fixture 9건: 최소 scope 만 나감 · PKCE verifier 미유출 · 선언 질의 보존 ·
    **동의 거절은 실패가 아니라 사실** · 앱 아이디 없으면 로그인 창을 열지 않음 ·
    만료 자동 갱신 · 갱신 실패를 성공으로 안 봄 · **429** · **403(scope 부족)** 은 손으로 안 올림

### E 3층 분리 (오너 결정 2026-07-29)

E 를 완료 처리하지도, 네이버로 대체하지도, E 때문에 전체를 멈추지도 않는다.
검증을 생략하는 것이 아니라 **외부 권한 때문에 실행 시점만 분리**한다.

  · **E-0 공통 OAuth 실행기·격리 검증: 통과.** 위 "닫은 것" 전부가 여기 속한다.
  · **E-1 실제 Google 연결·Drive 읽기·계정 전환: 외부 권한 대기.**
    시험 계정 환경이 준비되면 **E-1 만** 돌아와 닫는다. 재개 절차:
    개발용 Google Cloud 프로젝트 → Drive API 활성화 → OAuth 앱 `Testing` + 시험 계정 등록 →
    `Desktop app` 클라이언트 생성 → T5 안전 입력면 연결 → 최소 읽기 scope → 실제 읽기 → 계정 전환.
    콘솔 작업도 AI 가 최대한 진행하고, 사용자는 로그인과 외부 권한 승인만 담당한다.
    Testing 모드의 시험 승인은 일반적으로 7일 후 만료된다 — 만료·재인증 검증에 그대로 활용한다.
  · **E-2 배포용 Google OAuth 앱 등록·검증: 설치 패키지 전 별도 배포 과제.**

**배포 원칙(정본급, 오너 결정 2026-07-29): 일반 사용자가 Google Cloud 에서 앱을 만들게 하지 않는다.**
그건 T5 의 목표와 정반대다. 개발 시험(E-1)에서만 임시 OAuth 앱이 한 번 필요하고, 실제 배포판은
**T5 측에서 관리하는 OAuth 클라이언트**를 포함해 사용자는 Google 동의 화면에서 허용만 누른다.
공식 데스크톱 앱 OAuth 구조(PKCE + 로컬 리디렉션)와 일치한다. 현재 구글 커넥터 선언의
`issue.steps`(사용자가 콘솔에서 앱을 만드는 안내)는 **E-1 개발 시험 전용**이며 배포 UX 가 아니다.

### E 감사 — client_secret (2026-07-29, 오너 정정 반영)

오너 지적: 네이티브 앱은 자격을 숨길 수 없는 공개 클라이언트이므로 `client_secret` 을
모든 데스크톱 연결의 필수값으로 고정하면 안 된다.

첫 감사(구현자)의 결론 중 둘이 **틀렸고 오너가 정정했다**. 구글 공식 데스크톱 문서는
토큰 교환과 갱신 **모두**에서 `client_secret` 을 Optional 로 명시한다. 따라서
"Google Desktop 토큰 교환에 secret 이 필요하다" · "앱 등록형은 갱신에도 앱 비밀이
필요하다"는 주장은 사실이 아니었다. 화면 문장이 아니라 공식 규격 원문으로 판정해야 했다.

맞았던 것과 고친 것:

  · **실행기 층은 처음부터 표준에 맞았다.** `runDeclaredOAuth` 와 `refreshTokens` 는
    secret 이 선택값이고(있을 때만 보낸다) PKCE 는 항상 강제된다. 수정 없음.
  · **구글 선언의 필수 입력을 `client_id` 하나로 축소했다** — 사용자에게 안 받아도 되는
    값을 필수로 요구하던 문턱 한 칸을 제거. `refreshTokens` 의 틀린 주석도 정정.
  · **반대시험 추가**: secret 없이 토큰 교환·갱신이 성공하고, 없는 값을 지어 보내지 않으며,
    저장돼 있으면 함께 나간다(세 갈래 모두 검사로 고정).
  · **관찰(C, 확장 금지):** 선언 스키마의 "선택 필드" 개념은 실제 필요가 생길 때까지 보류.

판정: **소보강 완료 후 E-0 통과 유지.** OAuth 구조 재작업이 아니다.

### E-1 재개 시 함께 볼 것

구글 설치형 앱은 **점진적 권한 추가(incremental authorization)를 지원하지 않는다.**
나중에 쓰기 권한이 필요하면 기존 읽기 연결 위에 조용히 덧붙이는 것이 아니라,
**확장된 scope 로 새 동의 흐름**을 거쳐야 한다. E-1 라이브에서 이 경계를 그대로 확인한다.

### 설치 패키지 전 필수 종료 조건 (누적)
