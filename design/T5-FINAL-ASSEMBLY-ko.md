### 그다음 단위 — **모델 입력을 날것으로** (기계 확인 2026-08-11)

T5 는 사용자에게 친절하려고 **모델에게 가는 것까지 접었다.** 두 줄이다.

```js
task-context.js:880   summary: r.userSafeSummary        // 사용자용 문장을 모델에게 먹인다
task-context.js:887   data: compactResult(r.result, 1200)  // 결과를 ~1,200자 한국어 산문으로
task-context.js:891   ...(실패 ? { failureState } : { data })  // **실패하면 내용이 통째로 안 간다**
```

세 번째가 결정적이다. 주석의 이유(*"실패한 결과는 확인된 값이 아니니 사실처럼 싣지 않는다"*)는
타당하지만 **진단 정보까지 함께 버린다.** 그래서 모델은 왜 막혔는지 모른 채 다음 수를 정한다.

```
설계 규칙   **모델에게는 날것, 사용자에게는 사람 말. 두 벌을 만든다.**
           지금은 한 벌을 둘 다에게 쓴다 — 그것이 「됐는지 모르겠어요」·「창이 여러 개라
           모르겠어요」·F-77(한계가 산문으로 흩어짐)·L1 locate×7 의 공통 뿌리다
사용자 친화  **출력 층에서만** 한다. 사장님은 exit code 를 못 읽지만, 그건 마지막에 원장에서
           만들어 내는 것이지 모델 입력을 접어서 만드는 것이 아니다
안 버릴 것   실패 내용을 **사실로 승격하지 않는다**는 계약은 유지한다 —
           「확인 안 됨」 표식을 달아서 **주기는 준다**
```

```

승인 등급(결정)    저장·활성은 안 묻는다(정의는 세상에 영향 0). **행동에서 묻는다**
                 단 넷을 함께: 출처가 오너 대화일 것 · replay 통과 · 즉시 가시성 · 되돌리기 한 번
```

## 11. 일하는 방식

```
· 문서로 상태를 단정하지 않는다. 돌려서 정한다
· 고치면 그 자리에서 러너를 돌린다. 좋아졌는지 말로 하지 않는다
· 새 계획서를 만들지 않는다. 이 문서에 줄을 고친다
· 안 잰 것을 「완료」로 넘기지 않는다. 못 잰 것은 **「계측 불가 · 사유」**로 적는다
· 막히면 멈추고 오너에게 올린다. 조용히 넘어가지 않는다
```

**오늘 하루를 태운 셋**: 새 계획서 만들기 · 문서로 상태 단정하기 · 안 돌려보고 원인 적기.
