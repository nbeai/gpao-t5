# T5 2.0-C-0 · Capability Resolution Flow (+ 개인 도구/스킬 초안)

작성: 2026-07-25 · 상태: 구현·라이브 검증 완료, 깊은 감사 대기
정본: 헌법 최상위 원칙(b67e125 — 사용자를 덜 헤매게), Codex 전략 브리핑(오너 승인), 2.0 UX §6.8.

## 왜 이 슬라이스인가

T5는 부족한 능력 신호를 제각기 만들어 왔다: `connectionNeeded`(커넥터, 2.0-B) · `toolCandidate`(도구,
2.0-C) · send `clarify`(대상, P6-7) · `approval`(권한). Codex 지적대로, 이걸 **하나의 정식 패킷**으로 묶어야
"막힘"이 흩어진 카드가 아니라 **하나의 목적 달성 경로**가 된다. 최상위 기준: 사용자를 덜 헤매게.

방향: 2.0-C를 "개인 도구 등록"으로 좁히지 않고, 먼저 **Capability Resolution Flow**를 세운다. 개인 도구·
스킬은 그 안의 `capabilityType`이다. (오너 채택: 통합 패킷+리졸버, **비파괴 우선**.)

## CapabilityResolution 패킷 (`l2-plan/capability-resolution.js`)

`{ requestText, desiredOutcome, missingCapability, capabilityType, currentStatus, reason, nextAction,
requiresApproval, testPlan, resumeContext, alternatives, ref }`
- `capabilityType`: tool | skill | connector | profile | target | permission
- `nextAction`: connect | install | register | test | clarify | approve | alternative
- `resumeContext`: **원래 작업 복귀 경로**(원문 보존, 비우지 않는다).
- `resolveCapability(signals)`: 턴의 부족 신호를 첫 하나로 분류(우선순위 permission > connector > tool >
  target). **비파괴**: 기존 connectionNeeded/toolCandidate/send-clarify/approval을 근거로 재사용한다.

## 턴 통합

턴은 네 상황에서 `capabilityResolution`을 함께 낸다: 승인(permission) · 대상 확인(target/clarify) ·
연결 필요(connector) · 도구 준비(tool). UI는 **하나의 통합 카드**로 연결/도구를 렌더(2.0-B+2.0-C 카드 통합).
승인·대상확인은 기존 approval·clarify 흐름이 담당하되 패킷의 분류도 함께 싣는다.

## 개인 도구 (2.0-C-1, capabilityType:tool)

- `personal-tool.js`: `definePersonalTool`(등록=테스트 전, executable false) · `runProbe`(필수 설정 검사 —
  실제 외부 실행/OAuth는 후속) · `applyProbe` · `isPersonalExecutable`(passed만) · `detectPersonalToolRequest`.
- `personal-tools-store.js`(파일). 서버: `POST /personal-tools`(등록) · `POST /personal-tools/:id/test`
  (통과→executable / 실패→이유·다음 안전 행동). `GET /toolbox`가 개인 도구를 "개인용/테스트 전/실행 불가"로.
- **등록됨 ≠ 실행 가능**: 테스트 통과 전에는 사용 가능처럼 보이지 않는다. 죽은 버튼 없음(설정 확인은 실제 동작).

## 스킬 초안 (2.0-C-2, capabilityType:skill — 계약만)

- `skill-descriptor.js`: `defineSkill`(말귀·절차·맥락·결과물 형식·replay 다섯 축) · `detectSkillRequest` ·
  `isSkillReady`(replay 통과만). 도구 ≠ 스킬. 추천은 설치·승격 아님(확인·replay 전 영향 0). UI·store·실행은 후속.

## 감사 기준 대응

UI=runtime 상태 · 등록됨/실행/승인 분리 · 테스트 통과 전 실행 불가 · 실패 시 이유+다음 안전 행동 ·
복귀 경로(resumeContext) 유지 · 죽은 버튼 없음 · 사용자 언어(기술 용어 미노출 테스트로 강제).

## 라이브 검증(브라우저)

미연결 슬랙 + 도구 준비 요청 → **하나의 통합 카드 경로**로 각각 "연결이 필요해요" / "도구 준비가 필요해요".
"개인 도구 준비" → 도구함 포커스 → 테스트 전 → 설정 확인 → **확인 실패 + 이유·다음 안전 행동**
("path 필요… 채우면 다시 테스트"). 죽은 버튼 없음.
