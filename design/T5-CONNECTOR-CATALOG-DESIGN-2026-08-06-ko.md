# 커넥터 카탈로그 — 설계

- 날짜: 2026-08-06 · 오너 제안(2026-08-05)에서 나옴
- 개정: 2026-08-06 · **§7.2 약관 게이트 — 오너 결정으로 층에서 쥐는 것으로 옮겼다**
- 한 줄: **사장님이 혼자서는 못 붙이는 것을, T5 가 옆에서 같이 걸어 붙여준다.**
- 이 문서는 **카탈로그의 설계**다. 카탈로그 자체는 저장소 밖에 산다(§9).

---

## 0. 무엇이고 무엇이 아닌가

```
이다      어디에 · 무엇을 · 어떻게 붙이는지에 대한 목록. 데이터다
아니다    코드 · 도구 · 손. 손은 하나도 안 는다 (connector.declare 가 이미 있다)
```

**손이 안 느는 것이 이 설계의 전제다.** 항목 100개를 등록해도 모델이 보는 스키마는
그대로다 — 불변식 B(좁은 허리 넓은 가장자리)의 "가장자리"가 여기다.

> 2026-08-05 에 개발팀이 접은 **도구 스키마 지연공개 카탈로그**와 다른 물건이다.
> 그건 "손을 언제 보여줄까"였고, 이건 "어디에 어떻게 붙을까"다.

## 1. 왜 이게 §0 과 맞나

§0 은 *"AI 의 존재 이유는 인간 사용자의 목적 달성"* 이다.
그리고 [[사용자비용-0번-1번-2번]] 이 방법을 고르는 규칙이다.

**카탈로그의 실제 일은 2번을 1번으로 끌어내리는 것이다.**

```
사장님 혼자      키 발급 20분 · 중간에 포기      ← 에너지 비용이 제일 크다
T5 가 같이 걸음   화면 보며 5분 · 한 번이면 끝    ← 2번이 1번에 가까워진다
```

카탈로그가 **절차를 알고**, CU 가 **그 절차를 걷는다.** 둘이 따로면 반쪽이다.

## 2. 한 항목의 모양

```yaml
id: naver-searchad
이름: 네이버 검색광고
사장님말:                          # 이 항목으로 오는 실제 문장
  - 키워드 검색량 좀 봐줘
  - 우리 가게 뭐라고 검색해서 들어와?
  - 광고 뭐가 싸?
층: 2                              # 0 / 1 / 2 — 사용자 비용 등급
비용:
  에너지: 중                        # 헤매기 쉬운가 (제일 비싼 축)
  시간: 15분
  돈: 0
얻는것: 검색량 · 클릭률 · 연관키워드
필요한값:                          # **화면에 써 있는 그 단어로** (§3.1)
  - { 화면문구: 고객 ID,        받는곳: CUSTOMER_ID }
  - { 화면문구: 액세스라이선스,  받는곳: API_KEY }
  - { 화면문구: 비밀키,         받는곳: SECRET_KEY }
자리: https://searchad.naver.com
가는길:                            # 성기게 (§3) · 번호가 곧 "지금 어디"다 (§3.2)
  - 로그인한다
  - 도구 > API 사용관리 로 간다
  - 네이버 검색광고 API 서비스 신청
  - 세 값을 복사한다
끊김:  없음                        # 폰 인증이 끼면 여기에 적는다 (§3.3)
확인:                              # 이게 없으면 항목이 아니다 (§4)
  방법: 받은 값으로 /keywordstool 을 한 번 부른다
  성공: 응답에 keywordList 가 있다
함정:
  - 광고계정이 없으면 먼저 만들어야 한다(사업자 정보 필요)
  - 검색광고 계정과 네이버 아이디는 다르다
약관: { 쥐는것: 저장된키, 확인일: 2026-08-05, 판정: 허용, 근거: "제3자 도구 사용 제한 조항 없음" }
마지막통과: 2026-08-05
상태: 통과                         # 통과 | 확인필요 | 미확인 | 막힘
```

## 3. **절차를 성기게 적는다** — 세밀할수록 빨리 죽는다

```
✗  "우측 상단 파란 버튼 클릭 → 드롭다운 3번째 → #api-key 입력란"
✓  "도구 > API 사용관리 로 간다"
```

**세밀하게 적으면 화면이 한 번 바뀔 때 통째로 죽는다.** 그리고 자주 바뀐다.

성기게 적으면 **모델이 화면을 보고 채운다.** 그게 모델이 잘하는 일이다 —
[[모델은-같은-답을-낼-수-없다-유사하면-같은-답이다]] 전제 그대로, 화면을 읽고 판단하는 것은
모델의 몫이지 우리가 미리 적을 것이 아니다.

**우리가 적는 것은 모델이 화면만 봐서는 모르는 넷이다:**

```
어디로 가는가     자리(URL) — 검색으로 찾으면 광고·유사 페이지에 빠진다
무엇을 받는가     필요한값의 이름 — 화면에 "액세스라이선스"라 써 있으면 못 알아본다
다 됐는지         확인 방법 — 화면만 보고는 "받았다"와 "된다"를 못 가른다
함정             한 번 당해 봐야 아는 것
```

### 3.1 **사장님이 화면에서 보는 그 단어를 쓴다**

Plaid Link 가 은행 연결을 쉽게 만든 첫 번째 이유다 —
**입력 라벨을 그 은행 사이트에 써 있는 문구와 정확히 같게 맞춘다.**

```
✗  "API_KEY 를 입력하세요"        화면 어디에도 그런 말이 없다. 사장님이 멈춘다
✓  "액세스라이선스 를 복사해서"    화면에 그렇게 써 있다. 눈이 바로 찾는다
```

`필요한값` 을 코드 이름으로 적으면 카탈로그가 **개발자용**이 된다.
**화면문구가 사장님용이고, 받는곳이 기계용이다. 둘 다 적는다.**

### 3.2 **지금 어디쯤인지 항상 보인다**

`가는길` 의 번호가 곧 진행 표시다.

```
연결 중 · 4단계 중 2단계
✔ 로그인했어요
▶ 도구 > API 사용관리 로 가는 중
· 서비스 신청
· 값 세 개 받기
```

Plaid 가 `onEvent` 로 이탈 지점을 재는 것과 같은 자리인데,
**우리는 그걸 개발자가 아니라 사장님에게 먼저 보여준다.**

### 3.3 **끊김을 전제로 설계한다** — 한국에서 제일 다른 지점

한국 금융·공공은 **인증이 폰으로 간다.** 간편인증 · PASS · 문자.
**T5 가 대신 못 한다**(헌장 ① 비밀값). 사장님이 폰을 들어야 하고, 그 순간 흐름이 끊긴다.

미국 서비스 설계는 이 끊김이 없다. 그래서 그대로 베끼면 안 된다.

```
끊김이 있는 항목    어디서 끊기는지 미리 적는다
끊긴 뒤            "폰 인증 하고 오세요. 여기서 기다릴게요"
돌아오면           처음이 아니라 그 단계부터
```

**이어붙이기(resume)가 없으면 사장님은 두 번째 시도에서 포기한다.**
연결 진행 상태는 턴이 아니라 **세션 밖에** 남아야 한다.

### 3.4 "그 값을 우리는 안 본다"를 말한다

Plaid 가 명시적으로 권하는 문구다 — *"우리는 당신의 자격증명에 접근하지 않는다."*
사장님이 제일 겁내는 순간이 값을 넘기는 순간이다.

T5 는 실제로 그렇다(§7). **그러면 말해야 한다.** 사실인데 말 안 하면 없는 것과 같다.

## 4. **확인이 없으면 항목이 아니다**

CU 에서 배운 A14 가 그대로 온다 — **눌렀다 ≠ 됐다.**

```
키를 받았다        ≠  연결됐다
화면에 값이 떴다    ≠  그 값이 유효하다
```

그래서 **모든 항목은 실제로 한 번 불러 본다.** OpenClaw 의 live test 패턴이다 —
준비됐다고 선언하기 전에 가장 싼 읽기 호출을 실제로 한 번 한다.

**확인을 못 적는 항목은 카탈로그에 안 넣는다.** 넣으면 "붙었다"고 말해 놓고
사장님이 나중에 안 되는 걸 발견한다. 그게 제일 나쁘다.

## 5. **자가 갱신** — 카탈로그가 사용에서 배운다

이게 이 설계의 심장이다. **손으로 관리하는 목록은 반드시 썩는다.**

T5 가 항목을 걸을 때마다 결과를 되돌린다:

```
성공        마지막통과 를 오늘로
확인 실패    상태: 확인필요  +  몇 단계에서 막혔는지
자리 없음    상태: 막힘      +  받은 상태 코드
```

그러면 **사용자 수만큼의 눈**이 생긴다. 네이버가 화면을 바꾸면 며칠 안에 드러난다.

**되돌아오는 것에 개인정보는 없다.** 올라가는 것은 셋뿐이다 —
`항목 id` · `몇 단계에서` · `무엇이 달랐나(우리가 미리 정한 어휘로)`.
사장님이 입력한 값, 화면 내용, 계정 이름은 **절대 안 올라간다.**

> 되돌리기 자체가 외부 전송이다. **헌장 ③(새 상대 첫 전송)에 걸린다** —
> 처음 한 번은 물어야 하고, 끄고 쓸 수 있어야 한다. 끄면 카탈로그는 읽기 전용으로 돈다.

**신선도를 사장님에게도 보여준다.**

```
✔ 2026-08-05 확인됨            그대로 따라가면 된다
⚠ 확인이 오래됐어요(43일)       바뀌었을 수 있어요. 같이 가 볼까요?
✖ 지난번에 여기서 막혔어요       고쳐질 때까지 안 권한다
```

**틀린 절차는 없는 절차보다 나쁘다.** 모르면 모른다고 말하는 것이 §0 이다.

### 5.1 확인은 깜빡인다 — **한 번 실패로 뒤집지 않는다**

Hermes 가 이걸 비싸게 배웠다(`tools/registry.py` 원문):

> 부하 걸린 상태에서 `docker version` 이 한 번 타임아웃하면 그 순간 **터미널+파일 도구셋이
> 통째로 사라지고**, 서브에이전트가 *"read_file 도구가 없다"* 고 보고한다.

그래서 **마지막 성공 시각을 기억하고, 짧은 유예 안의 실패는 마지막 성공으로 서빙한다.**
유예를 넘어 지속되는 실패만 진짜 고장으로 친다.

```
Hermes 값    확인 캐시 30초 · 실패 유예 60초
우리 값      확인 캐시는 필요 없다(호출 빈도가 낮다)
             실패 유예 = 연속 2회 실패까지는 "통과" 유지, 3회부터 "확인필요"
```

**우리 쪽이 더 위험하다.** Hermes 는 30초 안에 회복되지만, 우리는 사장님이
*"어제 됐는데 오늘 안 된대요"* 를 겪는다. 네이버가 잠깐 느린 것과 화면을 바꾼 것을
**한 번의 실패로는 못 가른다.**

## 6. 0번은 "연결"이 아니다

0번(사장님이 이미 쓰는 것)은 붙일 게 없다. **이미 있다.**
카탈로그에는 **어디에 있는지와 무엇을 볼 수 있는지**만 적는다.

```yaml
id: naver-place-manager
이름: 네이버 스마트플레이스
층: 0
자리: https://new.smartplace.naver.com
전제: 사장님이 이 브라우저에 이미 로그인해 있다
얻는것: 방문자 통계 · 리뷰 · 예약 · 검색 유입
가는길: [ 통계 탭으로 간다 ]
확인: { 방법: 통계 화면에 이번 달 숫자가 있는가, 성공: 숫자가 하나 이상 }
약관: { 쥐는것: 없음, 확인일: null, 판정: 해당없음 }   # ← §7.2 · 사장님 화면을 볼 뿐 아무것도 안 쥔다
상태: 막힘                                          # ← 약관은 해당없음이지만 **4단계(로그인 유지 브라우저)가 없다**
막는것: BUTLER-4단계                                 # 그게 서면 확인(§4)을 돌려서 통과로 바꾼다
```

**0번 항목의 절차는 "로그인하세요"로 시작하지 않는다.** 이미 로그인돼 있는 게 전제다.
안 돼 있으면 그때 사장님이 로그인한다 — **T5 는 비밀값을 대신 넣지 않는다**(헌장 ①).

> ### ⚠ 그 전제가 아직 없다 — 이 절 전체가 **BUTLER 4단계에 막혀 있다**
>
> 0번 항목은 전부 *"사장님이 이 브라우저에 이미 로그인해 있다"* 를 전제로 선다. 그런데
> **지금 브라우저 손은 임시 프로필**이다(`browser.js` — 매번 새 프로필, 로그인 없음).
> 즉 **§11 의 0번 세 항목이 하나도 안 돈다.** 카탈로그를 아무리 잘 써도 그렇다.
>
> **오너 결정 2026-08-06 (BUTLER §9 D2): 사용자 브라우저를 쓴다.** 전용 프로필을 만들지 않는다 —
> 그래야 사장님이 다시 로그인할 일이 없고(0번 유지), T5 가 자격증명을 하나도 안 쥔다
> (§7.2 의 `쥐는것: 없음` 이 그때 참이 된다).
>
> **결정은 났고 구현은 안 됐다.** 그게 BUTLER 4단계이고, **이 카탈로그의 선행 조건**이다.
> 4단계 전에 0번 항목을 `상태: 통과` 로 켜면 §4("확인 없는 항목은 안 넣는다")를 어기는 것이다.

## 7. 비밀값은 카탈로그에 없다

```
카탈로그가 담는 것    값의 "이름"과 어디서 받는지
카탈로그가 안 담는 것  값 그 자체 — 한 글자도
```

받은 값은 **T5 커넥터로 바로 간다.** 카탈로그는 그 값을 보지도 저장하지도 않는다.
카탈로그는 공개돼도 아무 일이 안 나야 한다 — 그게 이 분리의 판정 기준이다.

---

## 7.1 **더 싼 길이 있으면 그 길을 낸다** — 조사에서 나온 실례

같은 데이터에 길이 여럿이면 **비용 등급이 낮은 길을 카탈로그에 적는다.**
사장님은 어느 길이 싼지 모른다. **그걸 아는 게 카탈로그의 일이다.**

```
홈택스 전자세금계산서 · 현금영수증 매입/매출

  비싼 길   공동인증서 + 로그인 + 폰 인증        에너지 상 · 끊김 있음
  싼 길     홈택스 "부서사용자 계정" 하나 만들기  공동인증서 불필요 · 무료 ·
            반영구 · 동시 다중 로그인            (팝빌 홈택스수집 API 문서에서 확인)
```

**부가세·매출 연동이 "인증서 + 폰 인증"에서 "계정 하나 만들기"로 내려간다.**
등급이 통째로 바뀐다. 이런 항목을 하나 찾을 때마다 사장님 하루가 바뀐다.

> 그래서 카탈로그 항목을 만들 때 **"이게 제일 싼 길인가"를 한 번 묻는다.**
> 첫 번째로 찾은 길이 보통 제일 비싼 길이다.

## 7.2 카드사·마이데이터 — **개정: 게이트를 "층"에서 "자격증명"으로 옮긴다** (오너 결정 2026-08-06)

### 무엇이 틀렸었나

첫 판은 **층으로** 막았다 — *"3층(카드사·배달앱) 항목은 오너가 법률 확인을 받기 전에는
카탈로그에 안 올린다."* 그래서 **사장님이 자기 화면에서 자기 매출을 보는 일**까지 같이 멈췄다.

그게 나비효과였다. "이번 달 얼마 벌었지"는 사장님이 제일 많이 하는 말이고, 그 자리가 막히니
카탈로그 전체가 안 섰고, *"나머지는 도구 연결로 해결된다"* 가 성립을 못 했다.
**법률이 막은 게 아니라 우리가 층 단위로 뭉뚱그려 막았다.**

### 갈라야 할 선은 층이 아니다

조사에서 나온 사실은 그대로 유효하다:

```
스크래핑 방식은 규제가 API(마이데이터) 쪽으로 정리되는 중이다
마이데이터 가이드라인에 "사용자가 연결할 기관을 직접 선택해야 한다" 조항이 있다
간편인증 PIN 방식은 "플랫폼이 접근수단 권한을 가진 것"으로 해석될 수 있다는 지적이 있다
```

셋을 다시 읽으면 **문제 삼는 것이 전부 하나다 — 플랫폼이 접근수단을 쥐는 것.**
층(카드사냐 배달앱이냐)이 아니라 **T5 가 무엇을 쥐느냐**가 축이다.

```
게이트 없음   사장님이 이미 로그인한 화면을 본다. T5 는 아무것도 안 쥔다
              → 옆에 앉은 직원이 하는 일과 같다. 사장님 자기 데이터를 자기가 보는 것이다

게이트 있음   T5 가 자격증명을 보관하거나 · 대신 로그인하거나 · 사장님 없이 혼자 접속한다
              → 여기가 "접근수단 권한을 가진 것"으로 해석될 수 있는 자리다
```

**T5 의 기본 동작은 위쪽이다.** 헌장 ①이 이미 그것을 강제한다 — 비밀값은 대신 넣지 않는다.
그래서 0번 항목(§6)은 애초에 아래쪽 자리로 갈 수가 없다.

### 그래서 항목의 `약관` 칸이 하는 일이 바뀐다

층 이름표가 아니라 **그 항목이 T5 에게 무엇을 쥐게 하는가**를 적는다.

```yaml
약관:
  쥐는것: 없음            # 없음 | 저장된키 | 대리로그인 | 무인접속
  확인일: null            # `없음` 이면 확인 대기로 막지 않는다
  판정: 해당없음
```

- `쥐는것: 없음` → **바로 켠다.** 확인 대기로 막지 않는다.
- 그 밖 → 켜기 전에 오너 확인. 그때는 법률이 아니라 **T5 가 무엇을 쥐는지**가 질문이다.

### 내가 판정하지 않은 것 — 그대로 남는다

**법률 자문은 여전히 내 자리가 아니다.** 이 개정이 바꾼 것은 *"어디에 게이트를 두는가"* 이고,
게이트 안쪽 항목(`저장된키`·`대리로그인`·`무인접속`)의 판단은 그대로 오너 몫이다.
바뀐 것은 **게이트 밖에 있어야 할 것을 안에 가둬 두지 않는다**는 것뿐이다.

## 8. 무엇부터 채우나 — **사장님 문장에서 역산한다**

100개를 먼저 만들면 안 쓰는 장치가 된다(2026-08-05 에 이미 한 번 접었다).

```
① 사장님 문장을 모은다        "요즘 손님이 없어" · "이번 달 얼마 벌었지"
② 그 문장이 필요로 하는 것만   문장 하나에 항목 한둘
③ 확인까지 통과한 것만 켠다    미확인은 목록에 있되 안 권한다
```

**문장이 없는 항목은 안 만든다.** "있으면 좋을 것 같아서"가 이 물건을 죽인다.

## 9. 어디에 두고 어떻게 관리하나

```
카탈로그 본체    저장소 밖. 한 파일(YAML 또는 JSON)
왜              안에 넣으면 목록 한 줄 고칠 때마다 배포해야 한다
누가 고치나      오너. 코드가 아니라 목록이라 개발팀 없이 는다
T5 는           읽어 온다. S8 슬롯 구조 그대로 — 코어를 안 고치고 붙는다
사람이 보는 표   같은 파일에서 만든다. 두 벌로 관리하지 않는다
```

**진실은 한 곳이다.** 표와 데이터가 갈라지면 표가 최신처럼 읽히고 그게 제일 나쁘다.

## 10. 이 물건이 죽는 방식 넷 — 그리고 막는 법

| 죽는 방식 | 막는 법 |
|---|---|
| 절차가 낡아 틀린 안내를 한다 | §5 자가 갱신 + 신선도 표시. 오래되면 안 권한다 |
| "붙었다"고 했는데 안 된다 | §4 확인 없는 항목은 안 넣는다 |
| 안 쓰는 항목만 100개 | §8 사장님 문장에서 역산. 문장 없으면 안 만든다 |
| T5 가 쥐면 안 될 것을 쥐었다 | §7.2 항목마다 `쥐는것` 칸. `없음` 이 아니면 켜기 전에 오너 확인 |
| 안전을 이유로 되는 것까지 막았다 | §7.2 개정 — 게이트를 층이 아니라 **쥐는 것**에 건다. 첫 판이 여기서 틀렸다 |

## 11. 첫 판에 넣을 것

문장이 확실한 것부터. **각 항목은 §4 확인을 통과해야 켜진다.**

```
0번   네이버 스마트플레이스        "요즘 손님이 없어"
      배달앱 사장님 사이트         "주문 얼마나 들어왔어"        쥐는것: 없음 → 바로
      카드사 매출내역              "이번 달 얼마 벌었지"         쥐는것: 없음 → 바로

1번   소상공인 상가(상권)정보 API   "저 옆에 새로 생긴 데 뭐야"
      네이버 데이터랩              "요즘 뭐가 뜨지"

2번   네이버 검색광고 API          "우리 가게 뭐라고 검색해?"
      네이버 커머스API             "스토어 얼마나 팔렸어"
      쿠팡 오픈API                 "쿠팡 정산 언제 들어와"
```

**위 항목은 전부 `쥐는것: 없음` 이다** — 사장님이 이미 로그인한 화면을 보는 것뿐이라 §7.2 개정
기준으로 바로 켠다. *"사장님이 자기 계정으로 자기 데이터를 보는 것"* 과 *"도구가 대신 긁는 것"* 은
다르게 취급된다는 판단은 그대로이고, 그 선을 **층이 아니라 쥐는 것**으로 그은 것이 개정이다.

게이트가 서는 자리는 앞으로 이렇게 생긴다 — 항목이 `저장된키`·`대리로그인`·`무인접속` 중 하나를
요구할 때. 그때만 오너 확인을 받는다.

---

## 12. 안 밟은 것

- **한 항목도 실제로 안 걸어 봤다.** §7.2 개정이 게이트를 옮겼지만, `쥐는것: 없음` 이 실물에서
  정말 아무것도 안 쥐는지는 첫 항목을 걸어 봐야 안다.
- 자가 갱신 되돌리기가 **헌장 ③에 어떻게 걸리는지** 실제 배선으로 확인 안 했다.
- 카탈로그 파일 형식(YAML/JSON)과 **T5 가 읽어오는 경로**를 안 정했다. 슬롯이 될지 손이 될지도.
- 이 설계는 **한 항목도 실제로 안 걸어 봤다.** 스키마가 실물에서 버티는지는 첫 항목에서 드러난다.
