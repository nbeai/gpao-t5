# P6-18 · 사용자 표면 통합 — Slice-4: Memory Rollback (반영 되돌리기)

작성: 2026-07-26 · 상태: 구현·라이브 검증 완료, 깊은 감사 대기.
근거: §6.16 검색 표면 후속(감사 지적 — 반영하기가 있으면 되돌리기도 같은 수준), 헌법 §3-5(되돌릴 수 있음).
관련: [[gpao-t5-hermes-absorption-roadmap]], §6.16·§6.19.

## 왜

Slice-3에서 "반영하기"(찾은 기억 → 반영)를 붙였다. 감사 지적: 일반 사용자에게는 **"잘못 반영했을 때 되돌릴
길"도 같은 수준으로** 보여야 한다. 되돌리기가 없으면 반영이 불안한 일방통행이 된다.

## 절대 원칙

- **반영하기가 있는 곳엔 되돌리기도 같은 수준**: 검색 카드(반영됨↔되돌리기 토글), overview "반영 중"(되돌리기 액션).
- **되돌리면 다음 턴부터 영향이 사라진다**: promoted에서 제거 → admittedContext에 안 들어감(P6-17 Slice-3의
  "승인 철회 후 영향 사라짐"과 같은 원리).
- **rollbackable=false(고정 원칙 등)는 거부**: 되돌릴 수 없는 것은 되돌리지 않는다.

## 배선 (기존 엔드포인트 재사용 — 신규 발명 아님)

**감사 보정(내 실수 정정)**: 처음 새 `/memory/rollback`을 만들었으나 **이미 있는 `/memory/rollback`(419)**과
중복이었다(원칙 2 — 기존 코드 먼저 확인 실패). 중복을 걷어내고 **기존 엔드포인트를 재사용·소보강**했다:
- `POST /memory/rollback {candidateId}` — promoted에서 candidateId 제거. **소보강**: rollbackable=false 거부 +
  `rolledBack`(실제 제거 여부) 반환. 기존 `ok:true`는 하위호환 유지.
- `POST /search/admit`은 `candidateId`를 함께 반환(되돌리기용).
- `projectUserModel`/`buildOverview`: 반영 중(admitted) 항목에 candidateId(id)를 실어 되돌리기 액션 가능.

## 표면 (UI)

- 검색 카드: 반영하기 → "반영됨 · 이제 관련 대화에 쓰여요" + **되돌리기** → 다시 "찾은 기억 · 반영 안 됨" + 반영하기
  (토글). 되돌리면 화면·영향 모두 원상.
- overview "선호 · 반영 중": 각 항목에 **되돌리기** 액션(추정은 여전히 액션 없음 — 읽기 전용, 경계 유지).

## 테스트 (3, 총 286)

`/memory/rollback`이 promoted에서 빼고 **admittedContext에서 사라짐(영향 제거)** · 없는 candidateId는
rolledBack:false(그대로) · **rollbackable=false는 거부** + overview 반영 중 항목이 되돌리기용 id를 실음.

반대 테스트: rollback을 no-op(제거 안 함)으로 바꾸면 "되돌린 뒤 영향 사라짐" 테스트 실패 실측 → 제거가
load-bearing. 라이브(브라우저): 검색→반영하기→"반영됨"+되돌리기→클릭→"찾은 기억·반영 안 됨"+반영하기로 원상 복귀.

## 완료/미완료 (사용자 언어)

- **된 것**: 잘못 반영했으면 **되돌리기** 한 번으로 원래대로. 되돌리면 그 기억은 이후 대화에 다시 안 쓰인다.
  반영과 되돌리기가 같은 자리·같은 수준으로 보인다. 되돌릴 수 없는 고정 항목은 되돌리기가 안 된다(정직).
- **아직 아닌 것**: overview에 반영된 recalled_context(검색 기억)를 함께 보기(현재는 선호만), 되돌리기 후 사용자
  언어 확인 토스트, 모바일 레이아웃.

## 남은 후속

- 반영된 recalled_context를 §6.19 overview "반영 중"에 함께 표면화(현재 선호만) — 되돌리기 일원화.
