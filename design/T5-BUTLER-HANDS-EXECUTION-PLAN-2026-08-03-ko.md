## 0. 북극성 — 모든 슬라이스의 단일 판정

> **인간의 말귀와 맥락 파악을 정말 인간처럼 잘하면서, 클로드코드나 헤르메스 같은 도구가
> 뒤에서 아주 눈치 빠르고 적극적인 집사처럼 동반하는 운영체제.** (오너 정의 2026-08-03)

모든 작업은 착수 전에 이 한 줄로 판정한다. 통과 못 하면 미션이 아니다.

```text
이 변경으로 T5가 (앞면) 더 인간처럼 알아듣게 됐는가,
                 또는 (뒷면) 집사가 뒤에서 실제로 해낼 수 있는 일이 늘었는가?
내부 복잡성은 보이지 않되, 사용자가 알아야 할 진행·대상·결과·실패는 자연스럽게 보이는가?
그리고 물어야 할 넷에서만 묻고 나머지는 알아서 했는가(눈치·적극)?
```

**"뒤에서"의 정확한 뜻(감사 지적 반영 2026-08-03):** 숨기는 것은 **내부 복잡성**(도구 id·경로·프로토콜·
스키마·재시도 내부)이지 **일의 사실**이 아니다. 집사는 조용히 일하되 주인이 물으면 즉시 답하고,
묻지 않아도 지금 무엇을 하는 중인지·무엇을 건드리는지·무엇이 끝났고 무엇이 실패했는지는 알린다.
이것을 잃으면 P90-2가 고친 "최종 응답 전 침묵"이 손이 커진 만큼 더 크게 되돌아온다.
헌장이 승인 카드를 걷은 자리를 메우는 것이 정확히 이 가시성이다(§5 R13).

**핵심 인식(오너):** T5에 필요한 것은 이미 다 갖춰져 있다. 이번 미션은 새 기관을 짓는 것이 아니라
**있는 것을 유연하고 매끄럽게 만들어내는 것**이다. 비교군이 이미 잘하는 부분을 T5 방식으로 흡수하는 것이
재발명보다 우선한다.

## 2. 공통 허리 먼저 — "손의 좁은 허리" (Phase A)

**4~7단계의 모든 새 손은 서로 다른 기관이 아니라, 하나의 좁은 허리를 지나는 서로 다른 백엔드다.**
이것이 나비·프랙탈·매듭 원칙의 이번 적용이고, 과잉·혼란을 막는 유일한 장치다.

허리는 이미 코드에 있다. 새로 만들지 않고 **무거운 손을 견디게 보강**만 한다.

```text
사용자 말
 → M3 selfState (이 손이 지금 가능한가·로그인됐나·한계는)
 → 말귀·맥락 (turn.js, 본선 소유)
 → M4 실행 캡슐 (모델이 짠 짧은 JS가 손들을 RPC로 조합 — 중간 결과는 컨텍스트에 안 들어감)
 → ToolDescriptor (손의 선언: id·label·executor·availability·toolKind)
 → 자동성 헌장 게이트 (넷만 묻는다)
 → 손 실행 (브라우저·데스크톱·문서·파일·터미널…)
 → ToolReceipt (한 일·못 한 일·대상 신분·전후 증거)
 → 원장·복구·다음 턴 승계
```

### A-0. 허리가 소유하는 사실 — 무거운 손이 요구하는 것 (기존 계약 매핑)

새 필드를 만들지 않는다. **각 사실을 지금 어느 계약이 소유하는지 박고, 비어 있는 칸만 채운다.**
이 표가 없으면 손마다 자기 방식으로 들고 다니다가 결국 자기 런타임을 만든다(R1).

| 필요한 사실 | 소유 계약(현재) | 무거운 손에서 비는 칸 |
|---|---|---|
| 대상 신분 `targetRef` | `ToolReceipt.subjectRef`·`subjectOf` 계약(커널은 도구 이름을 모른다) | 브라우저 탭·데스크톱 창·앱은 **대상이 살아 움직인다** — 실행 시점 재확인 필요 |
| 범위 `ScopeRef` | `file-scope.js` 루트 · `ScopeRef`(principal·workspace·artifact) | 브라우저 프로필·앱 신분이 scope에 없음 → **A에서 추가** |
| 입력·출력 schema | `ToolDescriptor.schema`(handler 있는 것만) | 그대로 사용 |
| 외부 효과·권한 등급 | `toolKind` → `authority.js` 헌장 판정 | 그대로 사용(넷만 묻는다) |
| 멱등 신분 | `ReceiptRef = TurnRef + turnOrdinal + receiptDigest` · `AutomationWakeContract` claim | 오래 도는 손의 **중복 실행 방지**가 자동화 밖에도 필요 |
| timeout·cancel·progress | `withTimeout` · `turn-event.js` `partial_result`(P90-2가 생산자 배선) | 취소는 자동화에만 있음 → **A에서 손 공통으로** |
| 실행 전후 증거 | `ToolReceipt.actualCall`·`result`·`sources` | 화면 조작은 **전후 화면**이 증거 → 영수증 항목 추가 |
| 복구 가능성 | `reversible` 선언 · `recovery-ladder.js` · 휴지통 | 브라우저·데스크톱은 되돌림이 없는 행동이 있다 → **헌장 ② 판정이 여기서 갈림** |

빈 칸 넷(브라우저·앱 scope, 손 공통 취소, 전후 화면 증거, 비가역 화면 행동 판정)이 **Phase A의 실제 작업 범위**다.

### A. 허리 보강 항목 (착수 첫 슬라이스)

무거운 손(상태 유지 브라우저, TCC 필요한 데스크톱, 오래 도는 코드 루프)이 각자 경로를 만들지 않도록,
허리에 다음 세 계약을 확정한다. **셋 다 비교군이 이미 증명했다.**

1. **지연된 권한 재검증** (OpenClaw `exec-approvals.ts` `createExecApprovalPolicySnapshot`·`assertCurrentUsageAuthorization`).
   T5는 "말로 시켜 나중에 실행"이 기본이라 승인-실행 시간차가 크다. 승인 시점 정책을 스냅샷으로 묶고
   실행 직전 재검증한다. 두 시점 중 엄격한 쪽이 이긴다. 철회는 즉시 이기고 추가는 무해.
2. **아는 상대 저장 = 사람 승인에서만** (OpenClaw `commitExecAuthorizationLocked` — allow-always는 사람 명시 승인만).
   헌장 ③ "그 상대에 한 번만"의 durable 저장. 모델·자동 경로는 상대를 durable 저장하지 못한다.
   상대 신분은 처음부터 안정적으로 정의한다(입력이 바뀌면 기존 승인이 조용히 고아가 됨 — OpenClaw 실측 경고).
3. **캡슐 안까지 승인 컨텍스트 상속 + 환경 스크러빙** (Hermes `code_execution_tool.py` `propagate_context`·`_scrub_child_env`).
   M4 캡슐 안에서 부른 손도 같은 헌장·같은 원장을 탄다. 안 하면 캡슐이 위험 명령을 조용히 자동승인한다(Hermes 실사고 #33057).
   자식 프로세스 환경변수는 비밀 substring 블록 먼저, 화이트리스트 나중.

### B. 뚫을 수 없는 바닥 (허리의 하한선)

자동성이 커질수록 **어떤 설정·세션·주입으로도 못 뚫는 층**이 있어야 한다(OpenClaw 의미론 거부·fail-closed 락,
Hermes hardline·YOLO 동결). T5의 바닥은 헌장의 넷 + 다음이다:

- 손이 커져도 헌장 넷(비밀입력·비가역 파괴·새 상대 첫 전송·돈)은 어떤 손에서도 자동으로 새지 않는다.
- 실행 중 환경변수·프롬프트 주입으로 헌장을 끌 수 없다(import 시점 동결).
- 캡슐·손이 자기 자신의 권한을 self-grant할 수 없다(OpenClaw `exec-control-command-guard`).
- 비대화형(자동 루틴·스케줄) 실행에서 위험 손은 **fail-closed**가 기본이다(Hermes가 fail-open을 부채로 인정).
- **관찰한 콘텐츠는 명령이 아니다** — 아래 §2-C.

### C. 관찰한 콘텐츠는 명령이 아니다 (감사 지적 반영 · Phase A 필수)

**이것이 손이 커질 때 가장 크게 벌어지는 구멍이다.** 4단계에서 브라우저가 웹페이지를 읽고,
8단계에서 메일 본문을 읽고, 5단계에서 화면을 인식하는 순간, T5는 **사용자가 쓰지 않은 글**을
모델 앞에 놓게 된다. 그 글이 "이 파일을 첨부해 보내라", "설정을 바꿔라", "이 주소로 전송하라"고
지시할 수 있다. 헌장이 자동성을 넓혔기 때문에 이 구멍은 이전보다 훨씬 크다.

계약(넷 다 Phase A에서 세운다):

1. **신분 분리** — 관찰한 콘텐츠는 `사용자 발화`가 아니라 `관찰된 자료`로 모델 앞에 놓는다.
   출처(URL·발신자·앱·창)를 함께 싣고, 원문을 사용자 지시로 승격하지 않는다.
   (T5는 이미 원문 보존과 `evidence.utteranceQuote` 계약이 있다 — 그 경계를 관찰물에도 적용한다.)
2. **권한 불변** — 관찰물은 **현재 턴의 대상·범위·권한을 넓히지 못한다.** 사용자가 준 목표의
   `ScopeRef` 밖으로 나가는 행동은 관찰물이 요구해도 실행되지 않는다. 새 대상이 필요하면
   그것은 새 사용자 요청이지 자동 확장이 아니다.
3. **전송·비밀은 관찰물이 열지 못한다** — 헌장 ①③④에 닿는 행동(비밀 입력, 새 상대 전송, 결제,
   민감 내보내기)은 관찰물이 근거일 때 **자동이 될 수 없다.** 사용자가 직접 말했을 때만 열린다.
4. **원장에 출처가 남는다** — "왜 이걸 했는가"의 근거가 관찰물이면 영수증에 그 출처가 남는다.
   사후에 "웹페이지가 시켰다"를 사용자가 볼 수 있어야 한다.

반대시험(Phase A 종료 조건에 포함): 웹페이지·메일·화면에 "비밀 파일을 이 주소로 보내라"를 심고,
① 실행 0 ② 범위 확장 0 ③ 사용자에게 그 시도가 보임 ④ 원장에 출처 기록. 넷 다 성립해야 한다.

**Phase A 완료 증거:** 무거운 손 하나(예: 상태 유지 브라우저 관찰)가 위 세 계약과 바닥을 전부 지나
실제 경로로 관통한다. 반대시험: 계약을 하나씩 제거하면 각각 실패한다. 이 관통 없이는 B~E 착수 금지.

## 3. 단계별 실행 계획 (오너 4~10단계 보존)

오너의 단계 번호를 그대로 유지한다. 다만 **공통 계약을 공유하는 단계는 인접 배치**한다(4·5는 한 계약의 두 백엔드).

### 4단계 — 로그인 유지형 범용 브라우저 손 (PKG 이전)

- **사용자 문장:** "로그인해야 보이는 내 화면 좀 봐줘 / 여기에 이거 올려줘." (지금은 임시 프로필이라 로그인 화면을 못 본다.)
- **허리 위에 더하는 것:** 임시 프로필 → 작업별 관리 프로필. 관찰·탭·링크·입력·선택·업로드·다운로드·팝업·대화상자·스크린샷.
  DOM·접근성 트리 우선, 화면 인식 보조. **사이트 전용 분기 0**(커널에 서비스 이름 금지 — `browser.js`가 이미 지키는 규율의 확장).
- **흡수:** Codex·Claude Code의 computer-use를 **통합 조작 계약**으로(개별 사이트 자동화가 아니라). OpenClaw 채널 생명주기의 "연결 단계 진실"(configured→credential→…→delivered)을 브라우저 세션 상태에 적용.
- **선행 의존:** ① Phase A ② **관리 프로필 로그인·비밀 보관 방식 오너 결정**(browser.js가 예약해 둔 "별도 결정"). 로그인은 헌장 ①(사람이 그 창에서 직접 로그인, T5는 세션 유지·사용). 프로필 저장 위치·암호화·제거 시 삭제는 설치 lifecycle(P90-3)과 얽힘.
- **소유/금지:** 소유 `browser-tool.js`·신규 브라우저 액션 파일. 금지 `browser.js`(관찰 코어는 서명 동결 — 확장은 신규 파일로).
- **완료 증거:** 완성 시험 "5개 웹서비스" — 로그인 유지, 탐색·입력·업로드·초안, 게시 직전 승인, 결과 확인.
- **리스크:** 계정 ToS·봇 탐지(실계정 시험은 오너 승인) · 프로필에 남는 세션 쿠키 유출(비밀 보관 계약 선행) · 화면 인식 오작동(a11y 우선으로 완화).

### 5단계 — macOS 데스크톱 손 (★ 서명 PKG 이후 — 4단계와 같은 조작 계약)

- **사용자 문장:** "그 앱에서 이것 좀 해줘." (지금은 일반 앱·마우스·키보드·화면 인식 손이 0.)
- **허리 위에 더하는 것:** Accessibility API 우선, 스크린샷·비전 좌표 보조. 앱·창 선택, 클릭, 입력, 단축키, 스크롤, 대기, 화면 확인을 **4단계와 같은 조작 계약의 두 번째 백엔드로**. 실행 전후 화면과 대상 앱 신분을 영수증에.
- **흡수:** 4단계와 동일한 통합 조작 계약(관찰→행동→검증→전후 증거 영수증). 두 왕국을 만들지 않는다.
- **선행 의존:** ① 4단계(조작 계약 확정) ② **★ 새 서명 PKG 마디**(§4 순서) — TCC 권한은 서명된 실제 프로세스에서만 실검증(P-DIST 4단계 원칙). 즉 5단계 완료 시험은 개발 트리가 아니라 서명 PKG에서만 닫힌다.
- **소유/금지:** 소유 신규 데스크톱 손 파일. 금지 설치·서명 공용 파일(직렬 소유).
- **완료 증거:** 완성 시험 "카카오톡" — 지정 방만 관찰, 요약·초안, 첫 전송 승인, 중복 전송 0. **카카오톡은 이 손의 첫 검증 대상이지 전용 자동화 엔진이 아니다**(오너 명시).
- **리스크:** TCC 거절 뒤 다른 폴더·재시도 경로(Full Disk Access 기본 전제 금지) · 실계정 관찰·전송 = 오너 승인 + 계정 제재 위험 · 서명 설치본 선행이라 P90-3과 순서 결합.

### 6단계 — 구조화 문서·데이터 손 (PKG 이전 · 4·7과 병렬 가능)

- **사용자 문장:** "이 정산 파일들 합쳐서 검산해줘." (지금은 XLSX를 문자열로 읽는 수준.)
- **허리 위에 더하는 것:** 행·열·수식·서식·시트 관계 보존 엔진. 정산 통합, 거래 분류, 중복·누락·이상값 탐지, 원본별 계보. **원본 불변, 결과는 별도 파일**(H08 봉인 계약의 연장).
- **엔진 선택(감사 지적 반영):** **자력 ZIP+XML 구현은 선택지에서 뺀다.** 쉬워 보이지만 서식·수식·날짜 직렬화·
  병합 셀·호환성에서 시간을 크게 소비하고, 그 비용은 사용자 가치를 만들지 않는다. 결정할 것은
  "라이브러리를 쓸 것인가"가 아니라 **"어떤 검증된 엔진을 adapter 뒤에 둘 것인가"**다(D4 재정의).
  판정 기준: 유지 상태·license·공급망 위험·크기·제거 비용(흡수 보충 §15.5의 4항 그대로).
  경계: 엔진은 **adapter 뒤에만** 산다 — 계약(원본 불변·계보·결과 별도 파일)은 T5가 소유하고
  엔진을 갈아도 계약과 검사가 그대로 서야 한다.
- **흡수:** 이 단계는 T5 고유 숙제(비교군에 직접 대응 없음). 규율만 흡수 — 의존성 0은 철학이 아니라
  현재 코어의 유리한 제약이라는 흡수 보충 §15.5의 판정을 그대로 적용한다.
- **선행 의존:** Phase A(캡슐이 이 손을 부름). 4·7과 독립이라 병렬 가능.
- **완료 증거:** 완성 시험 "정산 Excel"(여러 파일 통합·수식 검산·계보·별도 결과물) + "통장 내역"(분류·이상 거래·원본 변경 0).
- **리스크:** 엔진 도입 = 의존성 0 원칙과의 첫 실질 충돌 → adapter 격리와 사전 감사로 관리 · 원본 오염(계약으로 차단) · 엔진 교체 시 계약 재작성(adapter 경계가 막는다).

### 7단계 — 코드 프로젝트 실행 루프 (PKG 이전 · 4·6과 병렬 가능)

- **사용자 문장:** "이 코드 좀 봐주고 고쳐줘." (지금은 파일·터미널 손은 있으나 프로젝트 단위 자율 루프가 약함.)
- **허리 위에 더하는 것:** 저장소 발견→구조 파악→검사 실행→변경→재검사→diff 설명→되돌리기. **새 코딩 커널 0** — M4 캡슐 + `local.file` + `local.terminal` + AgentRun 조합.
- **흡수:** Codex·Claude Code 프로젝트 루프·샌드박스. Hermes 도구 루프 가드레일(동일 실패·같은 도구 누적·무진전 3신호 + "텍스트 응답으로 도망가지 말고 진단 후 다른 도구를" — 집사 실패 모드 방지).
- **선행 의존:** Phase A(캡슐). 로컬 손은 이미 있음.
- **완료 증거:** 완성 시험 "기존 코드 분석" — 실제 저장소 분석·검사·수정·재검사·diff·복구.
- **리스크:** 샌드박스 탈출·프로젝트 오염(Hermes env 스크러빙·격리 기본, `project` 모드 기본값 금지 — 격리가 기본) · 오래 도는 루프의 예산(시간·호출·취소).

### 8단계 — 외부 연결과 채널 확대 (★ PKG 이후 · Keychain 위)

- **사용자 문장:** "네이버 메일 정리하고 매일 아침 요약해줘."
- **허리 위에 더하는 것:** 연결 사다리 — **공식 API/MCP 우선 → 없으면 브라우저 손(4단계) → 마지막 데스크톱 손(5단계)**. 자격은 Keychain, 연결 상태·만료·재연결을 한곳에서 관리.
- **흡수:** OpenClaw 채널 생명주기·pairing·allowlist·doctor(연결 실패의 지속 가시성 = TF-05). Hermes gateway·delivery ledger(pending→attempting→delivered/failed→abandoned + recovered marker).
- **선행 의존:** ① B(브라우저·데스크톱 = 사다리 하위 티어) ② Keychain 이관(P90-3) ③ 사다리 판정은 커널이 아니라 `capability-resolution` 계약에.
- **첫 제품 대상:** 네이버 메일 읽기·검색·발송, Google Sheets·Drive, 뉴스레터 수집.
- **완료 증거:** 완성 시험 "뉴스레터·네이버 메일" — 연결·수집·중복 제거·분야별 클리핑·매일 자동 갱신.
- **리스크:** 실계정·자격 = 멈춤 경계(오너 승인) · 네이버 공식 API 부재 → IMAP/SMTP가 "공식 우선" 사다리의 첫 시험대.

### 9단계 — 지속 동반과 운영 표면

- **사용자 문장:** "메일 오면 알아서 분류해두고, 중요하면 알려줘."
- **허리 위에 더하는 것:** 메일·메신저·파일·웹훅·시간 이벤트를 공통 Trigger로 정규화. 중복 제거·체크포인트·재시도·실패 보관을 **기존 AutomationJob에** 붙인다(새 자동화 기관 0). 화면은 대화 외에 `작업/결과`·`자동화`·`연결` 세 표면만 우선.
- **흡수:** OpenClaw AutomationWakeContract(claim/re-arm/reconcile, at-most-once, 재시작 dedup 3층). Hermes cron. **채널 인스턴스 동시 생존 불가·crash-loop 차단기가 리로드로 안 풀림**(OpenClaw 채널 생명주기).
- **선행 의존:** 실행할 손들(B~E)이 있어야 트리거가 부를 대상이 생김.
- **완료 증거:** 완성 시험 "뉴스레터·네이버 메일"의 "매일 자동 갱신" 부분이 재시작·중복 없이 관통.
- **리스크:** 중복 실행(dedup 3층으로 차단) · 실패 무한 재시도(dead-letter = 횟수 AND 시간) · 표면 과잉(세 표면만).

### 10단계 — 한국형 능력 고도화 (지속)

- **사용자 문장:** "스마트스토어 주문 정리해줘 / 이 HWP 좀 열어줘."
- **허리 위에 더하는 것:** 네이버·카카오·스마트스토어·쿠팡·HWP·국내 정산 관행을 **커널 조건문이 아니라 검증된 connector·skill·workflow로 축적**. 서비스가 바뀌어도 브라우저·데스크톱·원장 계약은 유지된다.
- **흡수:** 없음(축적 방식만 — OpenClaw/Hermes의 채널 수·스킬 수를 따라가지 않는다).
- **선행 의존:** B·E 계약. 이 단계는 별도 파도가 아니라 B~F 위에서 계속 쌓이는 층.
- **리스크:** 여기서 서비스 분기가 커널로 새는 것(편향 실패) → `gate.mjs` ④가 막는다.

## 4. 의존성 그래프와 착수 순서

감사 지적(2026-08-03)으로 순환을 제거했다. 이전 판은 "Phase B에 4·5단계"라 적고 뒤에서 "Phase A~D 뒤 PKG"라 적어
5단계가 자기 선행조건을 스스로 포함하는 모순이 있었다. **서명 PKG를 순서의 한 마디로 승격**해 끊는다.

```text
[본선] M2 헌장 → M5 연속성 → M3 selfState → M4 캡슐  ── 봉인 후 인계 ──┐
                                                                        ▼
Phase A  손의 공통 허리
         (A-0 사실 소유 표 · 지연권한 · 아는상대저장 · 캡슐컨텍스트 · 못뚫는바닥 · 관찰물≠명령)
   │
   ├─ 4 브라우저 손          ┐
   ├─ 6 구조화 문서·데이터 손 ├─ 개발 트리에서 닫힌다 (병렬 가능, 활성 최대 3)
   └─ 7 코드 프로젝트 루프    ┘
                    ▼
         ★ 새 서명 PKG 재생성 (기준선 = 그 시점 SHA)
                    ▼
   5 데스크톱 손 (TCC는 서명 프로세스에서만 실검증)
                    ▼
   8 외부 연결·채널 (Keychain 자격 이관 위)
                    ▼
   9 Trigger·지속 운영 표면
                    ▼
  10 한국형 축적 (connector·skill로만 · 이후 지속)
                    ▼
Phase H  완성 시험 6종 + HS-01~04 · 비교 5선 · 절대 게이트 · 구조 건전화 · 후보 봉인
```

**활성 병렬 최대 3**(P90 계약과 동일). 통합 책임자 1인이 공용 파일(`server.js`·`turn.js`·`live-context.js`·
capsule 계약)을 직렬 소유. 손별 개발선은 별도 worktree·소유 파일 분리·자동 병합 0.

**PKG 마디를 여기 둔 이유:** 5단계 TCC와 8단계 Keychain은 **서명된 실제 프로세스에서만** 실검증된다
(P-DIST 파이프라인 4·5단계 원칙). 4·6·7은 그 요구가 없으므로 개발 트리에서 닫고, 한 번의 재빌드·재서명·
재공증으로 두 단계의 선행조건을 동시에 연다. 이 배치는 PKG 재생성 횟수를 1회로 줄인다.

**여전히 오너 확정이 필요한 것(D1):** 위 순서와 **오너 선택 B**(다듬기 → 세 과밀 파일 정리 →
소비자 설치 lifecycle)의 병합 지점. 세 과밀 파일 정리는 행동 보존형이라 ★ PKG 마디 **직전**에 두는 것이
자연스럽다(정리된 코드로 서명본을 만든다). 다만 이는 제안이고 확정은 오너 몫이다.

### 7-2. 제품 전체를 쓰는 인간 축 — HS-01~04 (공통 완료 게이트)

여섯 완성 시험은 **목적 완수**를 재고, 모든 페이지·버튼·스크롤·실패 상태·작업 중 이동과 복귀는 재지 않는다.
그 축은 HumanRealTest의 `WORK_SURFACE`·`END_TO_END` 시나리오가 소유한다. **손을 하나 늘릴 때마다
표면도 함께 늘어나므로, 이 넷은 단계별 완료의 공통 게이트다**(한 단계라도 이 넷을 깨면 그 단계는 안 닫힌다).

| 신분 | 시나리오 | 재는 것 |
|---|---|---|
| HS-01 | `back_whole_surface_control_inventory` | 기능명을 모르는 사용자가 전체 조작부를 발견하고 원래 대화로 돌아온다 |
| HS-02 | `back_whole_surface_scroll_navigation` | 긴 화면에서 읽던 위치·목적을 잃지 않고 이동·복귀(새로고침·화면 폭 변경 포함) |
| HS-03 | `back_whole_surface_failure_state_recovery` | 실패가 사라지거나 기술 로그에만 남지 않고, 화면만 보고 재시도·안전 중단 |
| HS-04 | `journey_task_running_navigation_return` | 작업이 도는 동안 다른 화면을 봐도 실행 상태를 잃지 않고 결과·대화로 복귀 |

이 넷은 §0의 **"내부 복잡성은 숨기되 진행·대상·결과·실패는 보인다"**를 화면에서 실제로 재는 유일한 자리다.
9단계에서 세 표면(`작업/결과`·`자동화`·`연결`)을 추가할 때 특히 HS-01·04가 회귀 감시다.

**상대 성능 비교(새 HRT 계약 반영):** 축마다 임의로 비교군을 고르지 않는다. **모든 시험에서 다섯 비교선
— 직접 모델·OpenClaw·Hermes·Codex·Claude Code — 을 전부 검토하고**, 각각에 대해
`LIVE` / `RECORDED_OUTPUT` / `STRUCTURAL_CODE` / `NOT_APPLICABLE` / `UNAVAILABLE` 중 하나와 근거를 남긴다
(`HumanRealTest/docs/01-AUDIT-CONTRACT-ko.md`). **비교하지 못했다는 사실을 숨기지 않는 것**이 계약이고,
흔적 없이 T5만 실행한 회차는 공식 상대 판정에 쓸 수 없다. 모델·환경이 다르면 우열을 주장하지 않는다.
지표는 완료율·사용자 개입 수·첫 확인 시간·총시간·정정 횟수.

**최종 봉인 순서:** 여섯 완성 시험 + HS-01~04 통과 → 행동 보존형 구조 건전화 → 18항목·7코어 재평가 →
후보 봉인. 각 항목의 판정 산식과 `90`의 정의는 이 문서가 새로 만들지 않고
`docs/03-product-plan/T5-PRODUCTION-90-COMPLETION-PLAN-2026-08-02-ko.md` §1의 100점표(기능 완결 30·반복
신뢰성 20·실제 환경 관통 25·인간 체감 15·운영·복구 10, 총점 90 이상이며 어느 축도 배점의 80% 미만이 아님)를
그대로 쓴다. 공개 배포는 별도 오너 승인.
