# T5 2.0 Toolbox / Connection Center UX Reference

- Date: 2026-07-25
- Status: 2.0 surface reference
- Trigger: Codex plugin screen reference screenshot and owner direction
- Scope: T5 2.0 사용자 체감 확장. P6 본체 개발을 방해하지 않고, 도구/연결 표면의 2.0 기준으로 보관한다.
- Addendum: HTML-native generative output principle(HyperFrames/HeyGen talk transcript 참고)

---

## 0. 결론

T5는 2.0에서 앱스토어형 도구함/연결 센터를 가져야 한다.

다만 지금 단계에서 크게 만들면 안 된다. 현재 P6는 도구, 웹, 커넥터, 권한, 원장, 자동화의 실제 운영 계약을 세우는 단계다.
표면을 먼저 크게 만들면 T3 때처럼 "보이는 기능은 많은데 실제로 잠자는 기능"이 생길 수 있다.

따라서 이 문서는 **2.0 반영용 UX 기준**으로 둔다.

핵심 방향:

> 사용자는 플러그인이나 MCP를 이해하지 않아도 된다. 사용자는 "내 일에 필요한 도구를 연결한다"고 느끼면 된다.

2.0의 최상위 UX 원칙:

> 어떤 메뉴, 기능, 응답, 안내, 연결 흐름도 사용자를 덜 헤매게 해야 한다.  
> 사용자는 설정을 공부하는 것이 아니라, 채팅에서 말한 목적이 자연스럽게 이어진다고 느껴야 한다.

따라서 도구함은 기능을 많이 보여주는 화면이 아니라, T5의 자기파악을 사용자 언어로 번역해 "지금 가능한 일,
막힌 일, 필요한 연결, 다음 안전 행동, 원래 작업으로 돌아가는 길"을 보여주는 표면이다.

---

## 1. 참고한 표면의 장점

Codex 플러그인 화면에서 흡수할 점:

- 큰 제목과 짧은 설명으로 사용 목적이 즉시 보인다.
- 검색창이 첫 화면 상단에 있어 필요한 도구를 바로 찾을 수 있다.
- 설치됨 영역이 아이콘 중심으로 보여 현재 가진 능력을 즉시 인식할 수 있다.
- 공개/개인용 탭으로 도구의 출처와 범위를 나눈다.
- Featured, Productivity 같은 카테고리가 일반 사용자 언어에 가깝다.
- 설치 버튼이 작고 명확해 행동 부담이 낮다.
- 문서, PDF, 스프레드시트, GitHub, Notion, Calendar처럼 실제 업무 단위로 보인다.
- 플러그인을 기술 설정이 아니라 "즐겨 쓰는 도구"처럼 느끼게 한다.

흡수할 것은 UX 구조와 감각이다. 화면, 브랜드, 문구, marketplace 정책을 복제하지 않는다.

## 2. T5식 재해석

T5에서는 이 표면을 "플러그인"보다 사용자 중심 언어로 부르는 것이 좋다.

후보:

- 도구함
- 연결
- 작업 도구
- 내 도구함
- 능력 추가
- 연결된 일손

추천 명칭:

| 위치 | 추천 이름 | 이유 |
| --- | --- | --- |
| 일반 사용자 화면 | 도구함 | 기술 냄새가 적고 직관적 |
| 설정/연결 화면 | 연결 | 외부 앱·채널 연결 의미가 명확 |
| 내부 계약/개발 문서 | Toolbox / Connection Center | ToolDescriptor·ConnectorProfile과 연결됨 |

T5의 표면 문장:

```text
필요한 도구를 연결하면 T5가 작업 흐름 안에서 사용할 수 있어요.
위험한 행동은 실행 전에 확인받습니다.
```

## 3. 첫 화면 원칙

T5의 첫 화면은 여전히 Work Chat이다.

도구함은 주인공이 아니다. 도구함은 사용자의 목적 달성을 돕는 배후 표면이다.

사용자 흐름:

```text
사용자: 네이버 리뷰 보고 문제점 알려줘.
T5: 이 작업에는 브라우저/웹 자료 수집이 필요해요. 연결할까요?
사용자: 응.
T5: 도구함의 필요한 연결 화면을 조용히 연다.
```

즉, 사용자가 먼저 도구함을 공부하게 만들지 않는다.

작업 중 필요한 순간에 도구함이 열린다.

## 4. 2.0 화면 구조 초안

### 4.1 상단

- 제목: `도구함` 또는 `연결`
- 짧은 설명: `T5가 작업에 사용할 도구를 연결하세요.`
- 검색창: `도구 검색`
- 설정 아이콘: 도구 권한/개인용 소스 관리

### 4.2 설치됨

이미 연결된 도구를 아이콘 중심으로 보여준다.

표시:

- 도구 아이콘
- 짧은 이름
- 상태 점
  - 초록: 사용 가능
  - 노랑: 연결 필요
  - 빨강: 차단/권한 문제
  - 회색: 비활성

내부 연결:

- `ToolDescriptor.status`
- `ConnectorProfile.readiness`
- `AuthorityGrant`

### 4.3 추천 도구

사용자에게 필요한 가능성이 높은 도구를 보여준다.

카테고리 예시:

- 문서
- 표/매출
- 브라우저/웹
- 메신저
- 일정
- 고객/리뷰
- 로컬 파일
- 자동화
- 개발/깃허브

### 4.4 개인용 / 공개

공개:

- T5가 공식적으로 제공하거나 검증한 도구
- 일반 사용자에게 기본 추천 가능

개인용:

- 사용자가 직접 만든 도구
- 로컬 스크립트
- 개인 MCP
- 팀 내부 커넥터

### 4.5 도구 상세

도구를 눌렀을 때 보여야 하는 것:

- 이 도구로 할 수 있는 일
- 읽기/쓰기/전송/삭제/비용 발생 여부
- 연결 상태
- 필요한 권한
- 최근 실행 기록
- 실패 시 복구 행동
- 끄기/연결 해제

기술 용어 대신 사용자 언어:

| 내부 개념 | 사용자 표현 |
| --- | --- |
| `needs_auth` | 연결이 필요해요 |
| `needsApproval` | 실행 전에 확인받아요 |
| `sourceLedgerRequired` | 출처를 남겨요 |
| `blocked` | 지금 사용할 수 없어요 |
| `failureState` | 최근 문제가 있었어요 |

## 5. 반드시 지킬 T5 원칙

도구함이 예뻐져도 아래 원칙은 깨지면 안 된다.

1. **첫 화면은 채팅이다.**
   - 도구함이 T5의 중심 경험을 대체하지 않는다.

2. **설치됨은 실행 가능함이 아니다.**
   - 설치됨, 연결됨, 실행 가능, 실행 허가는 분리한다.

3. **연결됨은 보내도 됨이 아니다.**
   - 외부 전송은 A2 승인 경계를 유지한다.

4. **웹 도구는 출처 없이 확인했다고 말하지 못한다.**
   - WebToolDescriptor와 ToolReceipt.sources가 살아 있어야 한다.

5. **도구함 UI와 runtime 상태가 다르면 안 된다.**
   - UI는 실제 `SelfStateSnapshot`, `ToolDescriptor`, `ConnectorProfile`에서 온 상태만 보여준다.

6. **죽은 버튼 금지.**
   - 아직 구현 안 된 도구는 "설치됨"처럼 보이지 않는다.
   - 미구현은 추천 후보나 예정 항목으로 분리한다.

7. **일반 사용자 언어.**
   - MCP, schema, provider, auth token 같은 용어를 기본 화면에 노출하지 않는다.

## 6. HTML-Native Output Principle

2.0의 도구함은 "연결된 도구 목록"에서 끝나면 안 된다.

일반 사용자는 도구를 연결하고 싶은 것이 아니라, 결과물을 얻고 싶다.
소상공인, 자영업자, 일인기업, 일반 사용자가 T5에 기대하는 것은 다음과 같다.

- 가게 소개 이미지
- 이벤트 안내문
- 랜딩 페이지
- 메뉴판/가격표
- 리뷰 분석 리포트
- 발표용 화면
- 짧은 홍보 영상
- SNS용 카드뉴스
- 고객 안내 메시지와 발송 미리보기

이 영역에서 T5는 모델에게 낯선 전용 DSL을 먼저 강요하지 않는다.
모델이 이미 잘하는 **HTML/CSS/JavaScript**를 기본 출력 표면으로 삼고, 필요한 최소 메타데이터만 얇게 얹는다.

핵심 원칙:

1. **모델 친화 언어 우선**
   - HTML/CSS/JS는 LLM과 coding agent가 자연스럽게 다룰 수 있는 출력 언어다.
   - 새 JSON DSL, 복잡한 영상 전용 포맷, 과도한 schema를 먼저 만들지 않는다.
   - 필요하면 `data-*` 같은 얇은 메타데이터로 timing, scene, asset, export intent만 보강한다.

2. **문법 교육보다 취향·완성도 교육**
   - 스킬은 "HTML을 어떻게 쓰는가"보다 "좋은 결과물이 무엇인가"를 가르친다.
   - 런칭 영상이면 narrative, scene rhythm, caption, motion, brand consistency를 본다.
   - 랜딩/리포트/카드뉴스면 정보 위계, 가독성, tone, action clarity를 본다.

3. **브라우저 렌더가 검증 표면**
   - "생성했다"가 아니라 실제 브라우저에서 렌더된 화면을 본다.
   - 영상/이미지/문서 export는 preview와 최종 산출물이 같은 소스에서 나와야 한다.
   - 비동기 asset, font, image, external media는 로딩 완료·실패·대체 상태를 receipt로 남긴다.

4. **채팅에서 시작하고, 캔버스는 필요할 때 열린다**
   - 사용자는 "홍보 영상 만들어줘"라고 말한다.
   - T5는 필요한 자료, 톤, 길이, 목적을 묻거나 기존 맥락에서 좁게 복원한다.
   - 결과는 채팅 안 미리보기에서 시작하고, 세밀 조정이 필요할 때 Output Canvas로 열린다.

5. **일반 사용자용 결과물 중심**
   - 목표는 개발자용 데모가 아니다.
   - 사용자가 실제로 올리고, 보내고, 출력하고, 공유할 수 있는 산출물이어야 한다.
   - 공개 게시, 외부 발송, 고객 전송은 AuthorityGrant 경계를 유지한다.

금지선:

- HyperFrames/HeyGen의 화면, 브랜드, 코드, marketplace 정책을 복제하지 않는다.
- HTML-native 원칙이 T5의 ToolDescriptor, WebToolDescriptor, ConnectorProfile, AuthorityGrant, TruthLedger를 대체하지 않는다.
- 실제 렌더/파일/영상 export 없이 "완성됐다"고 말하지 않는다.
- 출처 없는 웹 asset, 권리 불명확한 이미지, 로그인벽 뒤 자료를 조용히 사용하지 않는다.
- 자동 publish, 외부 업로드, 고객 발송은 사용자 승인 없이 실행하지 않는다.

2.0에서의 위치:

> HTML-native output은 P6 커널의 중심이 아니라, 2.0 사용자 산출물 표면이다.  
> P6가 도구·권한·원장·자동화 계약을 닫고, 2.0은 그 능력을 사용자가 체감하는 결과물 제작 경험으로 번역한다.

## 7. 2.0 구현 순서

### Slice 2.0-A. 상태 기반 도구함

목표:

- 현재 연결된 도구를 실제 상태 기반으로 보여준다.

필수:

- installed tools
- available tools
- status dot
- search
- category
- tool detail drawer

금지:

- 실제로 없는 도구를 설치된 것처럼 보이기
- 클릭해도 아무 일 없는 버튼

### Slice 2.0-B. 작업 중 필요한 도구 연결

목표:

- 채팅 중 필요한 도구가 없을 때 도구함으로 자연스럽게 이어진다.

예:

```text
이 작업에는 브라우저 연결이 필요해요. 연결할까요?
```

필수:

- 현재 요청과 필요한 도구 매핑
- 연결 후 원래 작업으로 복귀
- 실패 시 다음 안전 행동

### Slice 2.0-C. 개인용 도구와 스킬 추가

목표:

- 사용자가 직접 만든 도구, 로컬 스크립트, 개인 MCP를 등록한다.
- 사용자가 반복적으로 쓰는 작업 방식은 스킬 후보로 등록한다.

구분:

- 도구는 실행 수단이다. 예: 웹 수집, 슬랙 전송, 로컬 스크립트, 개인 MCP.
- 스킬은 작업 방식이다. 예: 리뷰 분석 방식, 고객 응대 방식, 주간 보고 방식, 매장 운영 점검 방식.
- 스킬은 도구를 포함할 수 있지만 도구와 같지 않다. 스킬은 말귀, 맥락, 절차, 결과물 형식을 함께 가진다.

필수:

- 개인용/공개용 구분
- ToolDescriptor 또는 SkillDescriptor로 등록
- 권한 설명
- 실행 테스트 또는 replay 테스트
- 실패 시 다음 안전 행동
- 제거/비활성화
- 추가 후 도구함 상태와 실제 실행 가능 상태 일치

원칙:

- 추가는 곧 사용 가능을 뜻하지 않는다. 등록, 연결, 권한, 테스트 통과가 분리되어야 한다.
- 사용자는 기술 설정을 다룬다고 느끼기보다, “이 일을 할 수 있게 준비한다”고 느껴야 한다.
- T5는 필요한 도구/스킬을 먼저 알아차리고, 가능한 추가 경로를 제안하되, 설치·연결·권한 부여는 사용자 확인 뒤에만 진행한다.

### Slice 2.0-D. 추천 도구와 자동 제안

목표:

- 사용자의 반복 요청을 보고 필요한 도구나 스킬을 추천한다.
- 막힌 작업에서 필요한 도구/스킬을 찾아 도구함 또는 스킬 추가 흐름으로 자연스럽게 이어준다.

주의:

- 추천은 설치가 아니다.
- 추천은 기억 승격도 아니다.
- 설치/연결/권한 부여/스킬 승격은 사용자 확인이 필요하다.
- 추천은 현재 작업 복귀 경로를 보존해야 한다.

### Slice 2.0-E. HTML-native Output Canvas

목표:

- 채팅에서 요청한 홍보물, 리포트, 랜딩, 카드뉴스, 짧은 영상형 결과물을 HTML/CSS/JS 기반 출력 표면으로 만든다.

필수:

- 채팅 요청 → 목적/대상/톤/자료 확인 → HTML-native draft → 브라우저 preview → 수정 → export
- `data-*` 수준의 얇은 metadata(timing, scene, asset, export intent)
- asset/source receipt
- preview screenshot 또는 render receipt
- 외부 게시/전송 전 AuthorityGrant

금지:

- 렌더 확인 없는 완료 주장
- 전용 DSL을 먼저 만들고 모델의 자연 출력 능력을 죽이기
- 일반 사용자에게 HTML 편집을 강요하기
- 저작권·출처·로그인벽 경계 없는 asset 사용

## 8. 일반 사용자 시나리오

### 시나리오 1. 리뷰 조사

```text
사용자: 우리 가게 네이버 리뷰 보고 문제점 알려줘.
T5: 이 작업에는 웹 자료 수집이 필요해요. 연결할까요?
```

도구함:

- 브라우저/웹 자료 수집 추천
- 읽기 전용
- 출처 남김
- 대량수집 금지 안내

### 시나리오 2. 고객 메시지

```text
사용자: 내일 예약 손님에게 안내 문자 보내줘.
```

도구함:

- 문자/메신저 연결 필요
- 외부 전송 A2 승인
- 미리보기 필수
- 보낸 기록 원장화

### 시나리오 3. 매출표 정리

```text
사용자: 이번 달 매출표 정리해서 요약해줘.
```

도구함:

- 스프레드시트/파일 도구
- 읽기/쓰기 범위 분리
- 변경 전 미리보기

### 시나리오 4. 반복 조사 자동화

```text
사용자: 매주 월요일 경쟁사 가격 조사해줘.
```

도구함:

- 웹 자료 수집
- 자동화
- 알림 채널
- 예약 실행 권한
- 매 실행 원장

### 시나리오 5. 홍보 영상/랜딩 생성

```text
사용자: 이번 주말 할인 행사 홍보 영상이랑 안내 페이지 만들어줘.
```

T5:

- 목적, 대상 고객, 행사 기간, 톤을 확인한다.
- 이미 연결된 자료(메뉴, 가격표, 로고, 사진)가 있는지 SelfState로 확인한다.
- 부족한 자료는 사용자에게 요청하거나 웹/파일 도구 연결을 제안한다.
- HTML-native draft를 만든다.
- 브라우저 preview를 보여준다.
- 사용자가 수정하면 다시 렌더한다.
- 외부 게시/고객 전송 전에는 승인받는다.

도구함:

- HTML-native Output Canvas
- 이미지/영상 export
- 웹 asset 출처 원장
- SNS/메신저/웹 게시 커넥터
- AuthorityGrant

## 9. P6와 2.0의 경계

현재 P6에서 먼저 닫아야 하는 것:

- `ToolDescriptor`
- `WebToolDescriptor`
- `ConnectorProfile`
- `AuthorityGrant`
- `ToolReceipt`
- `TruthLedger`
- `GrowthCandidate`
- 자동화 후보/승인/실행/원장

2.0에서 본격화할 것:

- 앱스토어형 도구함 UI
- 설치됨/추천/개인용/공개 구분
- 아이콘 기반 도구 카드
- 도구 검색과 카테고리
- 연결 상태/권한 상태 시각화
- 작업 중 필요한 도구 연결 흐름
- 개인용 도구 등록
- 실제 connector/plugin registry
- HTML-native Output Canvas
- 브라우저 preview/render receipt
- 이미지/영상/랜딩/export 표면
- 런칭·홍보 산출물 제작 흐름

판정:

> P6는 도구가 실제로 살아 움직이는 OS 계약을 닫는 단계다. 2.0은 그 살아 있는 능력을 일반 사용자가 쉽게 발견하고 연결하는 표면이다.

## 10. 감사 기준

2.0 도구함은 UI 작업이지만 깊은 감사 대상이다.

통과 조건:

1. 실제 runtime 상태와 UI 상태가 일치한다.
2. 설치됨/연결됨/실행 가능/승인 필요가 섞이지 않는다.
3. 없는 도구를 있는 것처럼 보이지 않는다.
4. 외부 전송 도구는 승인 경계를 분명히 보인다.
5. 웹 도구는 출처 원장 조건을 표시한다.
6. 일반 사용자가 기술 용어 없이 이해할 수 있다.
7. 채팅 흐름에서 필요한 순간에 자연스럽게 열린다.
8. 모바일에서도 검색, 설치, 연결 상태가 깨지지 않는다.
9. HTML-native 결과물은 실제 브라우저 렌더 또는 export receipt 없이 완료로 말하지 않는다.
10. 미디어/런칭 산출물은 출처, 권리, 외부 게시 승인 경계를 유지한다.

---

## 11. 최종 판단

T5 2.0의 도구함/연결 센터는 반드시 필요하다.

그리고 2.0은 단순히 도구를 많이 보여주는 화면이 아니라, 사용자가 채팅으로 요청한 일을 실제 결과물로 바꾸는 표면이어야 한다.

HTML-native output 원칙은 이 확장을 위한 중요한 기준이다.

하지만 지금의 우선순위는 아니다.

지금은 P6에서 도구, 웹, 커넥터, 권한, 원장, 자동화의 실제 구동 계약을 단단히 닫고,
2.0에서 앱스토어형 도구함 표면과 HTML-native 산출물 표면을 제대로 올린다.

이 순서가 T3의 실패를 반복하지 않는 길이다.
