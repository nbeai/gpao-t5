# T5 현재 상태와 종합 개발 계획 정합 감사

작성: 2026-07-28
성격: 구현 전환을 위한 정합 감사. 완료 선언이 아님.
감사 질문: **현재 T5는 개발자 도구 묶음으로 커지고 있는가, 아니면 일반 사용자가 말로 목적을 맡기면 모델과 엔지니어링 손발이 함께 움직이는 AI 운영체제로 수렴하고 있는가?**

## 1. 판정

**방향은 정합이다. 현재의 가장 강한 설계 축은 정확하다.**

T5의 정체성은 "개발을 잘하는 챗봇"이 아니라 다음 결합이다.

```text
사용자 편에서 말귀와 맥락을 읽는 모델
        +
T5가 조립하는 현실·터미널·파일·웹·연결·원장·승인 경계
        =
일반 사용자가 말로 컴퓨터와 업무를 맡길 수 있는 AI 운영체제
```

현재 구현은 이 결합의 하체를 상당 부분 갖췄다. 다만 **모델이 그 하체를 모든 종류의 자연어 요청에서 일관되게 활용하는 상체**, 그리고 그 경험을 실제 모델·실제 화면에서 계속 판정하는 기준은 아직 완결되지 않았다.

따라서 지금의 최우선은 새 서비스나 새 화면을 많이 늘리는 일이 아니다. 이미 만든 손발을 `사용자 원문 → 현재 목적·현실 → 모델 판단 → 실행·승인 → 원장 → 다음 턴`으로 묶는 **Operator Harness**를 실전으로 닫는 일이다.

## 2. 기준 문서의 공통 중심

아래 문서는 서로 충돌하지 않는다. 모두 같은 제품을 가리킨다.

| 문서 | 확정하는 것 | 현재 감사의 해석 |
|---|---|---|
| `GPAO-T5-DEVELOPMENT-ABSOLUTE-PRINCIPLES...` §0 | 발화 이해 → 흐름 → 모델 앞 현실 → 실행 사실 → 승계 → 기능 | 모든 기능의 우선순위 |
| `GPAO-T5-FINAL-DEVELOPMENT-PLAN...` §0·§5·§6 | ChatGPT급 대화 체감 + Codex급 로컬 실행력 + 자기파악 | 제품의 한 몸 구조 |
| `GPAO-T5-DEVELOPMENT-PLAN-v3.1-SUPPLEMENT...` §15·§16·§19·§24 | T5 안에서 일을 끝냄, 라이브 우선, 모델 판단 침범 금지 | 완료와 개발 방식의 기준 |
| `GPAO-T5-MODEL-OS-OPERATING-LOOP...` | 원문·현실·판단·실행·원장·승계의 공동 순환 | 매 슬라이스의 설계/보고 단위 |
| `docs/03-product-plan/GPAO-T5-VISION-AND-PERFORMANCE-PHILOSOPHY...` | 일반 사용자가 개발 지식 없이 자연어로 AI-native 일을 맡김 | 사용자 경험의 최종 판정 기준 |
| `design/P5-B-1B-CONNECTOR-OPERATING-LAYER...` | 서비스가 아니라 연결 방식 단위의 발견·연결·편입 | 외부 연결의 일반화 방식 |

### 정합되는 핵심 원칙

1. **모델을 통제하지 않는다.** T5는 원문·현실·경계·결과를 제공하고, 해석·경로 선택·표현은 모델에 남긴다.
2. **능력은 줄이지 않는다.** 파일·터미널·브라우저·연결·자동화는 위험 때문에 제거하지 않고 승인·보호·원장·복구로 다룬다.
3. **사용자에게 방법을 떠넘기지 않는다.** 경로·명령·MCP·API·CLI는 T5가 먼저 확인할 현실이다.
4. **도구는 목적의 하위다.** 사용자가 "노션", "카페24", "터미널"을 말해도 T5는 제품명이 아니라 사용자가 끝내려는 일을 본다.
5. **완료는 실사용 흐름이다.** 테스트·게이트는 회귀 방지이고, 실제 모델·화면·승인·원장·다음 턴이 제품 판정이다.

## 3. 현재 구현 사실

### 이미 강하게 서 있는 하체

| 기관 | 확인된 기반 | 사용자에게 주는 의미 |
|---|---|---|
| 실행 손발 | `local.terminal`, `local.file`, `local.process`, `local.locate`, 웹·브라우저 | 사용자가 명령어를 몰라도 T5가 컴퓨터와 자료를 먼저 조사·실행할 수 있음 |
| 실행 경계 | probe sandbox, A0~A3, `previewOf`, secret 전용 통로 | 위험한 순간에만 이해 가능한 승인으로 멈춤 |
| 사실성 | ToolReceipt, `calledWith`, Truth Ledger, `subjectOf` | 한 일과 못 한 일을 답·원장·다음 턴에서 구분 |
| 지속성 | working state, places, subjects, awaiting, 세션/기억 기반 | "그거", "거기", "아까 하던 것"을 실제 사실에 연결할 기반 |
| 외부 연결 | local signs, MCP, OAuth/PKCE, API key, CLI admission, credential store | 사용자가 설정을 공부하지 않고 연결을 맡길 수 있는 일반형 연결 기반 |
| 사용자 보호 | 비밀값이 대화/원장/모델 입력을 통과하지 않음, 연결·전송은 승인 | 능력과 보호를 함께 확보 |

현재 브랜치 `p5-b-1a-local-connector-probe`에서 `npm test` 1010건, `npm run gate`는 통과했다. 이는 이 기반이 깨진 상태가 아니라는 증거일 뿐, 아래의 라이브 미검증을 대체하지 않는다.

### 막 시작된 상체

`operatorFact → SelfState → TaskContextPacket → buildModelMessages` 경로가 추가됐다. 이는 모델에게 "어떤 도구가 있나"뿐 아니라 **T5가 사용자를 대신해 먼저 맡을 수 있는 일**을 제공하는 P-OP-1의 시작이다.

이 방향은 정확하다. 하지만 현재 `OperatorReality`는 실행 가능한 손의 `label + operation` 목록이 중심이다. 아직 아래의 전체 운영 현실이 아니다.

- 현재 사용자가 끝내려는 일과 그 근거
- 지금 다루는 대상 후보와 신선도
- 이미 시도한 손·인자·결과
- 승인·동의·비밀 입력처럼 멈춰 있는 일
- 손별 한계와 가능한 다음 후보
- 사용자가 실제로 판단해야 하는 경계

`surfaceRequest → awaiting` 승계는 이 빈자리를 향한 유효한 선행 실험이다. 그러나 P-OP-2의 라이브 검증 전에는 완결된 Active Work 계약으로 부르지 않는다.

## 4. 정합성 평가

### A. 철학과 코드: 정합

- descriptor/handler/selfState에서 능력을 파생하는 단일 진실 방향은 "모델 앞의 현실" 철학과 일치한다.
- tool 이름이 아니라 `previewOf`, `subjectOf`, `operatorFact` 같은 계약을 쓰는 방향은 서비스·도구별 if 사다리를 줄인다.
- 커넥터를 서비스별 코드가 아니라 `mcp`, `oauth_pkce`, `api_key`, `cli` 같은 연결 방식으로 다루는 방향은 일반화 원칙과 일치한다.
- 승인·원장·복구를 능력 제거 대신 실행 경계로 쓰는 방향은 절대 역량 명제와 일치한다.

### B. 철학과 실제 제품 판정: 아직 불완전

1. **현재 게이트의 모델은 스텁이다.** 이번 실행에서 doctor는 `beai5-stub`을 보고했다. 따라서 "운영 현실을 실제 고성능 모델이 잘 읽고 자연스럽게 행동한다"는 핵심 가설은 이 브랜치 기준 라이브 미확인이다.
2. **공식 시나리오 문서가 제품 목표보다 얕다.** `docs/03-verification/SCENARIO.md`의 `Guided First Workflow`는 BEAI 일반 워크플로에 가깝고, T5의 터미널·연결·승계·외부 전송·복구를 측정하지 못한다.
3. **계획의 시간축이 분산됐다.** Final Plan, v3.0, v3.1, P5-B 설계, 운영 순환, 현재 브랜치가 각각 맞는 말을 하지만, "지금 어느 기관을 어떤 실사용 증거로 닫는가"를 한 곳에서 보여 주지 않는다.
4. **P-OP-1의 현실은 정확하지만 아직 넓다.** 모든 실행 가능한 손을 매 턴 나열하면 모델의 판단 자료가 늘어난다. 다음 단계에서는 키워드 분기 없이도 현재 작업·직전 증거·손의 역할에 따라 얇게 입장시키는 압축 계약이 필요하다.
5. **UI/UX는 문서가 앞서 있다.** UX Architecture의 사용자 언어·안티 대시보드 원칙은 좋지만, 진행 상태·승인 카드·연결 결과·중단된 일의 재개가 실제 화면/채널에서 계속 자연스럽게 보이는지는 매 슬라이스 라이브 확인이 필요하다.

## 5. 개발자 도구화 위험과 방지 기준

| 위험 | 나쁜 구현 | T5식 방지 |
|---|---|---|
| 터미널이 기능 전시가 됨 | 명령어·로그·cwd를 사용자에게 보여 주고 입력시킴 | 모델은 터미널을 엔지니어링 손으로 쓰고, 사용자는 결과·영향·승인만 봄 |
| 연결이 설정 마법사가 됨 | MCP/OAuth/API 키 절차를 사용자가 배움 | T5가 발견·등록·검증·편입하고, 사용자는 동의·비밀 직접 입력만 함 |
| 말귀가 intent 분류기가 됨 | "노션" 키워드면 정해진 문장/도구 | 원문·흐름·작업 상태·손발·결과를 함께 조립해 모델이 판단 |
| 자동화가 블랙박스가 됨 | 반복을 감지하면 조용히 실행 | 후보 → replay → 승인 → 원장 → 중지/되돌리기 |
| 시스템 프롬프트가 대본이 됨 | 사례별 금지문·답변 템플릿 누적 | 짧은 운영 헌장 + 파생된 정확한 현실 + 결과 사실 |
| UI가 관리자 화면이 됨 | 도구 목록·프로토콜·상태코드가 첫 화면을 점유 | Work Chat 중심, 필요할 때만 쉬운 말의 진행·승인·결과를 표시 |

## 6. 우선순위 보정

### 지금 멈출 것

- 새 서비스별 커넥터 추가 경쟁
- 새 OAuth/CLI kind를 계속 늘리는 일
- 대형 설정 센터·개발자용 대시보드 확장
- 사례별 응답 문장·키워드 규칙 추가

위 작업은 기반이 없어서가 아니라, 현재 가장 큰 병목이 **손의 수가 아니라 모델이 매 턴 정확한 운영 현실을 읽고 자연스럽게 이용하는가**이기 때문이다.

### 다음 순서

1. **현재 실행 보드 정본화**
   - 새 제품 기능이 아니라 문서 정합 작업이다.
   - 각 기관을 `구현됨 / 코드 검증 / 실제 모델 검증 / 실제 UI·채널 검증 / 남은 경계`로 표시한다.
   - v3.1 §15의 사용자 작업 10개와 현재 P5-B 증거를 연결한다. 오래된 ✗/◐ 표기를 조용히 완료로 바꾸지 않는다.

2. **P-OP-1을 실제 모델로 닫기**
   - 같은 실제 모델·실제 T5 대화에서 아래 세 문장을 각각 확인한다.
     - "컴퓨터가 왜 느린지 봐줘"
     - "지난달 정산 자료 정리해줘"
     - "카페24 주문 가져와줘"
   - 판정은 답변 문구가 아니라 모델 입력, 실제 조사, 승인 카드, 원장, 다음 턴이다.
   - 실패하면 금지문을 더하지 않고 어느 현실 칸이 비었는지 보완한다.

3. **P-OP-2 Active Work 계약 닫기**
   - 현재 대상·직전 실행·실패·대기 승인·비밀 입력/동의 대기를 사실로 합성한다.
   - "그거 다시", "아까 오류 고쳐줘", "연결하다 말았지?"를 일반 사용자 문장으로 라이브 검증한다.
   - 이전 일을 잘못 되살리는 반대 시나리오도 함께 본다.

4. **P-OP-3 공통 탐색 손 설계·실증**
   - 미선언 서비스/낯선 요청에서 앱·MCP·CLI·설정·파일·웹의 근거를 먼저 찾는다.
   - 탐색 결과는 후보일 뿐 자동 연결·설치·도구 편입이 아니다.
   - 이 단계가 "카페24 주문 가져와줘"를 서비스별 코딩 없이 다루는 진짜 시험대다.

5. **T5 사용자 운영 시나리오를 정본 검증 세트로 승격**
   - 아래 일곱 시나리오를 `SCENARIO.md`의 일반 워크플로와 분리해 T5 전용 상설 라이브 세트로 둔다.
     1. 로컬 PC 진단
     2. 자료 탐색·정리·파일 변경 승인
     3. 미선언 외부 서비스 발견·연결 경로
     4. OAuth/MCP 연결과 실제 tool admission
     5. 외부 전송 승인·원장·채널 복귀
     6. 멀티턴 복구·중단 작업 승계
     7. 기억 회수와 부적절한 기억 배제

6. **그 다음에야 연결 종류·UI 표면을 넓힌다**
   - 새 연결 방식은 위 시나리오가 실제로 필요로 할 때만 추가한다.
   - UI는 운영 사실이 사용자 화면까지 도달하는 것을 라이브로 확인하면서 확장한다.

## 7. 시스템 프롬프트와 하네스의 역할

시스템 프롬프트는 T5의 강력한 기관이어야 한다. 다만 그것은 사용자의 요청마다 답을 대신 쓰는 대본이 아니라, 모델이 사용자 편에서 사고하는 **운영 헌장**이다.

```text
고정: 정체성 · 사용자 편 · 정직성 · 승인 원칙 · 응답 태도
안정: 실제 가능한 손 · 선언된 한계 · 연결 상태
현재: 원문 · 대상 · active work · 관련 증거 · 대기 경계
결과: 실제 실행/미실행 · 원장 · 복구 후보
```

고정층은 짧고 모델의 판단력을 높여야 한다. 현재층은 정확하고 얇아야 한다. 서비스별 처방이나 문구 목록은 이 구조에 넣지 않는다.

다음 보강은 프롬프트를 길게 만드는 일이 아니라 다음을 가능하게 하는 **Prompt Assembly Contract**다.

- 어느 사실이 왜 이번 턴에 들어왔는지 추적
- 관련 없는 손·기억·과거 실패를 넣지 않음
- 제공한 현실과 실제 모델 행동을 원장으로 대조
- 모델별 보정은 공통 헌장이 아니라 얇은 provider profile에 격리

## 8. 단계 종료 판정

T5가 영화 속 비서처럼 느껴진다는 것은 모든 일을 마법처럼 자동 실행한다는 뜻이 아니다. 사용자가 결과를 말하면 T5가 먼저 현실을 확인하고 손발을 움직이며, 사용자는 자기 권한이 필요한 순간에만 이해 가능한 선택을 하는 경험이 반복되는 뜻이다.

따라서 이 감사의 최종 판정은 다음과 같다.

```text
제품 방향: 정합
구현 기반: 강함
현재 최대 병목: 모델-현실-실행의 공통 운영 하네스 라이브 입증
다음 우선순위: P-OP-1 라이브 → P-OP-2 → P-OP-3 → 상설 사용자 시나리오
현재 완료 주장: 불가 (실제 모델/실제 사용자 표면의 통합 검증이 남음)
```

이 순서를 지키면 T5는 개발자에게 도구를 나열하는 시스템이 아니라, 강한 모델의 말귀와 엔지니어링 능력을 일반 사용자의 삶과 업무에 연결하는 운영체제로 수렴한다.
