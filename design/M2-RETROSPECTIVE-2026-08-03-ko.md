시간이 아니라 **회차**로 적는다(시간은 학습의 근거가 아니다).

| 자리 | 헛돈 회차 | 원인 |
|---|---|---|
| 600초 폭증 원인 | 1 (틀린 가설) | 그럴듯한 원인(네트워크 타임아웃)을 측정 전에 채택 |
| 돌연변이 #293 | 2 | 폴백이 둘인데 두 번째가 첫 번째를 가려, 실행 여부로는 차이가 안 보임 |
| 검사 전환 | 다수 | 승인 카드를 **관측 도구**로 쓰던 검사가 카드가 사라지자 전부 깨짐 |
| 대본 모델 하네스 | 3 | `op`/`action` 인자명, "두 번째 호출" 판정, declare 스키마 |

(`approval-wording` 12곳, `smart-approval` 10곳, `pc-hands-c-closure` 9곳 …).

## 4. 하나의 원인이 둘을 동시에 설명한다

시간 폭증과 라이브-only 결함은 **다른 문제가 아니다.**

> 검사가 **사용자에게 도달하는 사실**이 아니라 **중간 장치**에 앵커돼 있었다.

- 앵커가 "승인 카드가 뜬다"였기 때문에 → 헌장이 설계로 카드를 걷자 53건이 한꺼번에 깨졌다.
  각각이 지키던 진짜 계약을 하나씩 되찾아 다시 앵커해야 했다. **이게 시간의 대부분이다.**
- 같은 이유로 `WHY_AUTO` 검사는 `explainAuthority` 라는 중간 장치를 직접 불러 초록이었다.
  제품 경로에는 그 값을 실어 나를 통로가 아예 없었는데도. **이게 라이브-only 결함이다.**

즉 **앵커를 잘못 잡으면 비용은 리팩터링 때 청구되고, 결함은 사용자에게 청구된다.**

이번에 옮긴 앵커의 예:
- "삭제가 멈춘다" → **원본이 `.trash` 에 바이트 동일하게 남는다**(md5 대조)
- "카드 문구가 이렇다" → **손이 낸 영수증이 대상·한 일·되돌릴 길을 말한다**
- "승인이 필요하다" → **승인 전 실행 0, 승인 후 실제 실행**(파일 시스템 대조)

### 지킨 것

| 기준 | 결과 |
|---|---|
| 최소 안전, 최대 자동화 | 안전 바닥 12→8. 카드 세 자리 제거, 파괴 경로는 그대로 |
| 카드와 클릭으로 괴롭히지 마라 | 읽기·목록·연결·서비스 붙이기에서 카드 사라짐(라이브 확인) |
| 나비·프랙탈·매듭 — 패치 금지 | 승인 모드 3종을 조정하지 않고 **제거**. `WHY_AUTO` 도 통로를 뚫지 않고 제거 |
| 감사 지적은 원인 제거로 흡수 | 결함마다 그 계열을 잡는 그물을 함께 세움(스윕 305건) |
| 모델을 멍청하게 만들지 마라 | 왕복을 깎지 않음. 벽시계는 오히려 25.9s→23.5s |
| 판정칸은 밟은 기계사실로 | 라이브 판정 전부 파일·원장·md5. 문구 일치 판정 0건 |

### 어긴 것 — 정면으로 적는다

**「슬라이스 완료 기준」(오너, 2026-07-28)**:
> "완료 보고 전에 웹 표면에서 라이브로 한 번 돌린다. **테스트로 화면 확인을 대신하지 않는다.**"

M2 는 **라이브 전에 커밋했다.** 회귀 2,088 · 스윕 304 · 게이트 PASS 를 근거로 삼았고,
커밋 메시지 마지막 줄에 "아직 아니다: 라이브 관통 0"이라고 적기까지 했다. 정직했지만
**기준이 요구한 순서는 아니었다.** 그 결과 오너가 든 카드가 커밋 안에 그대로 들어갔다.

**「계약 문장 정면대조 후에만 닫는다」**:
> "정의역·소비자 열거 후 1:1 증거."

`WHY_AUTO` 를 만들 때 **소비자를 열거하지 않았다.** 함수를 직접 부르는 단위 검사를 쓰고
초록을 근거로 삼았다. 이 메모리는 정확히 이 실수를 막으려고 존재했는데 적용하지 않았다.

**「다섯 질문」 5번 — "지역 문제에 빠져 전체 구조를 잃고 있지 않은가"**:
`connector.connect` 를 고치며 **바로 그 주석에** "새 서비스 붙이기 카드가 오너가 든 6장 중
하나"라고 적어놓고, `connector.declare` 라는 이름의 도구를 안 봤다. 한 자리를 고치면서
같은 종류의 다른 자리를 훑지 않았다.

## 6. 개발방식 개선 — 다음 개발에 실제로 거는 규칙

관행이 아니라 **집행 가능한 형태**로 적는다.

### R1. 앵커 규칙 — 검사는 사용자에게 도달하는 사실에만 건다
중간 장치(승인 카드·내부 함수 반환값·상태 이름)를 관측에 쓰지 않는다. 쓸 수밖에 없으면
그 검사에 **`// 중간앵커:` 주석과 이유**를 남긴다. 설계가 바뀔 때 무엇이 왜 깨지는지 즉시 안다.

### R2. 소비자 열거 없이 새 문장·새 값을 만들지 않는다
사용자에게 보일 문장이나 값을 새로 만들 때, **그 값을 화면까지 실어 나르는 경로를 먼저 짚는다.**
경로가 없으면 만들지 않는다. `WHY_AUTO` 는 이 규칙 하나로 애초에 생기지 않았다.

### R3. 라이브가 커밋보다 앞이다
슬라이스 완료 기준을 순서로 못박는다: **정면대조 → 구현 → 회귀·스윕 → 라이브 관통 → 커밋.**
라이브가 불가능한 경우(자격 없음 등)에만 예외이고, 그때는 무엇이 미측정인지 커밋 전에 적는다.

### R4. 한 자리를 고치면 같은 종류를 전수로 훑는다
도구 선언·분기·문구는 이름이 달라도 같은 계열이다. `grep` 한 번으로 끝나는 일이다.
그리고 **개별 자리를 알아맞히는 검사 대신 계열 전체를 훑는 그물**을 세운다 —
`test/live-descriptor-charter.test.js` 가 그 형태다(도구가 늘어도 같은 그물).

### R5. 라이브 하네스를 자산으로 남긴다
이번에 만든 대본 모델 종단은 매번 새로 짜면 3회차씩 헛돈다. 저장소에 넣어 재사용한다.

## 7. 역량강화 — 다음 개발 전에 세울 것

| 장치 | 하는 일 | 상태 |
|---|---|---|
| **라이브 하네스 상설화** | 격리 데이터 자리 + 대본 모델 종단 + 시나리오. `npm run live:charter` 한 줄로 헌장 넷 양방향 관통 | 만들 것 |
| **앵커 감사** | 검사 파일에서 중간 장치를 관측에 쓰는 자리를 세어 보고. 늘면 다음 설계 변경의 청구서가 늘어난다 | 만들 것 |
| **소비자 추적** | 새로 만든 사용자 문장/값이 화면 경로에 닿는지 자동 확인(정적 추적 또는 라이브 대조) | 만들 것 |
| **계열 그물 패턴** | 개별 도구를 알아맞히지 않고 선언 전체를 훑는 검사. M2 에서 형태 확보 | ✅ 확보 |
| **돌연변이 스윕** | 검사가 정말 무는가. 305건 | ✅ 운영 중 |

우선순위는 **라이브 하네스 상설화**다. M2 의 두 라이브-only 결함은 둘 다 20분의 실사용이
잡았고, 그 20분을 매번 손으로 차리느라 3회차를 헛돌았다. 이걸 한 줄로 만들면
R3(라이브가 커밋보다 앞) 이 규칙이 아니라 **기본값**이 된다.
