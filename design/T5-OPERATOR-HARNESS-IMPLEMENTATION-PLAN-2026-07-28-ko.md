# T5 Operator Harness 구현 계획

작성: 2026-07-28
지위: **구현 계획 초안** · 오너 검토 후 단계별 착수
상위 기준: `GPAO-T5-MODEL-OS-OPERATING-LOOP-2026-07-27-ko.md` · `docs/03-product-plan/GPAO-T5-VISION-AND-PERFORMANCE-PHILOSOPHY-2026-07-27-ko.md`
연결 대상: P2 대화 품질 기반 · W1~W3 작업 상태 · P5-B Connector Operating Layer

> T5의 코어는 새 모델이나 서비스별 규칙이 아니다.
> **말귀 좋은 모델이, T5가 조립한 정확한 현실과 엔지니어링 손발을 사용자 편에서 자유롭게 쓰게 하는 운영 하네스**다.

---

## 1. 결정

T5는 Codex·Claude Code처럼 컴퓨터와 개발 환경을 실제로 다루고, ChatGPT처럼 사용자의 목적과 대화 흐름을 자연스럽게 이해해야 한다. 둘 중 하나를 흉내 내는 제품이 아니다.

사용자가 "지난달 자료 정리해줘", "컴퓨터가 왜 느린지 봐줘", "카페24 주문 가져와줘", "노션 붙여줘", "아까 그거 다시 해줘"라고 말하면, T5는 다음을 한 흐름으로 수행한다.

```text
사용자 원문과 흐름
  → 현재 목적·대상·현실을 조립
  → 모델이 스스로 조사·도구·표현을 판단
  → T5가 터미널·파일·웹·브라우저·연결 손을 실행
  → 위험 순간만 승인·동의·비밀 직접 입력을 요청
  → 실행 사실을 원장에 남기고, 답과 다음 턴에 반영
```

사용자는 경로, 명령어, MCP, API, CLI, 환경 변수, 설정 파일을 관리하지 않는다. T5가 할 수 없는 실제 권한 행위만 사용자의 몫이다.

---

## 2. 이미 있는 기반

이 계획은 새 플랫폼을 만드는 일이 아니다. 이미 있는 기반을 하나의 모델 운영 환경으로 결합하는 일이다.

| 기반 | 현재 구현 | Harness에서의 역할 |
|---|---|---|
| 원문·최근 대화 | `runTurn`, `TaskContextPacket`, `recentTurns` | 모델이 사용자의 말과 흐름을 잃지 않는 입력 |
| 현재 대상·자리 | `working-state.js`, `subjectOf`, `local.locate` | "그거·거기·다시"를 실제 대상에 연결 |
| 실제 가능한 손 | `ToolDescriptor`, `SelfState`, `schema ⊆ executable ⊆ handler` | 모델이 없는 능력을 상상하지 않게 하는 자기자각 |
| 터미널·파일·프로세스 | `local-terminal.js`, `local-file.js`, `local-process.js` | 일반 사용자 대신 컴퓨터를 조사·실행하는 엔지니어링 손발 |
| 웹·브라우저 | `web.collect`, `browser.observe`, `browser.act` | 외부 현실을 읽고, 읽은 범위와 못 읽은 범위를 구분 |
| 연결 운영 | `local-signs.js`, `connector-connect.js`, Tool Admission | 설치·MCP·OAuth·API 키·CLI를 T5가 먼저 확인·연결 |
| 위험 경계 | probe sandbox, A0~A3, `previewOf`, 비밀 전용 통로 | 능력을 지우지 않고 실행 순간만 멈춤 |
| 사실·복구·승계 | `TruthLedger`, `calledWith`, recovery ladder, `subjectOf` | 한 일과 못 한 일을 구분하고 다음 턴으로 이어감 |
| 말투·운영 기준 | `judgment-charter.js`, SOUL, `buildModelMessages` | 모델을 억제하지 않고 사용자 편에서 사고하게 하는 기준 |

현재 진행 중인 첫 보강은 `operatorFact`다. 도구 이름만 보여 주던 짧은 턴에도, "T5가 사용자 대신 무엇을 직접 확인·실행할 수 있는가"를 descriptor 단일 진실에서 모델 입력으로 보낸다. 이것은 P-OP-1의 시작이지 완료 선언이 아니다.

## 3. 제품적 문제 정의

### 사용자가 보는 문제

사용자는 방법이 아니라 결과를 원한다.

- "정산 자료 봐줘"는 경로 찾기, 파일 열기, 계산을 부탁하는 말이다.
- "노션 붙여줘"는 MCP/OAuth 설정 절차를 배우겠다는 말이 아니라 연결을 끝내 달라는 말이다.
- "왜 안 돼?"는 로그·설정·권한을 먼저 조사해 달라는 말이다.
- "그거 다시"는 직전 대상·실패·승인 대기 상태를 이어 달라는 말이다.

### 지금 남은 공통 빈자리

도구와 연결 기반은 많이 생겼지만, 모델이 모든 종류의 요청에서 아래를 한 번에 보는 **공통 운영 현실**은 아직 얇다.

1. 지금 사용자가 원하는 결과와 현재 작업이 무엇인가
2. T5가 먼저 조사할 수 있는 현실이 무엇인가
3. 현재 쓸 수 있는 손의 역할과 실제 한계가 무엇인가
4. 이미 시도한 길과 다음으로 바꿔 볼 손이 무엇인가
5. 언제만 사용자에게 권한을 물어야 하는가

이 빈자리를 서비스별 프롬프트, intent 키워드, 답변 금지문으로 메우면 다음 요청에서 다시 샌다. Harness가 이 다섯 사실을 모델 앞에 조립해야 한다.

## 4. 목표 아키텍처

### 4.1 역할 분리

```text
T5 Runtime                         Model
────────────────────────────────────────────────────────
원문 보존                           목적·의도·생략을 해석
현실 수집·압축                      무엇을 먼저 볼지 판단
도구·연결·권한 상태 계산             어떤 손을 쓸지 선택
실행·승인·보호·원장                 결과를 사용자 말로 설명
회복 후보·다음 턴 상태 제공          대안과 질문의 필요성을 판단
```

T5는 모델의 판단을 규칙으로 대체하지 않는다. 모델은 T5가 제공한 사실 밖의 능력을 실행했다고 말할 수 없고, T5는 모델이 고른 실행을 경계에서만 집행한다.

### 4.2 Prompt / Harness 계층

| 계층 | 내용 | 갱신 | 원칙 |
|---|---|---|---|
| 고정 헌장 | 정체성, 사용자 중심 운영, 승인 원칙, 정직성 | 드물게 | 모델의 보는 법. 답변 대본 금지 |
| 사용자 목소리 | SOUL의 말투·온도 | 사용자 변경 시 | 취향이며 계약이 아님 |
| 안정 현실 | 사용 가능한 손, 선언된 한계, 연결 방식 | 상태 변경 시 | descriptor/handler에서만 파생 |
| 이번 작업 현실 | 원문, 현재 대상, 직전 사실, 작업 목표, 다음 후보 | 매 턴 | 필요한 것만 압축 |
| 실행 결과 | calledWith, 성공/실패, 본 범위, 출처, 승인 대기 | 도구 뒤 | 원장 사실만 |
| 도구 스키마 | 실제 executable 도구만 | 상태 변경 시 | `schema ⊆ executable ⊆ handler` |

고정 헌장은 짧고 강해야 한다. 동적 현실은 정확하고 얇아야 한다. 두 층을 섞어 긴 지시문으로 만들지 않는다.

### 4.3 Operator Reality Packet

`TaskContextPacket`에 아래를 파생해 싣는다. 이 패킷은 새 저장소가 아니라 기존 진실층의 얇은 조립물이다.

```ts
type OperatorReality = {
  activeWork?: {
    goal?: string;              // 현재 발화·명시 목표에서 온 사실
    targets: Subject[];         // workingState / subjectOf에서 온 현재 대상
    pending?: PendingAction[];  // 승인 대기·연결 진행·실행 중인 일
  };
  hands: Array<{
    label: string;
    operation: string;          // descriptor.operatorFact
    limit?: string;             // 선언된 한계만
    state: 'usable' | 'needs_connection' | 'blocked';
  }>;
  environment: {
    places?: Place[];
    connectors?: ConnectorTruth[];
    surface: ResponseSurface;
  };
  evidence?: {
    attempted: ReceiptFact[];
    nextCandidates: RecoveryFact[];
  };
  userBoundary: {
    onlyUserCanDo: Array<'approve' | 'consent' | 'secret_input' | 'choice'>;
  };
};
```

주의: `goal`은 모델의 추정을 영구 사실로 저장하지 않는다. 사용자가 명시했거나 현재 작업·원장에서 근거가 있는 경우에만 넣는다. 새 손의 `operation`도 descriptor가 선언하지 않으면 지어내지 않는다.

## 5. 구현 순서

각 단계는 독립적으로 사용자 체감 개선을 내고, 다음 단계를 위한 공통 기반이 된다. 단계 안에서 다른 문제를 끌어오지 않는다.

### P-OP-1. 공통 운영 현실 컴파일러

**목적**: 모든 턴에서 모델이 "T5가 먼저 맡을 수 있는 일"을 안다. 외부 서비스 질문에만 현실을 제공하는 분류 의존을 없앤다.

**구현**

- `ToolDescriptor.operatorFact`를 도구 진실 계약으로 유지한다.
- `operator-reality.js`가 실행 가능한 선언 손만 모은다.
- `TaskContextPacket → buildModelMessages`에 공통 운영 현실을 넣는다.
- 터미널·파일·프로세스·찾기·웹·브라우저·세션·연결의 역할을 descriptor에 선언한다.
- 연결/권한이 필요한 손은 "현재 실행 가능"과 "연결하면 가능"을 섞지 않는다.

**완료 조건**

- `fast_chat`, 복잡 작업, 채널 턴 모두에 운영 현실이 공급된다.
- 새 손의 역할을 런타임이 추측하지 않는다.
- 모델이 도구 이름만 보고 사용자를 터미널·설정으로 보내는 빈자리가 줄어든다.
- 실제 모델 라이브에서 "컴퓨터가 왜 느린지 봐줘", "카페24 주문 자료 좀 가져와줘"를 확인한다.

### P-OP-2. 현재 작업·목적·대상 컴파일러

**목적**: 모델이 원문과 `workingState`를 따로 읽어 조립해야 하는 부담을 줄이고, "무엇을 위해 어떤 대상을 다루는 중인가"를 사실로 본다.

**구현**

- 현재 작업트리의 `surfaceRequest → awaiting` 승계는 이 단계의 **선행 실험**으로 취급한다. 비밀 입력·연결 같은 중단된 일을 다음 턴에 잇는 데 유효한지, 다른 대상이나 끝난 일을 되살리지 않는지 라이브로 확인한 뒤에만 정식 계약으로 보존한다.
- `workingState`, `subjectOf`, 승인 대기, 진행 중 프로세스, 직전 receipt에서 `activeWork`를 파생한다.
- 현재 대상은 한 개의 확정 사실이 아니라 근거·신선도·실패 여부를 가진 후보로 보낸다.
- 새 발화가 이전 작업을 바꾸면 기존 대상은 감쇠·해제한다.
- 사용자가 말한 목표와 모델이 제안한 계획을 구분한다. 모델 계획은 원장이 확인하기 전 durable state가 아니다.

**완료 조건**

- "그거 다시", "거기서 찾아봐", "아까 오류 고쳐줘", "그 폴더에 정리해"가 실제 대상·실행 사실을 이어받는다.
- 비밀 입력창·동의창을 닫거나 놓친 경우에도 T5가 실제로 중단된 일만 짧게 이어 주며, 이미 끝난 일이나 무관한 일을 되살리지 않는다.
- 과거 대상이 새 작업을 덮지 않는다.
- 모델이 추정한 목표를 사용자 의도처럼 단정하지 않는다.

### P-OP-3. 엔지니어링 탐색 루프

**목적**: 미등록 서비스나 낯선 컴퓨터 요청에서도 T5가 "지원하지 않음"이나 설치 문서 안내로 끝나지 않고, 먼저 자기 현실을 조사한다.

**구현**

- 모델이 필요할 때 호출하는 읽기 전용 `operator.discover` 또는 동등한 공통 탐색 손을 설계한다.
- 탐색은 서비스 이름을 하드코딩하지 않는다. 이미 존재하는 MCP 등록, CLI, 앱, 동기화 폴더, 프로젝트 설정, 웹 공개 정보, 로컬 자료를 **근거와 함께** 수집한다.
- 결과는 `connection candidate` 또는 `work candidate`다. 탐색만으로 새 커넥터·새 권한·새 도구를 자동 편입하지 않는다.
- 후보가 실제 연결/설치/비밀 입력을 요구하면 기존 Connector Operating Layer의 승인·동의·secret surface로 넘긴다.

**완료 조건**

- "카페24 주문 가져와줘" 같은 미선언 요청에서 T5가 먼저 가능한 흔적과 연결 경로를 조사한다.
- 탐색 실패를 "그 서비스는 못 해요"로 단정하지 않는다.
- 근거 없는 connector declaration, API 추측, 임의 설치는 발생하지 않는다.

### P-OP-4. 다중 손 실행·복구 루프

**목적**: 한 손이 막혔을 때 모델이 현재 사실을 보고 다른 손을 선택할 수 있게 하며, 같은 탐색을 낭비하게 반복하지 않는다.

**구현**

- receipt의 실패 성격·범위·대상·시도 인자를 `recovery candidates`로 압축한다.
- 이미 같은 손·같은 인자로 시도한 것은 루프 안에서 재시도하지 않는다.
- 브라우저/웹/파일/터미널/연결의 실패를 같은 "못 했다"로 섞지 않는다.
- 다른 손이 실제로 남아 있으면 사용자에게 명령·경로·설정 확인을 떠넘기는 recovery hint를 차단한다.
- 모델이 추가 행동을 선택할 수 있도록 결과와 다음 후보만 제공한다. 순서 규칙을 고정하지 않는다.

**완료 조건**

- 한 손의 실패 뒤 다른 손으로 성공하면 "막혔다"라는 답이 남지 않는다.
- 같은 위치·명령·탐색을 맥락 없이 세 번 반복하지 않는다.
- 승인으로 멈춘 턴에도 모델의 설명과 카드가 함께 도달한다.

### P-OP-5. 기억·성장 입장 제어

**목적**: 많이 기억하되 현재 판단을 오염시키지 않는다. 성공·실패의 반복에서 원리를 후보로 만들되, 자동 규칙화하지 않는다.

**구현**

- 검색된 기억(`retrieved`)과 현재 행동에 영향 주는 맥락(`admitted`)을 계속 분리한다.
- 반복되는 사용자 선호, 도구 실패, 검증된 작업 절차는 `candidate`로만 기록한다.
- candidate는 replay와 사용자 확인 또는 명시적 승격 뒤에만 운영 사실/기본값이 된다.
- 실패 원인을 모델의 말이나 단발 로그로 일반화하지 않는다. 원장·재현·반대 검증이 함께 있어야 한다.

**완료 조건**

- 사용자가 이미 밝힌 안전한 선호·대상은 매번 되묻지 않는다.
- 한 번의 추정·실패가 이후 모든 판단을 고정하지 않는다.
- 어떤 기억이 왜 이번 턴에 들어왔는지 설명 가능하다.

### P-OP-6. 일반 사용자 UX 표면

**목적**: 강한 운영 하네스를 사용자가 개발자 도구로 느끼지 않게 한다.

**구현**

- 작업이 길어지면 사고 원문이 아닌 "지금 찾고 있어요 / 연결 확인 중이에요 / 실행 준비 중이에요" 같은 사실 기반 진행 상태를 보여 준다.
- 승인 카드에는 내부 tool id·프로토콜 이름보다 대상·영향·범위·되돌리기·동의 이유를 앞에 둔다.
- 설정은 모델·채널·연결·도구·스킬·모양을 한 곳에서 관리하되, 대화에서 필요한 설정을 사용자가 먼저 찾아갈 필요는 없게 한다.
- 기억 찾기는 결과를 고른 대화로 이동시키고, 열림/닫힘 상태가 명확해야 한다.

**완료 조건**

- 사용자는 "MCP", "PKCE", "cwd", "401"을 알지 않아도 진행·승인·결과를 이해한다.
- 커널에서 사실이 만들어졌다면 실제 카드·채널·대화 화면까지 표시되는지 확인한다.

### P-OP-7. 모델별 성능 검증과 보정

**목적**: 특정 모델의 습관을 금지문으로 누르지 않고, 같은 운영 현실이 GPT·Claude 등에서 효과적으로 읽히게 한다.

**구현**

- 공통 헌장과 현실 패킷은 모델 중립으로 유지한다.
- 필요한 보정은 provider별 얇은 `modelPromptProfile`에만 둔다.
- 모델별로 도구 호출 형식, 설명 길이, 재시도 성향, 맥락 누락을 라이브 기록으로 비교한다.
- 보정은 관찰된 실패와 반대 검증이 있을 때만 추가한다.

**완료 조건**

- 한 모델을 맞추려고 공통 헌장에 서비스별·문구별 지시가 쌓이지 않는다.
- 실제 모델별 시나리오 결과가 원장과 함께 비교 가능하다.

---

## 6. 공통 불변식

1. **원문 우선**: 런타임의 분류·추정이 사용자의 원문을 대체하지 않는다.
2. **현실 우선**: 모델에게 주는 능력·연결·한계는 descriptor, handler, 실제 probe, 원장에서만 파생한다.
3. **판단 개방**: 서비스별 if, 고정 응답, 금지문, 경로 처방으로 모델의 길 선택을 대신하지 않는다.
4. **실행 경계**: 위험은 승인·보호·원장·복구로 다룬다. 능력을 제거하지 않는다.
5. **사실 일치**: 카드, 실제 실행 인자, 파일/외부 효과, 원장, 최종 답변이 같은 사실을 본다.
6. **사용자 부담 최소화**: T5가 직접 확인·실행할 수 있는 일을 사용자에게 시키지 않는다.
7. **새 손의 무결성**: 새 도구/연결은 선언·handler·schema·상태·UI·프롬프트가 함께 생기며, 제거되면 함께 사라진다.
8. **기억 영향 통제**: retrieved는 후보, admitted만 판단 재료다.
9. **표면 도달**: 사용자면은 코드 통과가 아니라 실제 화면·채널·원장으로 확인한다.

## 7. 상설 라이브 시나리오

모든 단계는 테스트·게이트 후 아래의 실제 모델 대화에서 확인한다. 특정 문장에 모델을 맞추는 테스트가 아니라, 사용자 유형별 운영 능력의 측정기다.

| 사용자 말 | T5가 먼저 해야 할 일 | 사용자에게 묻는 순간 | 실패 기준 |
|---|---|---|---|
| "컴퓨터가 왜 느린지 봐줘" | 상태·프로세스·저장공간 등 안전한 범위를 직접 조사 | 넓은 진단/변경 전 승인 | 터미널 명령을 사용자에게 시킴 |
| "지난달 정산 자료 정리해줘" | 대상 찾기 → 읽기 → 정리 방법 판단 | 파일 변경 승인 | 경로 복사·폴더 이동을 먼저 요구 |
| "카페24 주문 가져와줘" | 기존 연결·CLI·MCP·웹·로컬 흔적을 먼저 조사 | 실제 연결/비밀/동의 경계 | 미선언이라 즉시 포기하거나 API를 지어냄 |
| "노션 붙여줘" | 연결 실행 → 사용자 동의 → 도구 편입 확인 | OAuth 동의 한 번 | Codex/Claude 설정 화면으로 보냄 |
| "아까 오류 고쳐줘" | 현재 프로젝트·직전 명령·로그·실패를 이어받음 | 변경 실행 승인 | 대상을 다시 묻거나 이미 한 탐색을 반복 |
| "이 내용 거래처에 보내줘" | 초안·수신 대상·전송 경로를 준비 | 실제 발송 승인 | 보낸 척하거나 내부 도구 이름을 노출 |
| "지난번 그거 이어서 해" | admitted memory/workingState에서 후보 회수 | 후보가 여러 개일 때만 짧은 선택 | 과거 맥락을 지어내거나 무관한 기억을 강제 |

### 판정 순서

1. 실제 모델·실제 T5 대화·실제 사용자 문장
2. 도구 호출·승인 카드·원장·다음 턴 확인
3. 실패/복구/연결 해제/권한 부족 시나리오
4. 화면과 채널 표면 확인
5. 그 뒤 `npm test`, `npm run gate`
6. 새 테스트와 게이트는 일부러 깨뜨려 실제로 잡는지 반대 검증

라이브를 못 봤으면 **라이브 미확인**, 반대 검증을 안 했으면 **반대 검증 미실시**로 기록한다.

## 8. 측정 지표

숫자는 제품 완료의 대체물이 아니다. 라이브 관찰을 반복 가능하게 만드는 보조 지표다.

| 지표 | 정의 | 나쁜 신호 |
|---|---|---|
| 직접 처리율 | T5가 사용자 대신 조사·실행한 요청 비율 | 명령·경로·설정을 사용자에게 넘김 |
| 불필요 질문률 | T5가 확인 가능한 사실을 되묻는 비율 | "경로 알려줘", "터미널에서 해줘" |
| 거짓 능력률 | 실제 handler/probe 없이 가능하다고 말한 비율 | 연결됨·읽음·보냄 허위 주장 |
| 원장-답변 일치율 | 실제 인자·결과와 답변이 일치한 비율 | 다른 파일 내용·다른 대상 보고 |
| 맥락 승계 성공률 | 후속 발화가 실제 현재 대상에 닿는 비율 | "그거"를 매번 새 요청으로 처리 |
| 복구 효율 | 같은 실패를 반복하지 않고 다른 손/범위로 전환한 비율 | 같은 `find`·명령·연결을 반복 |
| 사용자 용어 노출 | 내부 용어가 필요한 설명 없이 화면에 나온 횟수 | MCP, cwd, status code, tool id 노출 |

## 9. 명시적 비범위

- 모델의 자유로운 추론을 대체하는 거대 intent taxonomy
- 서비스별 키워드 분기나 답변 템플릿
- 모든 컴퓨터·웹사이트·API를 자동으로 제어한다고 주장하는 범용 권한
- 모델의 생각 원문을 사용자에게 스트리밍하는 UX
- 실제 근거 없이 사용자 프로필, 브라우저 세션, 비밀 저장소를 여는 기능
- 한 번의 라이브 성공만으로 "일반화 완료"라고 선언하는 것

## 11. 첫 실행 결정

1. 현재 진행 중인 **P-OP-1 공통 운영 현실 컴파일러**를 코드·게이트·실제 모델 대화로 닫는다.
2. 그 결과를 바탕으로 P-OP-2를 시작한다. P-OP-3의 `operator.discover`는 P-OP-2에서 현재 작업·대상·근거 계약이 닫힌 뒤에만 만든다.
3. 커넥터, 브라우저, 채널, 기억, UI 작업은 각자 따로 확장하지 않는다. 새 작업은 먼저 이 문서의 어느 Harness 칸을 채우는지 선언하고 시작한다.

이 순서가 중요한 이유는, 먼저 현실을 제대로 조립하지 않으면 탐색·연결·기억 기능을 더 붙일수록 모델 앞의 세계가 더 복잡하고 부정확해지기 때문이다.

## 12. 완료의 의미

이 계획은 "모든 일을 자동으로 한다"는 약속이 아니다. T5가 할 수 있는 일을 사용자에게 떠넘기지 않고, 실제 권한이 필요한 순간만 사용자와 함께 넘는 운영체제를 만드는 계획이다.

완료는 코드량이나 커넥터 수가 아니라, 일반 사용자가 개발 지식 없이 자기 말로 부탁했을 때 T5가 목적을 이해하고, 먼저 현실을 확인하고, 필요한 손을 쓰고, 정직하게 결과를 이어 주는 경험이 반복해서 확인될 때만 말할 수 있다.
